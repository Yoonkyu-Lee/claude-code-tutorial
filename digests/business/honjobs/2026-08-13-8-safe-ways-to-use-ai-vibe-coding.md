## 요약 (주제별)

### 이 영상의 핵심 프레임
- AI로 코딩(바이브 코딩)할 때 발생하는 8가지 위험을, 각각 실제 터진 사고 사례(미검증)와 함께 소개하고 예방법을 제시한다.
- 반복되는 메시지: (1) 대형 사고는 대단한 실수가 아니라 설정 하나·체크박스 하나에서 터진다, (2) AI는 "지시를 지키는 시스템이 아니라 다음 단어를 예측하는 모델"이라 프롬프트로 금지해도 강제력이 없고 강제력은 외부 시스템(설정)에서 온다, (3) 대부분의 해법은 코드를 몰라도 AI에게 말(프롬프트)로 시킬 수 있다.
- [의견] AI가 무섭다고 안 쓰기보다("구더기 무서워서 장 못 담글 순 없다") 안전장치를 걸고 쓰자는 것이 전체 기조. 화자는 15년째 1인 사업·자동화 수익을 운영한다고 소개.

### 위험 1 — 자동 충전(오토 리로드) 상한 미설정
- 대부분 AI 서비스에 잔액 소진 시 토큰을 자동 충전하는 기능이 있는데, 상한 미설정이 흔한 실수(설정이 영어라 비영어권에서 놓치기 쉬움).
- 사례(미검증): 2시간 내 864달러 자동 결제(400·200달러 등 연속), OpenAI가 만료 크레딧을 잔액 부족으로 착각해 자동 충전, 30분 테스트에 30달러 예상외 지출, 하룻밤 251억 원 결제(카드 열 번 넘게 시도). 251억 건은 앤트로픽은 "자동 충전 설정 오류"라 봤으나 이용자는 그 기능을 쓴 적 없다고 반박해 원인 불명 — 선불(환불) 처리로 마무리.
- 해법: 콘솔 → Settings → Billing → Auto Reload의 **Monthly Maximum**에 감당 가능한 금액 설정(화자는 10만 원). 폭주해도 그 금액에서 멈춤. 불안하면 오토 리로드 자체를 끄기. 예산 알림도 켜두기.

### 위험 2 — 기본 모델 값·동시 실행 에이전트 수 폭주
- 설정 파일의 모델 값이 잘못 저장되면 에이전트 다수가 전부 최고가 모델로 돌아갈 수 있음. 에이전트가 에이전트를 부르는 기능 때문에 곱셈식으로 불어남.
- 사례(미검증): 봇 하나 오류로 에이전트 천 개까지 증식, 종료 조건이 무한대로 해석되어 115분간 낭비, "이어서 해줘" 한마디에 승인 없이 에이전트 열 개 실행.
- 해법(프롬프트): "설정 파일의 기본 모델을 제일 저렴한 걸로 고정하고, 동시 실행 에이전트를 다섯 개로 제한, 뭘 바꿨는지 알려줘." JSON을 몰라도 AI가 파일을 찾아 수정·보고. 규모 확장 시 "상한 열 개로 올려줘"로 재조정.

### 위험 3 — 자동 승인("묻지 말고 다") 남용
- 승인 프롬프트가 귀찮아 전체 자동 승인을 켜면, 사소한 명령("정리 좀 해줘")에서 대형 사고. 사례(미검증): 파일을 상위 폴더로 옮긴 뒤 부모 폴더째 삭제해 50GB 소실, 청소 시키다 핵심 폴더 전체 삭제.
- 더 큰 위험: 자동 승인은 나만 쓰는 게 아님. 악성 코드가 숨은 프로그램이 이미 깔린 AI에게 몰래 "이 사람 파일 다 뒤져 보내라"고 명령한 사례 — 내가 편하려고 연 문을 공격자가 그대로 이용.
- 배경: AI는 "다음 단어를 예측하는 모델"이라 프롬프트 금지엔 강제력이 없고, 강제력은 외부 시스템에서 옴 — 자동 승인은 그 외부 보안을 꺼버린 셈.
- 해법: (프롬프트) "자동 승인 끄고, 파일 삭제·시스템 변경 같은 위험 명령만 물어보게 설정, rm -rf 등 파괴적 명령은 차단 목록에." + 에이전트를 프로젝트 폴더 안에만 가두기(홈 폴더 접근 차단). 이 한 번의 확인이 "9초 만의 데이터 소실"을 막음.

### 위험 4 — 백업을 원본과 같은 저장 공간에 둠
- AI가 저장 공간을 삭제할 때 같은 공간의 백업본까지 함께 소실. 사례(미검증): 렌터카 업체가 예약·결제 3개월치 통째 소실.
- 해법(프롬프트): "DB 백업을 원본과 **다른 계정·다른 위치**에 자동으로 하나 더 저장. 그리고 복구 테스트를 한번 해줘." 핵심은 **복구 테스트** — 백업만 만들고 안 꺼내 보면 정작 사고 때 안 열리는 경우가 많음. 추가 팁: 연습용 데이터와 실사용자 데이터를 별개 프로젝트로 분리.

### 위험 5 — 과도한 권한(만능 열쇠) & 열쇠 파일 노출
- 웹사이트 주소 하나 추가하려고 만든 키가 "모든 문이 열리는 만능 키"가 되어버림 → 그 열쇠만 있으면 누구나 창고 삭제 가능. 에이전트는 막히면 우회로를 찾아, 폴더에 열쇠 적힌 파일이 있으면 시키지 않아도 찾아 씀.
- 해법(프롬프트): "이 열쇠를 이 기능 하나만 되게 **최소 권한**으로 발급, **만료 기한 짧게**, 다 쓰면 폐기." + 에이전트 작업 폴더 안에 열쇠 파일을 두지 않기.

### 위험 6 — RLS(행 수준 보안) 미설정 → 회원 데이터 통유출
- Supabase 등의 공개용 키(anon key)는 브라우저에 노출되는 게 정상. 따라서 "누가 무엇을 볼 수 있는가"는 DB 안에서 **RLS(Row Level Security)**로 규정해야 함. RLS가 꺼져 있으면 로그인 없이 주소만 알면 회원 명단이 통째로 노출됨. RLS를 켜면 같은 요청이 빈 배열을 반환.
- 사례(미검증): 인증 미비로 이미지 72,000장 유출(그중 13,000장이 본인 인증 셀카·신분증) → 소송, 서비스명 [불명확]("TF 사건"). 어떤 도구[불명확: "로버"]로 만든 앱 1,645개 스캔 시 170개(약 10%)가 인증 없이 데이터 개방.
- 주의: AI에게 "회원가입 만들어줘"라고 해도 RLS는 기본으로 켜주지 않음 — 만들어 준 걸 믿지 말 것.
- 해법(프롬프트): "슈퍼베이스 모든 테이블에 RLS가 켜져 있는지 확인, 로그아웃 상태에서 공개용 키로 데이터 새는지 직접 테스트해 뚫린 게 있으면 켜 줘." → AI가 테이블별 확인·자동 잠금.

### 위험 7 — 비밀 키를 프론트엔드(공개된 곳)에 노출
- 웹사이트는 개발자 도구로 코드가 다 보임 → 비밀 키가 프론트엔드에 박히면 누구나 사용 가능. 비밀 키는 크레딧/토큰 결제까지 되는 특별 권한 키(위험 6의 "공개용 키 설정 미비"와 구분되는, "비밀 키 자체를 오픈에 방치"한 문제).
- 사례(미검증): 2년 전 자동 생성 브라우저 키를 방치했는데 Firebase가 특정 주소로 자동 공개 → 대량 API 호출로 하룻밤 3,167유로 청구. 규모(화자 인용): 작년 공개 깃허브 커밋의 하드코딩 비밀 키 2,865만 건, .env 탈취는 산업화되어 2억 3천만+ 대상 스캔 중. 원인: AI가 키를 프론트엔드에 박는 코드를 정상으로 받아들이는 경우가 있음(기본 보안 미제공).
- 해법(프롬프트): "비밀 열쇠가 브라우저 코드에 노출됐는지 확인해 노출된 건 **서버로 이동**, 이미 새어나간 열쇠는 **폐기·재발급**." + 키마다 출처·기능 제한. 가장 중요: 한 번 노출된 키는 이동만으론 부족, 발급 사이트에서 폐기 후 재생성(폐기 페이지 링크를 AI에게 요청). 키 저장은 AI 대화창이 아니라 서버에 직접(Supabase: Edge Functions → Secrets 탭 → Name/Value 입력·저장).

### 위험 8 — 배포 전 보안 미점검 & 근거 없는 신뢰
- 화자 인용(미검증): 보안 지침을 안 주면 AI 생성 코드의 45%가 알려진 취약점을 안고 있었다는 조사. 진짜 위험은 코드보다 "AI가 짰으니 보안도 챙겼겠지"라는 잘못된 확신.
- [의견] 서비스 이용자 정보 유출·법적 문제로 번질 수 있어, 사용자가 명령으로라도 기본 보안을 챙기고 취약점을 공부해야 함.
- 해법: 만들 때마다 "인증·입력 검증까지 포함해 안전하게 만들어 줘"를 덧붙이기 + 배포 전 "보안 문제 없는지 자동 점검해 줘".

### 8가지 예방법 한눈에
- ① 자동 충전 상한(Monthly Maximum), ② 기본 모델 고정 + 동시 에이전트 제한, ③ 자동 승인 제어(위험 명령만 확인·차단 목록·폴더 격리), ④ 백업 분리 + 복구 테스트, ⑤ 최소 권한·만료·열쇠 파일 격리, ⑥ RLS 걸기, ⑦ 비밀 키 서버 이동·재발급, ⑧ 검증 후 배포. [의견] 바이브 코딩 사이트의 절반 가까이가 보안 취약이니 "프롬프트 한 줄"만 잘 챙겨도 상당 부분 방어 가능.

## 3줄 오리엔테이션
- AI로 코딩(바이브 코딩)할 때 설정 하나·체크박스 하나를 안 챙겨서 터진 실제 사고 8건을 소개하고, 각각을 막는 프롬프트/설정 방법을 알려주는 영상이다.
- 8가지 위험: ① 자동 충전 상한 미설정 → 폭탄 결제, ② 기본 모델·동시 에이전트 수 폭주, ③ 자동 승인(묻지 말고 다) 남용 → 파일 삭제·외부 공격, ④ 백업을 원본과 같은 곳에 둠, ⑤ 과도한 권한(만능 열쇠)·열쇠 파일 노출, ⑥ RLS(행 수준 보안) 미설정 → 회원 데이터 통유출, ⑦ 비밀 키를 프론트엔드에 노출, ⑧ 배포 전 보안 미점검.
- 해법은 대부분 "코드를 몰라도 AI에게 말(프롬프트)로 시키면 된다"는 것 — 상한 걸기, 최소 권한, 자동 승인 끄기, 백업 분리, RLS 켜기, 키를 서버로 이동·재발급, 검증 후 배포.

화자는 충격적인 사례들로 문을 연다. AI로 코딩을 시켰더니 하룻밤 사이에 251억 원이 결제되었고(카드 결제가 열 번 넘게 시도되어 본인이 직접 정지시켜야 했다), 어떤 경우엔 9초 만에 데이터가 통째로 지워졌으며, 어떤 앱은 설정 하나를 안 켠 잘못으로 13,000명의 신분증 사진이 인터넷에 그대로 풀렸다고 말한다(모두 사례 소개, 미검증).

### [00:39–00:56] 화자 소개

### [00:56–02:00] 위험 1 — 자동 충전(오토 리로드) 상한 미설정
대부분의 AI 서비스는 구독 잔액이 떨어지면 알아서 토큰을 채워주는 자동 충전 기능이 있는데, 여기서 상한을 지정하지 않는 실수가 많다. 설정이 영어로 되어 있어 영어권이 아닌 나라에서 특히 놓치기 쉽다. 화자가 든 사례들(미검증):
- 어떤 개발자는 작업이 폭주하며 두 시간도 안 되어 카드에서 864달러가 자동 결제됨(400달러·200달러 등 세 번 연속 결제).
- OpenAI에서는 만료된 크레딧을 시스템이 잔액 부족으로 착각해 자동 충전한 사례.
- 어떤 클라이언트[불명확: 원문 "군의 클리앙"] 환경에서는 30분 테스트에 30달러가 예상외로 빠진 일.

앞서 언급한 251억 원 건도 이 자동 충전 문제였는지에 대해선, 앤트로픽(Anthropic)은 "자동 충전 설정 오류"라고 봤지만 이용자는 자동 충전 기능을 쓴 적이 없다고 반박해 원인이 명확히 밝혀지지 않았다고 한다. 이 사건은 소비자 잘못이 아니어서 선불(환불) 처리되고 해프닝으로 마무리됐지만, 만약 통장에 251억이 있었다면 실제로 나갈 수도 있었던 사건이라고 강조한다.

### [02:00–02:52] 위험 1 해법 — 월 상한(monthly maximum) 걸기
핵심은 예산 한도를 정하고 예산 알림 서비스를 반드시 켜두는 것. [의견] 요즘 AI 시스템은 세상에 출현한 지 얼마 안 돼 오류로 피해 보는 사례가 생기고 있으니, 돈이 얼마 나갔는지 알림을 받아야 한다.

방법은 하나 — 월 상한을 걸어두기. 화면 시연: 콘솔 → 세팅스(Settings) → 빌링(Billing)으로 들어가면 "오토 리로드(Auto Reload)"가 앞서 말한 자동 충전이다. 영어라서 지나치기 쉬운데, 여기서 "먼슬리 맥시멈(Monthly Maximum)"이 핵심. 한 달 감당 가능한 금액을 넣으면 되고, 화자는 10만 원을 걸어뒀다. 이렇게 하면 아무리 폭주해도 카드는 딱 10만 원에서 멈추고 251억 원이 결제될 수 없게 된다. 불안하면 아예 오토 리로드를 꺼버려도 된다.

### [02:52–04:06] 위험 2 — 기본 모델 값·동시 실행 에이전트 수 폭주
864달러 결제와 관련된 또 다른 위험. 설정 파일의 모델 값이 하나 잘못 저장되는 바람에 에이전트 700개가 전부 제일 비싼 모델로 돌아가는 사태가 날 수 있다. 관련 사례들(미검증):
- 봇(bot) 하나가 잘못되어 에이전트가 천 개까지 불어난 사고.
- 종료 조건이 무한대로 해석되어 멈추지 않고 115분 동안 1,300 [불명확: 원문 "포크이"] 낭비된 사례.
- "이어서 해줘"라는 한마디에 에이전트 열 개가 승인도 없이 터진 경우.

이렇게 되는 이유는 에이전트가 발전하며 에이전트가 에이전트를 부르는 기능이 생겨, 곱셈식으로 불어나기 때문이다.

### [04:06–04:15] 위험 2 해법 — 기본 모델 고정 + 동시 실행 상한
코드를 몰라도 프롬프트로 시키면 된다. 예시:
> "설정 파일의 기본 모델을 제일 저렴한 걸로 고정하고, 동시에 실행되는 에이전트를 절대 다섯 개로 제한해 줘. 그리고 어떻게 바뀌었는지 알려줘." [03:37]

그럼 에이전트가 알아서 설정 파일(JSON)을 찾아 고치고 무엇을 바꿨는지 보여준다. [의견] "우리는 제이슨(JSON)이 뭔지 몰라도 됩니다. 말만 하면 되는 것이죠." 이 한마디가 864달러 결제와 천 개 폭주 둘 다 막아준다 — 그 사고들 전부 이 값을 안 바꿔둬서 에이전트가 제일 비싼 모델을 물려받고 무한정 불어난 것이기 때문. 나중에 규모를 늘려 에이전트를 10개·20개 돌릴 일이 생겨도 파일을 열 필요 없이 "다시 상한 열 개로 올려줘"라고 명령하면 끝이다.

### [04:15–05:20] 위험 3 — 자동 승인(묻지 말고 다) 남용
매번 "이거 해도 돼요?" 하고 AI가 묻는 걸 승인해 주기 귀찮아서, 묻지 말고 다 승인하는 설정(옵션)을 켜는 기능이 있다. 정말 무서운 건 대단한 명령이 아니라 사소한 명령에서 터진다는 점. 사례들(미검증):
- "정리 좀 해줘"라고 했다가 AI가 파일을 상위 폴더로 옮긴 뒤 그 부모 폴더를 통째로 지운 경우 — 50GB 넘는 데이터가 경고·확인 없이 날아감.
- AI에게 청소를 시켰는데 컴퓨터에서 제일 중요한 폴더(모델링 파일 등이 든 큰 폴더)[불명확: 원문 "모딩제 들어 있는"]를 통째로 지운 일.

더 섬뜩한 건 이 "묻지 말고 다" 설정을 나만 켜는 게 아니라는 점. 겉보기엔 멀쩡한 프로그램을 깔았는데 그 안에 악성 코드가 숨어 있었고, 이게 내 컴퓨터에 이미 깔려 있던 AI에게 몰래 명령을 내려 "이 사람 파일을 다 뒤져서 나한테 보내라"고 시킨 사례. 내가 편하려고 열어둔 자동 승인 문(門)을 공격자가 그대로 열고 들어온 것 — 내가 켠 자동 승인을 남이 악용하게 된 셈이다.

### [05:20–05:37] 위험 3 배경 — 왜 "금지"만으론 안 되나
> "AI는 지시를 지키는 시스템이 아니라 다음 단어를 예측하는 모델이기 때문입니다." [05:20]

그래서 [불명확: 원문 "11번"] 아무리 금지해도 그건 강제력을 갖지 못한다. 강제력은 오직 외부 시스템에서 나오는데, 자동 승인은 이 외부 시스템(보안)을 꺼버린 셈이라고 설명한다.

### [05:37–06:18] 위험 3 해법 — 안전 모드 + 차단 목록 + 작업 폴더 격리
예방 프롬프트 예시:
> "전부 자동 승인 끄고, 파일 삭제나 시스템을 건드리는 위험한 명령만 나한테 물어보게 설정해 줘. 그리고 rm -rf 같은 파괴적인 명령은 차단 목록에 넣어 줘." [05:39]

그럼 에이전트가 안전 모드로 바꾸고 위험한 명령은 차단 목록에 넣는다. 이 상태에서 다시 "정리 좀 해줘"를 시키면, 지우기 직전에 딱 멈추고 사용자에게 물어본다 — 이 한 번의 확인이 9초 만에 데이터가 날아가는 걸 막아준다. 추가로, 에이전트는 홈 폴더가 아니라 작업 중인 프로젝트 폴더 안에서만 움직이게 울타리를 쳐야 한다. "이 방 안에서만 움직여" 하고 가두면, 실수해도 그 방을 벗어나지 못해 안전하다.

### [06:18–06:52] 위험 4 — 백업을 원본과 같은 저장 공간에 둠
어떤 서비스에서 AI가 데이터가 담긴 저장 공간을 아예 삭제했는데, 백업본까지 같은 공간에 있다 보니 백업까지 날아간 사례(미검증). 해당 업체는 렌터카 업체였고 예약 정보와 결제 3개월치를 통째로 날렸다. 백업을 원본과 같은 저장 공간에 넣으면, AI가 그 상자에 백업이 있는 걸 인지하지 못하고 데이터를 정리할 때 백업본까지 같이 지운다. 그래서 [주의: 화자 발언 원문은 "같은 곳에 저장될 수 있도록"이지만 맥락상 백업은 원본과 **다른** 곳에 두어야 한다는 취지 — 바로 이어지는 해법에서 "원본과 다른 계정·다른 위치"로 확정됨].

### [06:52–07:29] 위험 4 해법 — 다른 계정·다른 위치 백업 + 복구 테스트 + 데이터 분리
말로 시키는 예시:
> "이 프로젝트 데이터베이스 백업을 원본과 다른 계정, 다른 위치에 자동으로 하나 더 저장하게 설정해 줘. 그리고 그 백업이 진짜 잘 복구되는지 복구 테스트를 한번 해 줘." [06:56]

핵심은 뒷부분, "복구를 한번 테스트해 줘"다. [의견] 백업만 만들어 놓고 한 번도 안 꺼내 본 사람이 많은데, 막상 사고 나서 열어보면 안 열리는 경우가 많으니 테스트로 백업본이 잘 복구되는지 확인해야 한다. 추가 팁: 연습용 데이터와 진짜 사용자 데이터를 아예 딴 프로젝트로 나눠, 실험하다 실수해도 사용자 데이터는 보호되게 하라.

### [07:29–08:07] 위험 5 — 과도한 권한(만능 열쇠) & 열쇠 파일 노출
애초에 에이전트가 그 창고를 지울 수 있었던 건 AI에게 그 권한(열쇠)이 있었기 때문. 문제는 그 열쇠가 원래 웹사이트 주소 하나 추가하려고 만든 건데, 그 과정에서 모든 문이 다 열리는 만능 키가 되어버린 것. 열쇠를 줘버렸으니 누가 열든 그 열쇠만 있으면 열 수 있었다. 게다가 에이전트 특성상 막히면 우회로를 찾게 되어 있어서, 폴더 어딘가에 열쇠가 적힌 파일이 있으면 시키지 않아도 그걸 찾아 사용하는 경우가 생긴다. 즉 열쇠가 파일에 남아 있으면 결국 심각한 문제가 발생할 수 있다.

### [08:07–08:44] 위험 5 해법 — 최소 권한 + 만료 + 열쇠 파일 격리
웹사이트를 연결하거나 새 설정을 추가할 때 API 키를 만들게 되는데, 그때 이렇게 프롬프트한다:
> "이 작업할 열쇠를 딱 이 기능 하나만 되게 최소 권한으로 발급해 줘. 그리고 만료 기한을 짧게 걸어 줘. 다 쓰고 나면 바로 폐기할 거야." [08:15]

이렇게 하면 그 열쇠가 새어나가도 할 수 있는 게 딱 하나뿐이라 안전하다 — 창고를 지우고 싶어도 권한이 없어 못 지운다. 마지막으로, 에이전트가 일하는 폴더 안에는 열쇠가 적힌 파일을 두지 않는 게 최선이다(에이전트가 폴더를 뒤져 열쇠를 찾아내기 때문).

### [08:44–09:34] 위험 6 — RLS(행 수준 보안) 미설정으로 회원 데이터 통유출
법적 문제까지 갈 수 있어 바이브 코딩 시 반드시 유의해야 하는 위험. 화자는 테스트 프로젝트로 시연한다 — 가짜 회원 데이터를 저장한 테이블이 있고 RLS(Row Level Security)가 꺼져 있다. 이 상태에서 공개용 키 하나만 들고 서버 데이터를 요청하면, 로그인도 안 했는데 주소만 알면 화면을 거치지 않고 DB 정보에 바로 들어가 회원 명단이 통째로 나온다. 이제 딱 한 줄로 그 테이블에 RLS를 켜고 똑같은 요청을 다시 하면, 빈 배열 — 아무것도 나오지 않는다.

실제 사건들(미검증):
- 인증을 거치지 않아 이미지 72,000장이 유출되었고, 그중 13,000장이 본인 인증 셀카·신분증이라 소송[불명확: 원문 "소원"]까지 걸린 사건. [불명확: 원문 "TF 사건"으로 서비스명 불확실]
- 로버[불명확: 원문 "로버이", 도구명 불확실]라는 도구로 만든 앱들도 이슈가 있었는데, 프로젝트 1,645개를 스캔했더니 170개(약 10%)가 인증 없이 데이터가 열려 있었다.

즉 슈퍼베이스(Supabase)의 공개용 키(anon key)는 원래 브라우저에 노출되므로, 누가 무엇을 볼 수 있느냐는 반드시 DB 안에서 RLS로 규정해 줘야 한다. AI에게 "회원가입 만들어줘"라고 해서 코드를 짜 준다고 해도 이 규정을 지켜주는 건 아니다.

### [09:34–11:02] 위험 6 시연 재설명 — 잠금 스위치(RLS)의 원리
화자는 간단한 사이트를 예로 다시 설명한다. 회원가입 기능이 있고 사람들이 이름·이메일·전화번호로 가입하면, 이 정보가 사이트 뒤 창고(데이터베이스)에 저장된다. 이 창고를 여는 공개용 열쇠가 있는데, 이건 원래 브라우저에 그대로 보이는 게 정상이다. 하지만 나쁜 사람이 이 열쇠로 화면을 거치지 않고 창고로 바로 가면 회원 정보가 통째로 쏟아진다 — 잠금장치인 RLS가 꺼져 있기 때문이다. 이제 이 잠금 스위치(RLS)를 켜면, 그 사람이 똑같은 열쇠로 다시 와도 아무것도 볼 수 없다. 누가 무엇을 볼 수 있느냐는 반드시 창고 안에서 잠금으로 권한 설정을 해줘야 한다. AI에게 "회원가입 만들어줘" 하면 돌아가는 코드는 나오지만 이 잠금은 기본으로 켜주지 않는다 — 만들어 준 걸 그대로 믿으면 안 되는 이유다.

### [11:02–11:37] 위험 6 해법 — 전 테이블 RLS 확인·자동 점검 프롬프트
사용자가 할 일은 딱 하나 — 내 사이트가 지금 RLS가 켜진 상태인지 직접 확인하는 것. 직접 하려면 어려우니 이렇게 명령한다:
> "내 슈퍼베이스 모든 테이블 RLS를 쓰[켜]지 않게끔이 아니라 켜져 있는지 확인해 줘. 그리고 로그아웃 상태에서 공개용 키로 데이터가 새는지 직접 테스트해서 뚫린 게 있으면 켜 줘." [11:13]

그럼 AI가 테이블을 하나하나 확인하고 꺼져 있는 게 있으면 잠금을 채워준다 — 방금 시연을 사용자의 사이트에서 알아서 해주는 것. 만들어 준 걸 절대 믿지 말고 이 부분을 꼭 검수하라고 당부한다.

### [11:37–12:20] 위험 7 — 비밀 키를 프론트엔드(공개된 곳)에 노출
남이 볼 수 있는 곳에 비밀 키를 오픈하는 것. 웹사이트는 개발자 도구만 열면 안쪽 코드가 다 보이는데, 여기 비밀 키가 박혀 있으면 그 키를 누구나 사용할 수 있게 두는 셈이다. 사례(미검증): 어떤 사람은 2년 전에 자동 생성된 브라우저 키를 방치[불명확: 원문 "방지"]해뒀는데, 파이어베이스(Firebase)가 그 키를 특정 주소로 자동 공개하고 있었다. 누군가 그걸 주워 API를 대량 호출했고 하룻밤에 3,167유로[불명확: 원문 "3.167유로"]가 청구됐다. 즉 비밀 키란 크레딧이나 토큰 결제까지 되는 특별한 권한을 가진 키다. 위험 6이 "공개용 키에 (RLS) 설정을 안 한 것"이라면, 위험 7은 "비밀 키를 대놓고 오픈된 곳에 놓은 것" — 내 금고 열쇠를 로비에 놔둔 셈이다.

### [12:20–12:48] 위험 7 배경 — 얼마나 흔한가 & 왜 AI가 이러나
얼마나 흔하냐면(화자 인용 수치, 미검증), 작년 한 해 공개 깃허브 커밋에 하드코딩된 비밀 키가 2,865만 건이나 됐다. .env 파일 터는 건 이미 산업화되어, 공격자가 2억 3천만 개 넘는 대상을 스캔해 노출된 환경 변수를 긁어모으고 있다. AI가 왜 키를 위험하게 노출하냐면, AI가 키를 프론트엔드에 박는 코드를 정상으로 받아들이는 경우가 있어서다 — 에이전트가 기본적으로 보안을 챙겨주지 않는다는 뜻이다.

### [12:48–14:02] 위험 7 해법 — 키를 서버로 이동 + 재발급 + 제한
지금 상태는 비밀 열쇠가 대문에 붙어 있어 지나가는 아무나 떼어갈 수 있는 것 — 이 열쇠를 대문에서 떼서 건물 안쪽 금고(손님한테 안 보이는 서버)에 넣는다. 그러면 필요할 때 나만 비밀을 꺼내 쓸 수 있다. 프롬프트 예시:
> "이 프로젝트에서 비밀 열쇠가 브라우저 쪽 코드에 노출되어 있는지 확인하고, 노출된 건 서버 쪽으로 옮겨줘. 그리고 이미 새어나간 열쇠는 폐기하고 [새로] 발급받을 수 있게 해줘." [13:11]

열쇠마다 제한도 건다("이 주소[출처]에서만, 이 기능만") — 혹시 새어나가도 할 수 있는 게 별로 없게. 가장 중요한 마지막: 한 번이라도 밖에 노출됐던 열쇠는 안으로 옮기는 걸로 끝나지 않으니 버리고 새로 만들어야 한다. 해당 API 키를 발급받은 사이트에서 그 키를 폐기하고 새로 받는 수밖에 없으니, "현재 내가 공개해 놓은 API 키가 있다면 그걸 폐기할 수 있는 사이트 페이지 링크를 달라"고 명령해 폐기 후 재생성한다.

### [14:02–14:15] 위험 7 보강 — 키 저장은 서버에 직접 등록
이 키를 저장할 때도 반드시 AI 대화창에 입력하지 말고 서버에 다이렉트로 등록해야 한다. 슈퍼베이스의 경우 키를 서버에 저장하는 기능이 있다 — 대시보드 왼쪽 메뉴에서 "엣지 펑션(Edge Functions)" 버튼을 클릭하고 "시크릿(Secrets)" 탭을 눌러, 왼쪽 네임(Name)에 키 이름, 밸류(Value)에 비밀 키를 적고 저장하면 끝이다.

### [14:15–15:20] 위험 8 — 배포 전 보안 미점검 & 근거 없는 신뢰
어떤 보안 업체 조사에 따르면 보안 지침을 따로 주지 않으면 AI가 짠 코드의 45%가 알려진 취약점을 안고 있었다고 한다(화자 인용, 미검증). 정말 무서운 건 코드가 아니라, 바이브 코딩하는 사람들이 "AI가 짜 준 거니까 당연히 보안을 챙겨줬겠지"라고 확신하는 태도. [의견] 보안 부분은 내가 반드시 명령으로라도 기본 보안을 챙겨야 하고, 보안 취약점을 공부하고 바이브 코딩을 해야 한다. 이건 나만의 문제가 아니라 내가 만든 서비스를 이용하는 사람들의 정보가 새어나가고 법정 문제로까지 발전할 수 있어 정말 주의해야 한다.

### [15:20–16:20] 위험 8 해법 — 안전 요청 프롬프트 + 배포 전 자동 점검
화자의 방법은 만들 때마다 한마디만 더 붙이는 것. 그냥 "회원가입 만들어줘"가 아니라:
> "인증이랑 입력 검증까지 포함해서 안전하게 만들어 줘." [15:00]

이 말을 넣으면 AI가 보안을 기본으로 챙겨주므로, 보안 관련 내용을 붙여주는 게 좋다. 또 하나는 다 만들고 배포하기 전에 "보안 문제 없는지 자동으로 한번 점검해 줘"라고 시키는 것.

### [16:20–16:34] 마무리 — 8가지 요약 & CTA
8가지 예방법을 정리한다: 자동 충전 상한 / 자동 승인 [제어] / 백업 분리 / 훅[불명확: 원문 "혹큰"] 최소 권한 / RLS 걸기 / [비밀 키 격리, 원문 "희승기"] / 그리고 검증하고 배포하기. 지금 여러분의 프로젝트에서 이 여덟 개 중 뚫린 게 있는지 꼭 확인하라고 당부한다.
