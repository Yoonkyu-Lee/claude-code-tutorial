## 요약 (주제별)

### 1. 문제 제기 — 아스트라는 일을 잘하는 대신 토큰을 빨리 태운다
- 출시 일주일 시점, 사용자들 사이의 공통 반응은 "일은 곧잘 하는데 토큰이 너무 빨리 녹는다".
- 화자 본인 경험: 제미나이·클로드·GPT를 모두 구독 중이며, GPT는 월 20달러 플러스를 쓰다가 아스트라로 여러 작업을 돌리면서 사용량이 급감해 **월 100달러 프로 요금제로 상향**했다. "일을 잘하긴 하는데 토큰도 정말 많이 쓰는 모델이라는 걸 제 금액으로 직접 체감한 셈"[00:32].
- [의견] 인터넷에는 게임 제작·건물 설계 같은 화려한 데모가 많지만, 평범한 직장인·학생은 매일 영상을 만들지 않는다 → 영상의 질문은 "귀찮아서 밀어둔 잡일에도 쓸모가 있는가, 그리고 덜 쓰면서 효과적으로 쓰는 법은 있는가".

### 2. 비용 구조의 핵심 개념 — 컴퓨터 유즈와 하네스
- **컴퓨터 유즈(Computer Use)**: 화면이 바뀔 때마다 상태를 확인하며 다음 행동을 이어가는 기능. 전용 연결(예: 캘린더 API)이 없거나 사람이 보듯 화면을 직접 확인해야 하는 사이트에서 쓴다. 모든 걸 마우스로 하는 게 아니라 **파일·전용 도구로 빠른 일은 그쪽, 화면을 봐야 하는 부분만 컴퓨터 유즈**.
- **하네스(harness)**: 긴 과정을 이어주는 장치. 모델이 다음 행동을 정하면 하네스가 도구를 실행하고 결과를 다시 모델에게 보여준다. 처음 요청과 지금까지 한 일을 계속 기억시키는 역할도 하며, 이걸 놓치면 같은 페이지를 또 열거나 끝낸 일을 반복한다.
- 엔비디아 GTC 타이페이에서 젠슨 황도 모델을 둘러싼 하네스·도구·작업 환경을 언급했고, 엔비디아 발표 자료에도 "에이전트가 일을 나누고 앞의 내용을 기억하고 도구를 쓰려면 하네스가 필요하다"는 설명이 들어가 있다(화자 인용).
- 일반 사용자는 하네스를 직접 만들지 않는다 — **ChatGPT 워크가 준비해 둔 하네스를 쓰고, 자료·목표를 주고 중간 승인을 하고 결과를 확인**하는 역할.

### 3. 토큰이 녹는 실제 메커니즘
- **맡긴 일의 길이 ≠ AI가 실제로 한 일의 길이.** 요가 일정 등록 한 문장에도 예약 내역 조회 → 캘린더 선택 → 애매하면 되묻기 → 등록 → 검증이 붙는다.
- 컴퓨터 유즈에서 **클릭 한 번당 고정 토큰이 빠지는 게 아니라, 화면 정보량과 판단 횟수에 따라 달라진다.** 화면이 바뀔 때마다 새 화면 정보가 들어오고, 모델은 매번 "처음 요청 + 지금까지 한 일"을 함께 읽는다. 마지막 답변이 "등록했습니다" 한 줄이어도 앞에서 여러 번 읽고 생각한 것.
- 코딩도 동일 구조: 폴더 열기 → 코드 검색 → 파일 읽기 → 수정 → 터미널 테스트 → (실패 시) 긴 오류 메시지 재입력 → 재수정. 화면에 남는 건 코드 몇 줄이지만 읽은 파일·명령 결과·테스트 기록 전부가 비용이다.
- **멀티 에이전트**: 각 에이전트가 자기 요청과 자료를 따로 읽고, 중심 에이전트가 결과를 다시 읽어 합친다 → 대기 시간은 줄어도 총 토큰은 늘 수 있다. "직원 세 명에게 같은 업무 설명을 나눠 주면 설명서도 세 번 읽는 거랑 비슷"[05:27].
- 줄일 수 있는 낭비: 오조작으로 같은 화면 반복 열람, 작은 수정에 붙는 불필요한 확인 작업, 일을 너무 잘게 쪼개 나누고 합치는 오버헤드.

### 4. 방식이 성능·비용을 바꾼다는 근거 — ARC 프라이즈
- ARC 프라이즈가 공개한 아스트라 평가에서 **같은 "높음" 설정에서도 하네스를 바꾸자 점수는 오르고 비용은 절반 아래로** 내려간 사례가 있다(인용, 미검증). 앞선 사고 내용을 잘 이어주고 긴 대화에서 덜 헤매게 만든 결과.
- 화자 유보: **퍼즐 평가라서 일반 회사 업무에 그대로 적용된다고 볼 수 없다.** 다만 "모델만큼이나 일을 굴리는 방식도 중요하다"는 증거로 제시.

### 5. 늘어난 위임 범위 — 공개된 활용 사례들
- **오픈AI 내부(린지 매캘럼 레미)**: 제품 출시 준비에서 AI가 기자 명단 관리, 브리핑 참석 여부 확인, 나온 기사 수집, 보고서 작성까지 수행. 화자 평가 — 글 한 편 쓰기보다 손이 많이 가는 일(신규 답장 반영, 처리 완료자 구분, 팀 보고서 양식 준수)이며, **사람에게 시켰으면 "어디까지 했어요?"를 몇 번 물었을 일이 한 덩어리로 이어진 것**.
- **공유된 프롬프트 유형**: ① 인터넷에 퍼진 주장을 원래 출처까지 추적하고 이견이 갈리는 부분을 확인해 가이드로 만들기, ② 스프레드시트를 검색·필터 가능한 웹 앱으로 만들고 계산 결과를 원본과 대조하기. 직장인의 자료 조사·보고서, 학생의 발표 자료 준비에 해당.
- **개인정보 삭제 요청(필리페 플로레스)**: ChatGPT 에이전트로 자신에 관한 정보를 찾고 사이트별 삭제 요청서를 작성해 절차 진행. **화자 유보 2건 — 아스트라 출시 전 사례라 GPT6 전용 기능이 아니며, 정보가 전부 지워졌다고 확인된 사례도 아니다.**
  - 안전한 요청 형태: "요청서도 작성하되, 보내기 전에는 어디로 어떤 내용을 보낼지 나한테 먼저 보여 줘"[07:57].
  - 주의: 본인 인증·최종 제출 같은 민감 단계는 사용자가 직접 해야 할 수 있고, **구글 검색 결과에서 사라진 것과 원본 사이트에서 지워진 것은 별개라 두 곳을 따로 확인**해야 한다.
- **ScreenSpot Pro(화면에서 지시한 위치 찾기)**: 아스트라 **약 93%**, 이전 세대 솔(Sol) **약 77%**(오픈AI 발표 기준). 화자 유보 — **인터넷 업무 전체의 성공 확률이 아니라 작은 버튼·입력란을 찾는 능력** 지표.

### 6. 토큰 절약법 (화자 정리 — 측정 절감률 아님)
- **원칙**: 프롬프트 글자 수를 줄이는 것보다 **비싼 모델이 맡는 구간과 반복 횟수를 줄이는 쪽**이 효과가 크다. ([불명확: 자막 원문 "에 박스"]가 소개한 방식 — 평범한 실행·확인은 솔, 어려운 판단만 아스트라 호출.)
- **모델 갈아타기 3단계(참석자 명단 예시)**: ① 솔 "중간"으로 "첨부한 답장을 보고 명단을 고치고, 같은 이름이거나 확실하지 않은 항목은 따로 모아 줘" → ② 애매한 항목만 남으면 같은 채팅에서 아스트라 "높음"으로 전환해 "원문과 다시 맞춰 보고, 같은 사람이라고 본 이유를 적고, 확실하지 않으면 '확인 필요'라고 남겨 줘" → ③ 다시 솔 "중간"으로 내려 확정 내용을 보고서에 반영.
  - **실행 주의**: 채팅창에 "솔로 해 줘"라고 쓰는 게 아니라 **메시지 전송 전 모델 선택 메뉴에서 직접 변경**해야 한다.
  - 역방향도 가능 — 업무 순서를 모르겠으면 아스트라를 앞에 잠깐 써서 처리 기준을 만들게 하고 나머지를 솔에 넘긴다.
- **추론 강도는 모델과 별개 설정**(중간 / 높음 / 매우 높음 / 최대, 계정·모델에 따라 표시 항목 다름):
  - 중간 — 회의록에서 담당자·날짜 추출, 정해진 양식에 자료 채우기
  - 높음 — 여러 자료 대조, 조건 확인
  - 매우 높음 — 숫자가 안 맞거나 예외가 많아 원인을 오래 찾아야 할 때
  - 최대 — 앞선 설정으로 풀지 못한 어려운 문제
  - **반전 규칙: 항상 낮게 잡는다고 절약되지 않는다.** 낮은 설정에서 같은 실수를 세 번 하고 고치느니 높은 설정에서 한 번에 끝내는 편이 총 토큰이 적을 수 있다 → **익숙한 일은 중간에서 시작, 막힌 부분만 상향**.
- **추가 에이전트 억제**: 명단 하나 고치는 데 에이전트 셋이 같은 자료를 따로 읽으면 분배·통합 토큰이 더 붙는다 → "이번 작업은 추가 에이전트 없이 직접 처리해 줘". 단 **서로 다른 사이트 여러 곳 동시 조사처럼 진짜 나눌 만한 일에는 나누는 게 낫다** — 무조건 금지가 아니라 판별.
- **끝나는 조건 명시**: "멋지게 만들어 줘"는 범위를 모른다 → "지난주 양식은 그대로 쓰고 이번 주 숫자·달라진 내용만 바꿔 줘. 합계가 맞는지 원문이랑 확인하면 끝이야"[11:52]. 학생용 예: "첨부한 자료 안에서 발표 초안을 만들어 줘. 자료에 근거가 없는 내용은 표시하고 인터넷 추가 조사는 하지 마." → **파일 안 확인 작업이 인터넷 전체 조사로 번지는 것을 차단.** 확인 작업을 빼는 게 아니라 종료 지점을 알려주는 것.
- **결과물 범위 통제**: [불명확: 자막 원문 "안"]으로 남은 제작자가 **45분 만에 작은 3D 데모**를 만든 뒤, 날씨·세부 표현을 계속 더해 **약 8시간 작업 후 주간 사용량의 절반**을 소진(개인 요금제·당시 환경 기준). 표 하나면 되는지 검색·수정 가능한 앱까지 필요한지에 따라 작업량이 완전히 달라진다 → **필요한 게 명단이면 명단 검증까지만 하고 끝내고, 확장은 결과를 본 뒤 결정.**
- **화자의 명시적 유보**: SNS의 절약법도 방향은 같지만 **"얼마나 절약된다"는 공통 수치는 아직 없다** → 자기가 자주 맡기는 일에서 결과와 사용량을 직접 비교해 볼 것.

### 7. 기업이 비싼 토큰을 감수하는 이유 — 조율 시간까지 계산
- 사람에게 시킬 때의 숨은 비용: 과장→대리→신입으로 내려가며 양식 설명, 되묻기, 부장 기준과 다르면 재작업, 타 부서 자료 대기.
- **AI가 못 없애는 것**: 부서 간 경쟁·의견 충돌. **줄일 수 있는 것**: 이미 접근 가능한 자료를 정해진 형식으로 만드는 일에서 발생하는 분배·진척 확인 시간.
- 공개 사례 2건(모두 회사 측 공개, **아스트라나 컴퓨터 유즈 단독 효과를 분리한 결과가 아님**):
  - **길버트+토빈(자막 음차 "길벌트 앤드 토비")** — ChatGPT 엔터프라이즈로 자료 조사·정보 추출이 **4시간 → 20분**. [불명확: 업무 종류를 자막이 "채용 자료 조사"로 옮김]
  - **[불명확: 자막 음차 "어디언스 스트래터지스"]** — 클로드 엔터프라이즈로 인터뷰 준비·분석이 **2시간 → 25분**.
- 금액 환산: 3시간 40분 절감 × 시간당 약 5만 원 ≈ **약 18만 원어치 시간**. 단 **그 돈이 그대로 남는다는 뜻은 아니며**, AI 이용료 + 사람이 결과를 확인·수정하는 시간을 빼고도 다른 일을 할 시간이 남는지를 봐야 한다.

### 8. 결론 프레임 — "토큰 절약"이 아니라 "되찾은 시간 대비 지불 가능액"
- 개인 계산식: 주간 보고서에 1시간 걸리던 것이 자료 제공 + 결과 확인 10분이면 **50분 절감** → 그 50분을 돌려받기 위해 토큰을 얼마나 쓸 수 있는가가 기준.
- [의견] 우리는 이미 배달비·택시비로 귀찮음과 시간을 돈으로 사고 있으며 AI도 같은 범주. "토큰을 무조건 적게 쓰는 것보다, 일을 맡긴 뒤에 내가 다시 해야 할 일이 얼마나 남았는지를 보는 편이 더 현실적"[15:18].
- [의견] 토큰을 아껴 엉성한 결과를 받느니, 더 쓰더라도 몇 시간 붙잡던 일을 빠르고 깔끔하게 끝내 준다면 지불할 명분이 생긴다.
- **첫 위임 권장 조건**: 내가 하기엔 귀찮으면서도 **결과가 맞는지 내가 직접 검증할 수 있는 일**(주간 보고서, 참석자 명단 등).
- **권장 루틴 요약**: 솔 "중간"으로 시작 → 애매한 부분만 아스트라 + 높은 설정 → 종료 조건 명시. 그러면 "토큰이 얼마나 녹았는지보다 내 시간이 얼마나 남았는지"가 보인다.

## 3줄 오리엔테이션
- GPT6 아스트라가 일을 잘하는 대신 토큰을 빠르게 태우는데, 그 이유는 "짧은 요청 뒤에서 모델이 여러 번 화면을 읽고 판단하기 때문"이다 — 그 구조를 컴퓨터 유즈와 하네스로 설명한다.
- 실제 절약은 프롬프트 글자를 줄이는 데서 오지 않는다. **비싼 모델이 맡을 구간을 좁히고, 추론 강도를 조절하고, 불필요한 추가 에이전트와 반복을 줄이고, 끝나는 조건을 미리 알려주는 것**이 핵심이다.
- 마지막 프레임은 "토큰을 아끼자"가 아니라 **"내가 되찾은 시간 대비 얼마까지 토큰을 쓸 수 있나"** — 배달비·택시비처럼 귀찮음을 돈으로 사는 계산으로 본다.

## 전문 — 시간순 워크스루

### [00:00–00:58] 도입 — 일은 잘하는데 토큰이 너무 빨리 녹는다
GPT6 아스트라 출시 일주일 즈음, 써 본 사람들 사이에서 "일은 곧잘 하는데 토큰이 너무 빨리 녹는다"는 이야기가 나오고 있다. 화자는 제미나이·클로드·GPT를 모두 구독 중이고 GPT는 월 20달러 플러스 요금제를 쓰고 있었는데, 아스트라로 여러 작업을 돌리기 시작하니 사용량이 생각보다 훨씬 빨리 줄어 결국 **월 100달러 프로 요금제로 올렸다**(화자 본인 지출 경험).

> "일을 잘하긴 하는데 토큰도 정말 많이 쓰는 모델이라는 걸 제 금액으로 직접 체감한 셈이죠." [00:32]

인터넷에는 아스트라 능력치를 보여준다며 게임을 만들고 건물을 설계하는 영상이 계속 올라오지만, 평범한 직장인이나 학생이 매일 영상을 만들지는 않는다. [의견] 그래서 "이 훌륭한 모델이 우리가 귀찮아서 밀어둔 일에도 쓸모가 있는지", "토큰을 덜 쓰면서 효과적으로 쓰는 법은 없는지"가 이 영상의 질문이다.

### [01:00–01:33] 출발점 사례 — 댄 시퍼의 요가 수업 일정 등록
화면에 띄운 건 댄 시퍼(자막 음차 "댄시퍼")가 X에 올린 실제 채팅 화면이다. 아스트라에게 부탁한 일은 "방금 신청한 요가 수업의 자세한 내용을 확인해서 오늘 캘린더에 넣어 줘" 한 문장이었고, 본인은 "어려운 수학 문제도 풀 수 있는 AI를 나는 요가 일정 넣는 데 쓴다"고 적었다. 화자는 이것이 AI와 일상의 거리를 좁히는 전환점이라고 본다 — **"이거 어떻게 하는지 알려줘"에서 "이 귀찮은 일 좀 나 대신 끝내 줘"로 바뀐 것**이다.

### [01:33–02:00] 짧은 요청 뒤에 숨은 긴 절차
일정 하나를 넣는 짧은 요청에도 AI가 뒤에서 할 일은 꽤 많다. 예약 내역에서 날짜와 시간을 찾고, 어느 캘린더에 넣을지 확인하고, 시간이 애매하면 사용자에게 되묻고, 등록 후 제대로 들어갔는지 확인해야 한다. 사이트 화면을 직접 다뤄야 하면 과정은 더 길어진다 — 화면을 읽고, 입력란을 찾고, 내용을 넣고, 저장 버튼을 누르고, 저장이 실패하면 오류 메시지를 읽고 재시도한다.

### [02:00–02:27] 컴퓨터 유즈(Computer Use)의 정의와 적용 범위
이렇게 **화면이 바뀔 때마다 상태를 확인하면서 다음 행동을 이어가는 기능이 컴퓨터 유즈**다. 캘린더가 ChatGPT와 바로 연결돼 있으면 전용 도구로 등록할 수도 있고, 컴퓨터 유즈는 그런 연결이 없거나 사람이 보듯 화면을 직접 확인해야 하는 사이트에서 쓴다. 모든 일을 마우스로 처리한다는 뜻이 아니라, **파일이나 전용 도구로 빠르게 처리할 수 있는 일은 그쪽을 쓰고, 화면을 봐야 하는 부분만 컴퓨터 유즈가 맡는 방식**이다.

### [02:27–03:00] 하네스(harness) — 긴 과정을 이어주는 장치
사용자는 명령 한 문장을 보냈지만 AI는 자료를 찾고 일정을 등록하고 결과까지 확인했다. 즉 **우리가 맡긴 일과 AI가 실제로 한 일은 길이가 다르다.** 이 긴 과정을 이어주는 장치가 하네스다. 모델이 다음에 무엇을 할지 정하면 하네스가 필요한 도구를 실행하고 그 결과를 다시 모델에게 보여준다. 작업이 길어질 때는 처음 받은 요청과 지금까지 한 일도 계속 기억하게 해줘야 하는데, 이걸 놓치면 같은 페이지를 또 열거나 이미 끝낸 일을 반복하게 된다.

### [03:00–03:23] 엔비디아 GTC 타이페이에서도 나온 하네스 이야기
채널 동료 "에러 님"이 다녀온 엔비디아 GTC 타이페이에서도 젠슨 황이 모델을 둘러싼 하네스·도구·작업 환경을 언급한 바 있다(화자 인용). 엔비디아 발표 자료에도 **에이전트가 일을 나누고, 앞의 내용을 기억하고, 필요한 도구를 쓰려면 하네스가 꼭 필요하다**는 설명이 들어가 있다. 로컬 AI에 직접 도구를 붙이고 하네스까지 만드는 사람들은 이미 이 구조를 쓰고 있을 것이다.

### [03:23–03:40] 일반 사용자는 이미 준비된 하네스를 쓴다
다만 이 영상의 청자 대부분은 별도 시스템을 만들지 않고 **ChatGPT 워크 채팅창**에서 일을 맡기는 일반 사용자일 것이다. 서비스가 하네스를 준비해 뒀기 때문에 사용자는 자료와 목표를 주고, 중간에 필요한 승인을 한 뒤, 결과를 확인하면 된다.

### [03:40–04:22] 토큰이 빠르게 줄어드는 이유 — 화면이 바뀔 때마다 모델이 움직인다
요가 일정 등록을 예로 보면, AI가 예약 메일을 읽을 때 한 번, 캘린더 화면을 보고 입력란을 찾을 때 한 번, 저장 뒤 결과를 확인할 때 또 한 번 모델이 움직인다. 저장 버튼을 잘못 눌렀다면 바뀐 화면을 다시 읽고 오류 원인을 생각한 뒤 재시도한다. **컴퓨터 유즈에서 클릭 한 번마다 일정한 수의 토큰이 빠지는 게 아니라, 화면에 담긴 정보량과 AI가 몇 번 판단하는지에 따라 달라진다.** 화면이 바뀔 때마다 새 화면 정보가 들어오고, 모델은 처음 요청과 지금까지 한 일을 함께 읽으며 다음 행동을 정한다. 마지막 답변이 "등록했습니다" 한 줄이어도 그 앞에서는 여러 번 읽고 생각한 것이다.

### [04:22–04:59] 코딩·글쓰기도 구조는 같다
"이 오류를 고쳐 줘"라고 요청하면 에이전트는 먼저 폴더를 열어 어떤 파일이 있는지 확인하고, 관련 코드를 검색하고, 파일을 읽고, 고친 코드를 쓴 뒤 터미널에서 테스트를 돌린다. 테스트가 실패하면 긴 오류 메시지가 다시 모델에게 들어가고, 모델은 코드를 다시 읽은 뒤 또 수정한다. **화면에는 수정된 코드 몇 줄만 남아도 그 전에 읽은 파일·명령어 결과·테스트 기록까지 모두 작업에 쓰인 것**이며, 파일을 읽고 코드를 만들고 터미널 결과를 다시 읽고 실패 원인을 찾는 데서 토큰이 계속 들어간다.

### [04:59–05:34] 멀티 에이전트 — 시간은 줄지만 총 토큰은 늘 수 있다
여러 에이전트가 따로 움직이면 작업 과정 자체가 여러 갈래로 늘어난다. 한 에이전트는 자료를 찾고, 다른 에이전트는 코드를 확인하고, 또 다른 에이전트는 결과를 검사할 수 있다. 각 에이전트는 자기가 맡은 요청과 필요한 자료를 **따로따로** 읽고, 마지막에 중심 에이전트가 그 결과들을 다시 읽어 하나로 합친다. 창 세 개가 동시에 움직이면 기다리는 시간은 줄지만 각 에이전트가 읽고 쓴 양을 합친 전체 토큰은 늘어날 수 있다.

> "직원 세 명에게 같은 업무 설명을 나눠 주면 설명서도 세 번 읽는 거랑 비슷한 거예요." [05:27]

### [05:34–05:53] 줄일 수 있는 낭비
필요한 작업도 있지만 줄일 수 있는 낭비도 있다. 버튼을 잘못 눌러 같은 화면을 여러 번 보거나, 작은 수정에 불필요한 확인 작업을 붙이면 토큰이 더 들어간다. **일을 너무 잘게 나눠 에이전트 여러 개에게 보내면 일을 나누고 다시 합치는 데도 추가 사용량이 든다.**

### [05:53–06:17] ARC 프라이즈 사례 — 하네스만 바꿔도 점수↑ 비용↓
ARC 프라이즈가 공개한 아스트라 평가에서는 **같은 "높음" 설정을 써도 하네스를 바꾸니 점수가 올라가면서 비용이 절반 아래로 내려간 사례**가 있다(인용, 미검증). 앞에서 생각하던 내용을 잘 이어주고 긴 대화에서 덜 헤매게 만든 결과였다. 화자 유보 — 이건 퍼즐을 푸는 평가라서 일반 회사 업무에 똑같이 적용된다고 볼 수는 없지만, **모델만큼이나 일을 굴리는 방식도 중요하다**는 걸 보여준다.

### [06:17–06:53] 오픈AI 내부 사용 후기 — 제품 출시 홍보 업무 전체를 한 덩어리로
오픈AI의 린지 매캘럼 레미(자막 음차 "린지 매클럼 레미")는 제품 출시를 준비하며 AI가 **기자 명단을 관리하고, 브리핑 참석 여부를 확인하고, 나온 기사를 모아 보고서까지 만들었다**고 공개했다(오픈AI 내부 사용자 후기). 화자 평가 — 이건 글 한 편 써주는 일보다 손이 더 많이 가는 작업이다. 새 답장을 기존 명단에 반영하고, 이미 처리한 사람과 구분하고, 팀에서 쓰던 보고서 양식에 맞춰야 하기 때문이다. **사람에게 시켰다면 중간에 몇 번씩 "어디까지 했어요?"라고 물어봤을 일이 한 덩어리로 쭉 이어진 것**이다.

### [06:53–07:27] 공유된 다른 프롬프트 사례 — 출처 추적과 스프레드시트 웹앱화
아스트라 관련해 공유된 다른 프롬프트도 있다. 하나는 **인터넷에 퍼진 주장을 원래 출처까지 찾아가고, 사람마다 말이 다른 부분을 확인해 가이드로 만들어 달라**는 요청이다. 또 하나는 **스프레드시트를 검색·필터가 가능한 웹 앱으로 만들고, 계산 결과가 원본과 맞는지 확인해 달라**는 사례다. 직장인이라면 자료 조사와 보고서 작성, 학생이라면 발표 자료 준비에 쓸 수 있는 일이다. 흐름은 **필요한 파일과 앱 접근 권한을 준 뒤 채팅창에서 부탁하고, 마지막에 나온 계산이 맞는지만 사람이 확인**하는 것.

### [07:27–08:06] 개인정보 삭제 요청 자동화 사례와 안전한 프롬프트 형태
인터넷에 공개된 개인 정보를 찾아 삭제 요청을 맡기는 방법도 퍼지고 있다. 필리페 플로레스는 ChatGPT 에이전트로 자신에 관한 정보를 찾고 사이트마다 삭제 요청서를 작성해 절차를 진행했다고 공개했다. 화자 유보 두 가지 — **아스트라 출시 전 사례라 GPT6에서만 처음 가능해진 일이 아니고, 인터넷에 있던 정보가 모두 지워졌다고 따로 확인된 사례도 아니다.** 그래도 시도한다면 채팅창에서 이렇게 부탁할 수 있다.

> "내 정보가 나온 이 페이지의 공식 삭제 방법을 찾아줘. 요청서도 작성하되, 보내기 전에는 어디로 어떤 내용을 보낼지 나한테 먼저 보여 줘." [07:57]

### [08:06–08:38] 삭제 요청의 실제 절차와 확인 포인트
그렇게 하면 AI는 사이트의 삭제 안내를 찾고 필요한 요청서를 준비한다. 다만 **본인 인증이나 최종 제출 같은 민감한 단계에서는 사용자가 직접 참여해야 할 수 있고**, 보낸 뒤에는 실제로 정보가 지워졌는지 확인해야 한다. 특히 **구글 검색 결과에서 사라졌다고 원래 사이트의 정보까지 지워진 건 아니므로 두 곳을 따로 확인**해야 한다. 사이트마다 메뉴와 신청서가 다르므로 컴퓨터 유즈의 성능이 결과에 영향을 준다 — 삭제 메뉴를 찾아 들어가고, 양식을 채우고, 제출하고, 추가 인증 안내가 나오면 아직 끝나지 않았다는 걸 알아야 한다.

3. 어려운 판단이 끝나면 **다시 솔의 "중간"으로 내려** 확정된 내용을 보고서에 넣게 한다.

주의점 — 채팅창에 "솔로 해 줘", "아스트라로 해 줘"라고 적는 게 아니라 **메시지를 보내기 전에 모델 선택 메뉴에서 직접 바꿔야 한다.** 반대로 업무 순서를 잘 모르겠다면 아스트라를 앞에 잠깐 써서 **처리 기준을 먼저 만들게 한 뒤 나머지 정리 작업을 솔로 넘기는** 방식도 가능하다.

### [10:05–11:06] 추론 강도는 모델과 별개 설정 — 중간/높음/매우 높음/최대
모델과 추론 강도는 서로 다른 설정이다. 모델을 고른 다음 **중간, 높음, 매우 높음, 최대** 중에서 얼마나 오래 생각하게 할지 고를 수 있으며, 계정이나 선택한 모델에 따라 화면에 보이는 항목은 달라질 수 있다. 화자의 용도 가이드는 이렇다.

- **중간**: 회의록에서 담당자·날짜를 뽑거나 정해진 양식에 자료를 넣는 일
- **높음**: 여러 자료를 맞춰보고 조건을 확인할 때
- **매우 높음**: 숫자가 서로 안 맞거나 예외가 많아 원인을 오래 찾아야 할 때
- **최대**: 앞선 설정들로 풀지 못한 어려운 문제

중요한 반전 — **항상 낮게 설정한다고 토큰이 절약되는 건 아니다.** 낮은 설정에서 같은 실수를 세 번 하고 고치는 것보다 높은 설정에서 한 번에 끝내는 편이 토큰이 적게 들 수 있다. 현실적인 방식은 **익숙한 일은 중간에서 시작하고 막힌 부분만 높이는 것**.
