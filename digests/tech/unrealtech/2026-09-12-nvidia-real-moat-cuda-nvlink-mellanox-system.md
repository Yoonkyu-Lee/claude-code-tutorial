## 요약 (주제별)

### 1. 영상의 질문과 프레임
- 반도체 인문학[불명확: 자막 원문 "침문학"/"측문학"] 시리즈 3편. 1편은 GPU가 AI 시대의 왕이 된 이유, 2편은 HBM 병목을 다뤘고, 이번 편은 "GPU 한 장 → 서버 → 랙 → 데이터센터"로 범위를 넓힌다.
- 중심 질문: 엔비디아의 진짜 해자는 GPU인가, GPU들이 실제로 일하게 만드는 시스템인가. 전 구간을 관통하는 점검 질문은 "GPU는 지금 무엇을 기다리고 있는가".
- 출발점이 된 관찰: 게임용 그래픽 카드 회사가 지금은 CPU·네트워크 카드·스위치를 만들고 서버와 랙까지 설계한다. 2019년 멜라녹스 인수 발표(약 69억 달러), 2020년 거래 완료.

### 2. GPU의 병렬 구조와 그 한계 (계산 능력 ≠ 활용 가능성)
- 풀HD 한 장이 200만 개 넘는 픽셀, 60fps면 초당 60장, 120fps면 120장을 다시 계산 → 그래픽 칩은 "복잡한 일 하나를 빠르게"가 아니라 "비슷한 계산을 많은 연산기가 나눠서"로 발전.
- 비유: CPU는 순서가 복잡하고 예외가 많은 일을 처리하는 소수 정예, GPU는 같은 종류의 일을 대량 처리하는 계산 공장.
- AI 신경망도 비슷한 곱셈·덧셈의 대량 반복이라 성질이 닮았지만, 병렬 연산을 잘한다는 사실만으로 바로 AI에 쓸 수는 없었다. 초기 GPU는 화면 그리는 장치였고, 연구자는 숫자를 색·위치 정보로 위장해 그래픽 명령으로 처리해야 했다 — "계산기는 가득했지만 작업 지시 체계가 없었다".

### 3. CUDA — 플랫폼 레이어
- 스탠퍼드에서 GPU 범용 계산을 연구하던 이안 벅 팀의 Brook 프로그래밍 모델이 출발점. 엔비디아는 2004년 이안 벅을 영입했고, 그 흐름이 C/C++에 가까운 방식으로 GPU에 계산을 전달하는 CUDA로 이어졌다.
- CUDA가 GPU를 병렬 프로세서로 만든 게 아니라, 이미 있던 병렬 능력을 그래픽 밖에서 꺼내 쓰게 한 플랫폼. 이후 CUDA가 활용 범위를 넓히고 → 넓어진 범위가 다시 GPU 명령 구조·메모리·연산기·개발 도구 설계를 바꾸는 공진화가 일어났다.
- CUDA는 언어 하나가 아니라 컴파일러·디버거·성능 분석 도구 + 최적화 라이브러리 스택. 같은 행렬 곱도 데이터 분할, 메모리 접근 순서, 연산기 공급 밀도에 따라 속도가 크게 달라지므로 라이브러리가 결정적이었다(cuDNN 등).
- PyTorch·TensorFlow가 이 라이브러리를 쓰면서 개발자는 CUDA 코드를 직접 안 써도 엔비디아 GPU를 쓰게 됐다 → CUDA는 화면에서 안 보이게 됐지만 AI 개발 환경 아래로 더 깊이 들어갔다.
- 2012년 AlexNet은 GeForce GTX 580 두 장으로 학습돼 ImageNet에서 큰 성능 차이를 냈다. 다만 "엔비디아가 그때부터 생성형 AI 시대를 다 내다봤다"는 말은 과장일 수 있다고 화자 스스로 유보([의견]) — 확실한 건 연구 폭발 시점에 병렬 하드웨어와 CUDA를 이미 함께 갖췄다는 것.

### 4. 여러 GPU로 확장할 때 생기는 통신 문제
- 학습 시 GPU 메모리에는 모델 파일만이 아니라 입력 데이터·중간 결과·수정 방향 계산용 값이 들어가므로, 필요한 메모리는 모델 파일 크기보다 훨씬 커진다.
- GPU를 1천 장 쓰면 1천 배 빨라지지 않는다. 계산 능력은 늘지만 각자 계산한 결과를 서로 맞추는 일도 함께 늘기 때문. "GPU 한 장의 속도와 천 장의 속도는 전혀 다른 문제."
- 그레디언트(모델 수정 방향)는 GPU마다 조금씩 다르게 나오므로, 다음 단계 전에 합쳐 같은 모델을 유지해야 한다. 값을 합쳐 모두에게 동일한 결과를 돌려주는 연산이 All-Reduce(예: 네 GPU의 1·2·3·4를 합친 값을 전원이 다시 받음).
- 동기화 대기 비용: 먼저 끝낸 GPU도 남의 값이 안 오면 못 넘어간다. 작업자가 늘수록 한 명의 지연에 묶이는 인원도 늘어난다.
- 전원이 전원에게 직접 보내는 방식은 수백~수천 장에서 배선·복사가 폭증 → 링(옆 GPU로 순차 전달)과 트리(가지 따라 모았다 배포) 방식. 어느 쪽이 빠른지는 데이터 크기·GPU 수·서버 연결 구조에 따라 달라진다.
- NCCL = 여러 GPU가 값을 주고받는 순서를 관리하는 라이브러리. CUDA가 GPU 안의 연산기에 일을 나누는 체계라면 NCCL은 GPU 사이의 체계.

### 5. 물리적 통로 — NVLink / NVSwitch / 스케일업
- 일반 서버는 GPU·CPU·SSD·네트워크 카드를 PCI Express로 연결하지만, 대규모 학습의 GPU 간 대량·반복 교환에는 부족 → GPU 전용 고속 통로 NVLink.
- GPU 두 장 연결은 쉬워도 8장·수십 장을 전부 직접 연결하면 배선이 폭증 → 중간에서 경로를 정해 주는 교환 장치 NVSwitch("수많은 통로를 이어주는 환승 센터").
- 결과: GPU들이 각각 떨어진 그래픽 카드가 아니라 하나의 더 큰 계산 장치처럼 연결되기 시작. 이렇게 한 서버·한 랙 안에서 묶는 것이 스케일업.
- 스케일업의 물리적 한계: GPU가 늘수록 전력·냉각이 어려워지고 스위치·케이블 공간도 커져 한 랙에 무한히 넣을 수 없다.

### 6. 랙 밖 — 멜라녹스, InfiniBand, RDMA (스케일아웃)
- 여러 서버·랙을 하나의 클러스터로 묶는 것이 스케일아웃. 랙 안은 "가까운 GPU 간 초고대역폭", 랙 밖은 "먼 거리 수많은 서버를 낮은 지연으로 안정적으로" — 같은 네트워크처럼 보여도 푸는 문제가 다르다.
- 엔비디아는 랙 안(NVLink·NVSwitch)은 있었지만 케이블이 랙 밖으로 나가는 순간의 기술이 없었고, 그 자리를 InfiniBand·고성능 이더넷 어댑터/스위치를 가진 멜라녹스가 채웠다.
- 인수 해석([의견]): GPU가 빨라지고 수가 늘수록 서버 간 이동 시간의 비중이 커진다. 생성형 AI 폭발을 예언했다고 말할 수는 없지만, 당시에도 슈퍼컴퓨터·대규모 데이터 분석에서 "계산이 빨라질수록 네트워크가 성능을 제한한다"는 문제는 분명히 있었고 엔비디아는 다음 병목이 네트워크로 옮겨갈 가능성에 일찍 들어갔다.
- RDMA: 통상 경로는 CPU가 시스템 메모리로 복사 → 네트워크 카드 전송 지시 → 반대편에서 다시 CPU·시스템 메모리를 거쳐 GPU로, 중간 단계가 여러 번. 수천 장이 매 학습 단계마다 교환하면 이 복사와 CPU 개입이 누적된다. RDMA는 네트워크 장치가 상대 시스템 메모리와 직접 교환해 CPU 개입을 줄인다.
- GPUDirect RDMA는 그 경로를 GPU 메모리까지 연결한 것. 핵심 문장: "GPU를 더 빠르게 만든 것이 아니라, GPU가 계산하지 않는 시간을 줄인 것."

### 7. 모델 구조가 바뀌면 통신 패턴도 바뀐다 (MoE)
- MoE는 모델 안에 여러 전문가 신경망을 두고 입력마다 일부만 선택해 계산량을 줄이는 구조.
- 선택된 전문가가 서로 다른 GPU에 있으면 입력을 보내고 결과를 받아야 하므로, All-Reduce(합치기) 대신 서로 다른 데이터를 주고받는 All-to-All 통신이 늘어난다.
- 함의: 네트워크는 GPU를 연결하는 부속품이 아니라 모델의 실제 성능을 결정하는 계산 시스템의 일부다.

### 8. 시스템 통합 — DGX와 역할 지도
- 부품을 다 모아도 자동으로 빨라지지 않는다. CPU·메모리 선택, GPU·스위치 연결 순서, 전원·냉각, 드라이버/OS/CUDA/통신 라이브러리 조합 검증이 모두 필요. "좋은 부품을 갖는 것과 그 부품들이 안정적으로 함께 작동하는 건 또 다른 기술."
- 2016년 DGX-1: GPU 8장 + NVLink + CPU + 저장 장치 + 딥러닝 소프트웨어를 하나의 검증된 시스템으로 묶음. 의미는 "한 상자에 여러 장"이 아니라 "고객이 엔비디아가 정한 기준 시스템에서 시작하게 만든 것".
- 이후 GPU에 데이터를 공급하는 CPU, 네트워크·스토리지를 맡는 DPU, 서버 보드·랙 설계까지 범위 확장. 역할 지도: HBM = GPU 옆 데이터 공급 / NVLink·NVSwitch = 랙 안 GPU 묶기 / InfiniBand·고성능 이더넷 = 서버·랙 사이 이동 / CPU·DPU = 시스템 관리·주변 작업 / 소프트웨어 = 언제 어떤 데이터를 어느 경로로 처리할지 조율.
- 한 줄 결론: 엔비디아가 파는 것은 점점 GPU의 최고 연산량이 아니라 "그 연산량을 실제로 꺼내 쓰기 위한 조건 전체".

### 9. NVLink Fusion과 빅테크 자체 칩
- 구글·아마존·마이크로소프트가 자체 CPU·AI 가속기를 만들면서, 데이터센터의 모든 계산 칩이 엔비디아 제품으로 채워질 가능성은 높지 않아졌다.
- 대응 전략이 NVLink Fusion — 타사 설계 맞춤형 CPU·AI 가속기를 엔비디아의 NVLink 연결 기술과 랙 구조에 결합할 수 있게 한다. 여기서 XPU는 GPU만이 아니라 기업이 특정 목적에 맞게 만든 여러 가속기를 아우르는 표현.
- 시장 채택 폭은 파트너 제품·클라우드 도입을 확인해야 한다고 유보(미검증). 다만 의도는 분명하다는 해석([의견]): 칩을 남이 만들어도 "칩들이 연결되는 시스템의 규칙"에는 엔비디아 기술이 반드시 들어가게 하려는 것.
- 빅테크 자체 칩(구글 TPU, 아마존 트레이니엄, MS 마이아, 메타 자체 가속기)은 CUDA·GPU를 복제하려는 게 아니라, 자사 데이터센터에서 반복되는 특정 작업에 맞춰 불필요한 기능을 덜어내고 비용·전력 효율을 높인 전용 칩이라는 해석([의견]).

### 10. 리스크·비용 관점 (통합의 반대편)
- 검증된 조합 덕에 빠른 구축이 가능하지만 한 회사 의존도도 커진다. CUDA·엔비디아 라이브러리에 맞춘 코드를 다른 가속기로 옮기려면 수정·검증이 필요하고, 네트워크·서버 관리 도구까지 썼다면 교체 범위가 더 넓어진다.
- 가격은 GPU 한 장이 아니라 스위치·네트워크 카드·서버·전력·냉각·소프트웨어 운영비까지 포함해 봐야 한다.
- 가동률이 관건: 비싼 시스템이라도 GPU가 높은 비율로 계속 계산하면 작업당 비용은 낮아지고, 반대로 활용을 못 하면 비싼 GPU가 데이터를 기다리며 논다.
- 따라서 모든 AI 작업에 가장 크고 복잡한 엔비디아 시스템이 필요한 건 아니며, 작업이 반복되고 모델 구조가 충분히 고정돼 있으면 전용 칩이 더 낮은 비용·전력으로 처리할 수도 있다(조건부 판단).

### 11. 결론과 다음 편 예고
- "GPU냐 시스템이냐"를 양자택일로 보면 답을 놓친다. 강한 GPU가 없었으면 CUDA 생태계·연결 기술도 지금의 가치를 못 가졌겠지만, 좋은 GPU 한 장만으로 수천 장 학습을 굴릴 수도 없다.
- 구조의 핵심은 GPU가 계산하는 시간을 늘리고 메모리·다른 GPU·CPU·네트워크를 기다리는 시간을 줄이는 것. "강한 GPU를 중심으로 소프트웨어·메모리·통신·네트워크·서버 설계가 서로의 가치를 더 높이도록 만든 구조"가 시스템 해자에 더 가까운 설명이다.
- 다음 편 예고: GPU와 ASIC[불명확: 자막 원문 "AD 회로"]의 회로 구조·비용 차이, 구글 TPU와 빅테크 자체 칩이 어떤 조건에서 유리해지는가. 남겨 둔 질문은 "자체 칩이 엔비디아를 완전 대체하려는 것인가, 비용 큰 일부 작업만 가져오려는 것인가".

## 3줄 오리엔테이션
- 엔비디아의 경쟁력을 "GPU 한 장의 연산량"이 아니라 "GPU가 실제로 계산하게 만드는 조건 전체"로 보는 관점을 세운다.
- GPU 한 장 → CUDA → 여러 GPU 통신(All-Reduce·NCCL) → NVLink/NVSwitch(스케일업) → InfiniBand/Mellanox(스케일아웃) → DGX·랙 설계로 범위를 한 단계씩 넓히며, 각 단계마다 "GPU는 지금 무엇을 기다리는가"를 반복해 묻는다.
- 결론은 GPU냐 시스템이냐의 양자택일이 아니라 "강한 GPU를 중심으로 소프트웨어·메모리·통신·서버 설계가 서로의 가치를 올리는 구조"이며, 그 완성도에도 불구하고 빅테크가 자체 칩을 만드는 이유는 다음 편 주제로 넘긴다.

## 전문 — 시간순 워크스루

### [00:00–00:25] 시리즈 3편 오프닝 — 2편(HBM) 복습
진행자 "패치"가 반도체 인문학[불명확: 자막 원문 "침문학"/"측문학"] 시리즈 3편으로 인사한다. 지난 2편에서는 AI 칩 바로 옆에 붙는 HBM이 왜 뜨거운 병목이 되는지를 다뤘다. 요지는 GPU가 아무리 빠르게 계산해도 필요한 데이터를 제때 받지 못하면 수많은 연산기가 멈춰서 기다리기 때문에, AI 성능이 GPU 내부 계산 능력만으로 결정되지 않는다는 것이었다.

### [00:25–00:56] 이상한 점 — 그래픽 카드 회사가 왜 네트워크 회사를 샀나
엔비디아를 조금 넓게 보면 이상한 점이 하나 보인다. 원래 게임용 그래픽 카드를 만들던 회사가 지금은 CPU와 네트워크 카드, 스위치를 만들고 서버와 랙 전체까지 설계한다. 2019년에는 고성능 네트워크 회사인 멜라녹스(Mellanox)를 약 69억 달러에 인수하겠다고 발표했고, 이 거래는 2020년에 완료됐다.

> "엔비디아의 진짜 해자는 GPU일까요? 아니면 GPU들이 실제로 일하게 만드는 시스템일까요?" [00:50]

### [00:56–01:09] 이 영상의 접근 방식
이 질문에 답하려면 GPU 한 장에서 출발해 서버와 랙, 데이터센터까지 범위를 넓혀 가야 한다. 그 과정에서 계속 확인할 질문은 하나로 고정된다 — "GPU는 지금 무엇을 기다리고 있는가?"

### [01:09–02:03] GPU가 그래픽에서 병렬로 발전한 이유
모니터에서 화면 하나를 본다는 건 디스플레이를 이루는 수많은 점에 어떤 색과 밝기를 표시할지 계속 계산한다는 뜻이다. 풀HD 한 장만 해도 200만 개가 넘는 픽셀이 있고, 게임에서는 캐릭터가 움직이거나 카메라·조명이 바뀔 때마다 이 픽셀들의 색을 다시 계산해야 한다. 1초에 60번 보여 준다면 60장을, 120프레임이면 120번 이 과정을 반복해야 한다. 픽셀 하나의 계산은 아주 복잡하지 않을 수 있지만 비슷한 계산을 엄청나게 많은 점에 적용해야 하므로, 그래픽 칩은 복잡한 일 하나를 빠르게 끝내기보다 많은 연산기가 비슷한 계산을 나눠 맡는 방향으로 발전했다.

> "CPU가 순서가 복잡하고 예외가 많은 일을 처리하는 소수 정예라면, GPU는 같은 종류의 일을 대량으로 처리하는 계산 공장에 가까운 거죠." [01:54, 자막 원문에서 앞쪽 'GPU'는 문맥상 CPU의 오인식]

### [02:03–02:22] AI 신경망과 닮은 점, 그러나 바로 쓸 수 있었나
AI 신경망도 수많은 숫자의 비슷한 곱셈과 덧셈을 반복한다. 그래픽의 픽셀 계산과 AI 학습이 같은 작업은 아니지만, 많은 데이터를 비슷한 방식으로 동시에 처리할수록 유리하다는 점은 닮아 있었다. 그렇다고 GPU가 병렬 연산을 잘한다는 사실을 안 것만으로 곧바로 AI에 쓸 수 있었던 것은 아니다.

### [02:22–02:48] 초기 GPU의 진짜 한계 — 작업 지시 체계의 부재
GPU 안에 수많은 연산기가 있다는 것과, 연구자가 그 연산기들에게 자신이 원하는 일을 시킬 수 있다는 것은 다른 문제였다. 초기 GPU는 화면을 그리는 장치였기 때문에, 과학 계산을 하려는 연구자도 숫자를 색이나 위치 정보처럼 바꾼 뒤 그래픽 명령으로 처리하고 그 결과를 다시 꺼내야 했다. 계산기는 가득했지만 그래픽이 아닌 계산을 편하게 전달할 작업 지시 체계가 없었던 셈이다.

### [02:48–03:11] CUDA의 등장 — 이안 벅과 Brook
여기서 등장한 것이 CUDA다. 스탠퍼드 대학교에서 GPU 범용 계산을 연구하던 이안 벅(Ian Buck) 팀은 Brook이라는 프로그래밍 모델을 개발했고, 엔비디아는 이안 벅을 2004년에 영입했다. 이 연구의 흐름은 개발자가 과학 계산을 그래픽 작업처럼 위장하지 않고도 C/C++에 가까운 방식으로 GPU에 전달할 수 있게 한 CUDA로 이어진다.

### [03:11–03:56] CUDA와 GPU의 공진화
CUDA가 GPU를 병렬 프로세서로 만든 것은 아니다. GPU는 이미 수많은 픽셀을 계산하기 위해 병렬 구조로 발전하고 있었고, CUDA는 다만 그 능력을 그래픽 밖에서도 꺼내 쓸 수 있게 만든 플랫폼이다. 이후 엔비디아는 CUDA 프로그램이 더 잘 실행되도록 GPU의 명령 구조와 메모리, 연산기, 개발 도구를 함께 발전시키기 시작했다. 즉 CUDA가 GPU의 활용 범위를 넓혔고, 넓어진 활용 범위가 다시 GPU의 설계를 바꿨다. CUDA·GPU 구조·텐서 코어·CPU와 GPU의 차이가 낯설게 느껴진다면 시리즈 1편 "GPU는 왜 AI 시대에 왕이 됐을까"를 참고하라고 안내하고, 이번 편은 그 기반 위에서 GPU 한 장이 여러 장의 시스템으로 확장되는 과정에 집중하겠다고 정리한다.

### [03:56–04:36] CUDA는 언어 하나가 아니라 스택이다
CUDA는 단순한 프로그래밍 언어가 아니다. 개발자의 코드를 GPU가 실행할 수 있게 바꾸는 컴파일러, 오류를 찾는 디버거, 성능 분석 도구가 있고, 그 위에 자주 쓰는 계산을 미리 최적화한 라이브러리가 올라간다. AI에서는 이 라이브러리가 특히 중요했는데, 같은 행렬 곱이라도 데이터를 어떻게 나누고 어느 순서로 메모리를 꺼내며 연산기에 얼마나 빈틈없이 공급하느냐에 따라 속도가 크게 달라지기 때문이다. 그래서 엔비디아는 신경망 연산을 최적화한 cuDNN 같은 라이브러리를 만들었고, 이후 PyTorch와 TensorFlow 같은 프레임워크가 이 라이브러리를 사용하면서 개발자는 CUDA 코드를 직접 쓰지 않고도 엔비디아 GPU를 활용할 수 있게 됐다.

### [04:36–05:19] 보이지 않게 더 깊어진 CUDA, 그리고 AlexNet
개발자가 PyTorch에서 모델을 만들면 그 아래에서 프레임워크와 라이브러리, CUDA와 GPU가 함께 움직인다. CUDA는 개발자 화면에서 잘 보이지 않게 됐지만 AI 개발 환경 아래로 더 깊이 들어간 것이다. 2012년 AlexNet은 GeForce GTX 580 두 장으로 학습돼 ImageNet에서 큰 성능 차이를 만들었다.

> "엔비디아가 이때부터 벌써 지금의 생성형 AI 시대를 모두 내다봤다고 하면 조금 과장일 수도 있겠지만, AI 연구가 폭발하기 시작했을 때 이미 병렬 연산 하드웨어와 연구자가 그 하드웨어를 사용할 CUDA를 함께 갖추고 있었습니다." [04:58] — [의견] 선견지명 주장은 과장일 수 있다고 화자 스스로 유보를 달아 둔 대목
그래서 새로운 AI 연구가 등장했을 때 GPU는 단순히 계산을 잘하는 칩이 아니라 이미 연구자가 쓸 수 있는 계산 플랫폼이었다.

### [05:19–05:58] 다음 문제 — 모델이 GPU 한 장을 넘어서다
여기까지는 1편에서도 다룬 이야기이고, 그다음부터 엔비디아에는 완전히 다른 문제가 생긴다. 모델이 GPU 한 장을 넘어섰기 때문이다. AI 모델을 학습할 때 GPU 메모리에 들어가는 건 모델 파일만이 아니라 입력 데이터와 계산 도중 만들어지는 중간 결과가 저장되고, 모델의 숫자를 어느 방향으로 고칠지 계산하기 위한 값들도 필요하다. 그래서 학습에 필요한 메모리는 모델 파일 크기보다 훨씬 커질 수 있다. 이 부분(왜 그렇게 많은 메모리가 필요하고 데이터를 기다리는 시간이 왜 성능을 제한하는지)은 2편 "HBM은 왜 AI보다 더 뜨거운 병목이 됐을까"를 다시 보고 오라고 안내한다.

### [05:58–06:34] 여러 GPU로 확장 — GPU 1천 장이면 1천 배 빨라지나
이번 편에서는 메모리 문제를 넘어 모델이 여러 GPU로 확장됐을 때 생기는 통신 문제에 집중한다. GPU 한 장에 들어가지 않으면 모델을 여러 GPU에 나누거나, 같은 모델을 여러 GPU에 복사하고 학습 데이터를 나눠 처리해야 한다. 그렇다면 GPU를 1천 장 쓰면 학습도 정확히 1천 배 빨라질까? 실제로는 그렇지 않다. GPU가 많아질수록 계산 능력은 늘지만 각 GPU가 혼자 계산한 결과를 다시 서로 맞춰 봐야 하는 일도 함께 늘어나기 때문이다.

> "GPU 한 장의 속도와 GPU 천 장의 속도는 전혀 다른 문제입니다." [06:30]

### [06:34–07:18] 그레디언트와 All-Reduce
AI 학습은 모델이 낸 답과 정답의 차이를 보고 모델 내부의 수많은 숫자를 어느 방향으로 얼마나 고칠지 계산하는 과정이고, 이 수정 방향을 그레디언트(gradient)라고 한다. 여러 GPU가 서로 다른 학습 데이터를 처리하면 각자 조금씩 다른 그레디언트를 계산하는데, GPU마다 자기 값만 쓰면 서로 다른 모델로 갈라지므로 다음 학습 단계로 넘어가기 전에 각자의 계산 결과를 합쳐 같은 모델을 유지해야 한다. 여러 GPU의 값을 합친 뒤 동일한 결과를 다시 모두에게 전달하는 연산이 All-Reduce다. 예를 들어 GPU 네 장이 각각 1, 2, 3, 4를 계산했다면 네 값을 합친 결과를 모든 GPU가 다시 받아가는 방식이다.

### [07:18–07:58] 동기화 대기, 그리고 링·트리 통신
한 GPU가 먼저 계산을 끝냈더라도 다른 GPU의 값이 도착하지 않으면 다음 단계로 넘어갈 수 없다. GPU 수가 많아질수록 함께 일하는 작업자는 늘지만, 한 명이 늦어졌을 때 기다려야 할 작업자도 많아진다. 그렇다고 모든 GPU가 다른 모든 GPU에게 직접 데이터를 보내면 되느냐 하면, 몇 장일 때는 가능해도 수백~수천 장으로 늘면 연결과 데이터 복사가 지나치게 복잡해진다. 그래서 데이터를 작은 조각으로 나눠 옆 GPU로 순차 전달하는 링(ring) 방식이나, 여러 단계의 가지를 따라 모으고 다시 배포하는 트리(tree) 방식을 쓰게 되며, 어느 쪽이 빠른지는 데이터 크기와 GPU 수, 서버의 연결 구조에 따라 달라진다.

### [07:58–08:20] NCCL — 통신 순서를 관리하는 체계
이런 여러 GPU 통신을 처리하는 엔비디아의 라이브러리가 NCCL이다. CUDA가 GPU 안의 수많은 연산기에게 일을 나누는 체계라면, NCCL은 여러 GPU가 서로 값을 주고받는 순서를 관리하는 체계다. 그런데 통신 순서를 아무리 잘 짜도 데이터가 지나갈 물리적 통로가 좁으면 속도는 나오지 않는다. 이제 문제는 GPU "안"에서 GPU "사이"로 옮겨 간다.

### [08:20–08:44] PCI Express의 한계와 NVLink
일반적인 서버에서는 GPU와 CPU, SSD, 네트워크 카드가 PCI Express라는 통로로 연결된다. 여러 종류의 장치를 연결할 수 있는 범용 규격이지만, 대규모 AI 학습에서는 GPU들이 서로 대량의 데이터를 반복 교환해야 한다. 그래서 엔비디아는 GPU 사이의 전용 고속 통로인 NVLink를 개발했다.

### [08:44–09:19] NVSwitch — 통로를 이어주는 환승 센터
GPU 수가 늘면 또 다른 문제가 생긴다. GPU 두 장을 연결하는 건 어렵지 않지만 여덟 장, 수십 장의 GPU를 모두 서로 직접 연결하려면 선의 수와 배선이 지나치게 복잡해진다. 그래서 중간에서 어느 GPU의 데이터를 어디로 보낼지 연결하는 교환 장치가 들어가는데 이것이 NVSwitch다. NVLink가 GPU 사이의 고속 통로라면 NVSwitch는 수많은 통로를 이어주는 환승 센터다.

> "중요한 점은 GPU들이 더 이상 각각 떨어진 그래픽 카드가 아니라 하나의 더 큰 계산 장치처럼 연결되기 시작했다는 거예요." [09:10]

### [09:19–09:47] 스케일업과 스케일아웃
한 서버나 한 랙 안에 GPU를 매우 빠르게 묶어 더 큰 계산 장치처럼 만드는 것을 스케일업(scale-up)이라고 한다. 그런데 GPU가 늘수록 전력 공급과 냉각이 어려워지고 스위치·케이블이 차지하는 공간도 커지므로 한 랙에 GPU를 무한히 넣을 수는 없다. 더 큰 모델을 위해서는 결국 여러 서버와 랙을 다시 연결해야 하고, 이렇게 랙 밖으로 범위를 넓혀 많은 서버를 하나의 클러스터로 묶는 것을 스케일아웃(scale-out)이라고 한다.

### [09:47–10:15] 두 문제는 성격이 다르다 — 그리고 멜라녹스
두 기술은 같은 네트워크처럼 보여도 푸는 문제가 다르다. 랙 안에서는 가까이 있는 GPU들이 매우 높은 대역폭으로 촘촘하게 값을 교환해야 하고, 랙 밖에서는 더 먼 거리의 수많은 서버를 낮은 지연 시간으로 안정적으로 연결해야 한다. 엔비디아는 랙 안에서는 NVLink와 NVSwitch를 갖고 있었지만, 케이블이 랙 밖으로 나가는 순간 GPU 회사만으로는 해결하기 어려운 기술이 필요했다. 여기서 멜라녹스가 등장한다.

### [10:15–10:56] 멜라녹스 인수를 다시 읽기
멜라녹스는 InfiniBand와 고성능 이더넷 네트워크 어댑터·스위치 기술을 갖고 있던 회사다. 인수 당시에는 단순히 사업 영역을 넓힌 것으로 볼 수도 있었지만, AI 클러스터의 구조를 따라가다 보면 인수의 이유가 다르게 보인다는 것이 화자의 해석이다([의견]). GPU가 빨라지고 GPU 수가 늘수록 데이터가 서버 사이를 이동하는 시간이 전체 성능에서 더 큰 비중을 차지하기 때문이다. 엔비디아가 생성형 AI 폭발을 정확히 예언했다고 말할 수는 없지만, 당시에도 슈퍼컴퓨터와 대규모 데이터 분석에서 계산 장치가 빨라질수록 네트워크가 성능을 제한한다는 문제는 분명히 있었고, 엔비디아는 GPU의 다음 병목이 네트워크로 이동할 가능성에 일찍 들어간 셈이다.

### [10:56–11:38] InfiniBand는 그냥 빠른 랜선인가 — RDMA
InfiniBand가 단순히 인터넷선을 더 빠르게 만든 것이냐 하면, 데이터가 이동하는 방식 자체에 차이가 있다. 일반적인 데이터 이동에서는 CPU가 데이터를 시스템 메모리로 복사하고 네트워크 카드에 전송을 지시하며, 반대편에서도 들어온 데이터가 CPU와 시스템 메모리를 거쳐 GPU로 옮겨지기 때문에 GPU끼리 한 번 데이터를 교환하는 데 중간 단계가 여러 번 생긴다. 규모가 작을 때는 감당할 수 있지만 GPU 수천 장이 학습 단계마다 값을 교환하면 이 복사와 CPU 개입도 쌓인다. 그래서 네트워크 장치가 상대 시스템의 메모리와 직접 데이터를 교환해 CPU 개입을 줄이는 기술을 쓰는데, 이것이 RDMA다.

### [11:38–11:56] GPUDirect RDMA — 빨라진 게 아니라 안 기다리게 된 것
엔비디아는 이 경로를 GPU 메모리까지 연결한 GPUDirect RDMA를 제공한다. GPU가 계산을 끝냈는데 CPU가 데이터를 옮겨 줄 때까지 기다리는 구간을 줄이는 기술이다.

> "그러니까 GPU를 더 빠르게 만든 것이 아니라, GPU가 계산을 하지 않는 시간을 줄인 겁니다." [11:51]

### [11:56–12:40] MoE 모델과 All-to-All 통신
최근 MoE(Mixture of Experts) 모델에서는 통신 방식이 더 복잡해진다. MoE는 모델 안에 여러 전문가 역할의 신경망을 두고 입력마다 필요한 일부 전문가만 선택해 쓰는 구조로, 계산량을 줄일 수 있다는 장점이 있다. 하지만 선택된 전문가들이 서로 다른 GPU에 있다면 입력을 해당 GPU로 보내고 결과를 다시 받아야 한다. 앞의 All-Reduce가 여러 GPU의 값을 하나로 합치는 통신이었다면, 여기서는 여러 GPU가 서로 다른 데이터를 주고받는 All-to-All 통신이 늘어난다. AI 모델의 구조가 바뀌면 GPU 안의 계산뿐 아니라 데이터가 어느 GPU에서 어느 GPU로 이동하는지도 함께 달라진다.

> "네트워크는 GPU를 연결하는 부속품이 아니라 모델의 실제 성능을 결정하는 계산 시스템의 일부가 돼 버리는 거죠." [12:34]

### [12:40–13:16] 부품을 다 모았다고 시스템이 빨라지지는 않는다
여기까지 오면 엔비디아에는 GPU와 CUDA, GPU 사이의 연결, 서버 사이의 네트워크가 모두 생겼다. 그러면 이 부품들을 고객이 알아서 조립하면 끝일까? 그렇지 않다. 어떤 CPU와 메모리를 쓸지, GPU와 스위치를 어떤 순서로 연결할지 결정해야 하고, 전원과 냉각도 맞춰야 하며, 드라이버와 운영체제, CUDA와 통신 라이브러리 조합도 검증해야 한다.

> "좋은 부품을 갖는 것과 그 부품들이 안정적으로 함께 작동하는 건 또 다른 기술입니다." [13:10]

### [13:16–13:44] DGX-1과 "기준 시스템"의 의미
여기서 등장한 제품이 DGX다. 엔비디아는 2016년 DGX-1을 공개하면서 GPU 여덟 장과 NVLink, CPU와 저장 장치, 딥러닝 소프트웨어를 하나의 검증된 시스템으로 묶었다. DGX의 의미는 그래픽 카드 여러 장을 한 상자에 넣었다는 데 있는 것이 아니라, 고객이 여러 회사의 부품을 직접 조합하고 성능이 안 나오는 이유를 하나씩 찾는 대신 엔비디아가 정한 기준 시스템에서 시작하도록 만들었다는 데 있다.

### [13:44–14:36] 역할 지도 — 제품명이 아니라 기능으로 보기
엔비디아는 이후 GPU에 데이터를 공급하는 CPU, 네트워크·스토리지 작업을 맡는 DPU, 그리고 서버 보드와 랙 설계까지 범위를 넓혔다. 화자는 제품명을 외울 필요 없이 역할로 연결해 보라고 정리한다. HBM은 GPU 바로 옆에서 데이터를 공급하고, NVLink와 NVSwitch는 랙 안의 GPU들을 묶고, InfiniBand와 고성능 이더넷은 서버·랙 사이로 데이터를 옮기며, CPU와 DPU는 시스템 관리와 네트워크·저장 장치 같은 주변 작업을 나눠 맡고, 소프트웨어는 이 하드웨어들이 언제 어떤 데이터를 어느 경로로 처리할지 조율한다.

> "이 모든 기술이 향하는 목표는 GPU가 메모리와 다른 GPU, CPU의 복사와 네트워크를 기다리는 시간을 줄이는 겁니다. 엔비디아가 판매하는 것은 점점 GPU의 최고 연산량만이 아니라, 그 연산량을 실제로 꺼내 쓰기 위한 조건 전체가 됐습니다." [14:21]

### [14:36–15:06] 통합이 깊어질수록 생기는 고민 — NVLink Fusion
시스템을 깊게 통합할수록 엔비디아에도 새로운 고민이 생긴다. 구글·아마존·마이크로소프트 같은 대형 고객들이 자체 CPU와 AI 가속기를 만들기 시작했기 때문이다. 이 회사들이 데이터센터의 모든 계산 칩을 엔비디아 제품으로 채울 가능성은 높지 않다. 엔비디아는 여기에 다른 회사가 설계한 맞춤형 CPU와 AI 가속기를 자사의 NVLink 연결 기술과 랙 구조에 결합할 수 있게 하는 NVLink Fusion 전략을 내놓았다. 여기서 XPU는 GPU만을 뜻하지 않고, 기업이 특정 목적에 맞게 만든 여러 종류의 가속기를 넓게 아우르는 표현이다.

### [15:06–15:31] 이 전략이 지키려는 것
이 전략이 실제 시장에서 얼마나 널리 채택될지는 파트너 제품과 클라우드 도입을 확인해야 한다고 유보를 단다(미검증). 다만 엔비디아가 무엇을 지키려는지는 분명하다는 것이 화자의 해석이다([의견]) — 칩을 다른 회사가 만들었더라도 그 칩들이 연결되는 시스템의 규칙에는 반드시 엔비디아 기술이 들어가게 하려는 것이다.

### [15:31–16:00] 통합의 반대편 — 종속과 총비용
통합된 시스템에는 반대편도 있다. 하드웨어·소프트웨어 조합이 검증돼 있어 시스템을 빠르게 구축할 수 있지만 한 회사에 대한 의존도도 그만큼 높아진다. CUDA와 엔비디아 라이브러리에 맞춰 만든 코드를 다른 가속기로 옮기려면 수정과 검증이 필요하고, 네트워크와 서버 관리 도구까지 함께 썼다면 교체 범위는 더 넓어진다. 가격 역시 GPU 한 장만 볼 것이 아니라 스위치와 네트워크 카드, 서버와 전력, 냉각, 소프트웨어 운영비까지 포함해야 한다.

### [16:00–16:28] 가동률이 비용을 결정한다 — 전용 칩의 여지
비싼 시스템이라도 GPU가 높은 비율로 계속 계산한다면 작업당 비용은 낮아질 수 있지만, 반대로 실제 작업이 시스템을 충분히 활용하지 못하면 비싼 GPU가 데이터를 기다리며 논다. 그래서 모든 AI 작업에 가장 크고 복잡한 엔비디아 시스템이 필요한 건 아니며, 특정 작업이 반복되고 모델 구조가 충분히 고정돼 있다면 필요한 기능에 집중한 전용 칩이 더 낮은 비용과 전력으로 처리할 수도 있다([의견]/조건부 판단).

### [16:28–17:05] 결론 — 양자택일 질문이 아니다
그렇다면 엔비디아의 진짜 해자는 GPU일까 시스템일까. 화자는 둘 중 하나만 골라야 하는 질문으로 보면 답을 놓친다고 정리한다. 강한 GPU가 없었다면 CUDA 생태계와 연결 기술도 지금 같은 가치를 갖기 어려웠겠지만, 좋은 GPU 한 장만으로는 수천 장을 실제 학습에 사용할 수도 없다. 엔비디아가 만들어 온 구조의 핵심은 GPU가 계산하는 시간을 늘리고 메모리·다른 GPU·CPU·네트워크를 기다리는 시간을 줄이는 데 있다.

> "강한 GPU를 중심으로 소프트웨어와 메모리, 통신과 네트워크, 서버 설계가 서로의 가치를 더 높이도록 만든 구조. 이것이 엔비디아 시스템 해자에 더 가까운 설명입니다." [16:54]

### [17:05–17:52] 그럼에도 빅테크는 왜 자체 칩을 만드나 — 다음 편 예고
이렇게 완성도 높은 시스템이 있는데도 구글은 TPU를, 아마존은 트레이니엄(Trainium)을, 마이크로소프트는 마이아(Maia)를 만들고 메타도 자체 AI 가속기를 개발하고 있다. 이 기업들이 엔비디아 GPU와 CUDA를 그대로 복제하려는 건 아니고, 자신들의 데이터센터에서 반복되는 특정 작업에 맞춰 필요 없는 기능을 덜어내고 비용·전력 효율을 그만큼 높인 전용 칩을 만들고 있다는 해석이다([의견]). 그렇다면 빅테크의 자체 칩은 엔비디아를 완전히 대체하려는 것인지, 아니면 엔비디아 시스템을 계속 쓰면서 비용이 큰 일부 작업만 자기 칩으로 가져오려는 것인지 — 다음 편에서는 GPU와 ASIC[불명확: 자막 원문 "AD 회로"]의 회로 구조·비용 차이, 구글 TPU와 빅테크 자체 칩이 어떤 조건에서 유리해지는지를 살펴보겠다고 예고하며 마친다.
