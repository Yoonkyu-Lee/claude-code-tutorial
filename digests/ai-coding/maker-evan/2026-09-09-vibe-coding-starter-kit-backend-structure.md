# AI가 만든 코드, 계속 이어 쓰는 방법 (바이브코딩 스타터킷)

> 메이커 에반 · 2026-09-09 · 696회 · 8분 19초 · [영상 링크](https://youtu.be/5dxXR-4VXU0)
> 정리 방식: 시간순 심층 워크스루 (paraphrase) + 주제별 상세 요약
> 검증 배너: 이 영상은 화자가 **직접 판매하는 유료 제품("바이브 코딩 스타터킷 확장형")의 홍보 영상**이다. 스타터킷의 구성·효과에 관한 서술은 대부분 화자 주장이며 제3자 검증이 없다. 언급된 성능 수치(uv의 10~100배)는 화자가 "공식 문서 소개"로 인용한 값이다.

## 요약 (주제별)

### 1. 문제 정의 — 왜 AI 코드는 이어 쓰기가 어려운가
- 로그인·결제·주문을 계속 붙이다 보면 한 군데를 고쳤을 때 다른 데가 깨지고, 그때마다 AI에게 전체 코드를 다시 설명하다 결국 처음부터 다시 만들게 된다.
- 화자의 진단: 이건 **프롬프트를 길게 써서 풀리는 문제가 아니다**. 코드가 들어갈 자리(구조)와 서로 연결되는 규칙이 먼저 있어야 한다 [00:15].
- 눈에 잘 안 보이는 **백엔드 구조**가 화면보다 중요하다는 것이 영상 전체의 전제. [의견]

### 2. 관통하는 비유 — 서비스를 "작은 가게"로 보기
- 손님이 보는 진열대·계산 화면 = 프론트엔드, 뒤에서 주문 받고 재고 확인하는 주방 = 백엔드. 화면이 예뻐도 주방 동선이 엉키면 주문 처리가 안 된다.
- 기술 스택 = 가게에 들일 설비 / 도메인 = 업무별 서랍 / 도커 이미지 = 준비물 상자 / 도커파일 = 포장 설명서 / AI 컨텍스트 = 지금 펼쳐 놓은 작업 책상. 영상 내내 이 비유 체계로 설명한다.

### 3. 기술 스택 선택 기준
- 화면은 무엇으로 만들고, 서버는 무엇으로 돌리고, 데이터는 어디 저장하고, 서버에 어떻게 올릴지를 정하는 일.
- "유명한 기술을 전부 가져온다고 좋은 설계가 되지는 않는다" [01:05] — 작은 카페에 대형 공장 설비를 들이면 관리할 것만 늘어난다. **만들 팀이 다룰 수 있는 범위**에 맞춰야 한다. [의견]
- 스타터킷의 실제 프론트엔드 구성으로 **Next.js + TypeScript + shadcn/ui**를 상세 페이지 캡처로 제시(자막 음차 "샤드 CN UI"). 출발점을 고정해 두면 매번 도구부터 다시 고르지 않아도 된다는 주장.

### 4. 도메인 분리 (핵심 주제)
- 여기서 도메인 = 인터넷 주소가 아니라 **회원·상품·주문처럼 서비스가 맡는 업무 단위**.
- 회원 서류와 주문표를 한 서랍에 섞으면 주문 하나 고치려다 회원까지 다 읽어야 하고, 사람도 AI도 관계 파악에 힘을 쓴다.
- 역할 3분할 예시(주문하기 버튼): **API = 주문 받는 창구**, **서비스 = 재고 확인하고 주문 처리하는 담당자**, **저장 코드 = 창고 담당**. 창구가 창고 물건을 직접 만지지 않고 정해진 담당자를 거치게 한다.
- 두 가지 단서: ① 폴더만 나눈다고 끝이 아니라 **서로의 내부 코드를 함부로 끌어다 쓰지 않는 연결 규칙**이 필요하다 [02:27]. ② 처음부터 서버를 여러 개로 쪼개라는 뜻이 아니다 — 한 서버 안에서도 업무·책임 분리는 가능하다.
- 스타터킷 상세 페이지에 "도메인·서비스·API에 자리를 정했다"고 명시돼 있다고 제품 화면을 그대로 보여 준다.

### 5. 코드 재사용 — 복붙과 다른 점, 그리고 하면 안 되는 것
- 재사용 = 복사·붙여넣기가 아니라 **같은 부품을 여러 곳에서 함께 쓰는 것**. 날짜 표시 규칙이 세 화면에 필요할 때 복사해 두면 규칙 변경 시 세 번 고쳐야 하고, 하나 놓치면 화면마다 날짜가 달라진다.
- 백엔드에서도 입력 확인·공통 오류 처리 등이 반복되며, 한 곳에서 관리하면 이미 검증된 동작을 계속 쓸 수 있다.
- **과잉 통합 경계**: 비슷하게 생겼다고 전부 합치면 안 된다. 회원 할인과 배송비 할인은 규칙이 나중에 갈릴 수 있다. "진짜 같은 책임을 가진 코드만 공통으로 묶는 게 좋다" [03:25].
- **재사용이 안전을 보장하지 않는다**: "재사용한다고 자동으로 버그가 없어지지는 않아요" [03:32]. 공통 부품을 바꾸면 쓰는 쪽의 영향까지 확인해야 안정성이 올라간다는 조건부 서술.

### 6. 구조와 AI 컨텍스트의 관계
- 컨텍스트 = AI가 지금 펼쳐 놓고 읽는 작업 책상. 주문 기능 하나 고치는데 모든 서류를 올려 두면 파일 찾기에도, 관계를 다시 설명하기에도 내용이 늘어난다.
- 업무가 분리되고 연결 규칙이 명확하면 **필요한 서랍부터** 볼 수 있고, 공통 부품 사용법을 알면 내부를 매번 새로 만들 필요도 준다 → 불필요한 읽기·재설명 양 감소(효과 크기는 수치 제시 없음, 미검증).
- 과장하지 않는 단서를 화자가 직접 붙인다: "컨텍스트를 전혀 쓰지 않는다는 뜻은 아니에요" [04:11]. AI가 실제로 어떤 파일을 읽는지에 따라 효과는 달라진다.
- 진짜 목적은 토큰 절감이 아니라 **기존 코드를 버리지 않고 이어갈 기준** — 새 대화를 시작해도 규칙 문서를 읽고 같은 자리에서 작업하게 만드는 것.

### 7. 도커파일 최적화와 빌드 캐시
- 도커 이미지 = 실행 준비물이 담긴 상자, 도커파일 = 그 상자를 어떤 순서로 만들지 적은 설명서. 공구와 안 쓰는 짐까지 넣으면 전송이 오래 걸리므로 실행에 필요한 것만 남긴다.
- **순서 원칙**: 매번 바뀌는 소스 코드보다 잘 안 바뀌는 준비물 목록(의존성)을 먼저 처리 → 준비물이 그대로면 이전 설치 결과를 재사용(빌드 캐시). "어제 포장한 기본 상자를 다시 쓰는 셈."
- **캐시의 한계**: 준비물 목록이나 앞 단계가 바뀌면 다시 만드는 구간이 생긴다. 캐시가 항상 유지된다고 생각하면 안 된다.
- 개발용 도구와 실행용 결과물을 나누는 방법도 언급(멀티스테이지 빌드에 해당하나 용어는 쓰지 않음) — 요리에 쓴 칼과 도마까지 배달 상자에 넣지는 않는다.

### 8. 파이썬 패키지 매니저 uv — 수치와 그 한계
- 패키지 = 남이 만들어 둔 부품, 패키지 매니저 = 그걸 설치하는 도구. 기존에는 pip을 많이 썼고, 대안으로 **uv**를 제시.
- **공식 문서가 pip 대비 10~100배 빠른 성능을 소개한다**고 인용(화자 전달, 영상 내 미검증).
- 즉시 붙는 단서: 그건 **패키지 작업 벤치마크**이며 "모든 배포가 100배 빨라진다는 뜻은 아니다" [05:56]. 실제 차이는 패키지 구성·네트워크·캐시 상태에 좌우된다.
- 설치를 여러 번 반복하는 환경에서는 대기 시간 절감 효과가 크고, 도커 캐시와 맞물리면 배포 준비 시간을 아끼는 데 도움.
- 속도 외의 이점: **uv 잠금 파일**이 어떤 버전 조합을 쓸지 기록해 내 컴퓨터와 배포 환경의 준비물을 일치시킨다.
- 전체 배포에서 테스트나 이미지 전송이 오래 걸리면 그 병목은 따로 봐야 한다 — "빠른 설치 도구 + 잘 만든 포장 설명서"를 함께 챙기자는 결론.

### 9. 컨벤션 — 문서로 고정해야 AI가 같은 자리에서 작업한다
- 컨벤션 = 프로젝트에서 함께 지킬 약속. 파일 이름 규칙, 어떤 코드를 어느 폴더에 둘지, 오류를 어떻게 돌려줄지, 공통 코드를 어디서 가져올지.
- 기준은 사람·프로젝트마다 다를 수 있고, **매번 AI에게 새 기준을 설명하면 같은 기능도 다른 모양으로 쌓인다**는 것이 문제. 그래서 스타터킷에 구조와 컨벤션을 함께 넣었다고 밝힘.
- 사용법: 규칙 파일을 AI에게 **먼저 읽히고** 프로젝트에 맞춰 조정. 요청 예시 — "기존 규칙과 주문 도메인을 먼저 확인하고 공통 오류 처리를 재사용해서 취소 기능을 추가해 줘" [07:12]. 즉 새로 만들기 전에 이미 있는 부품부터 찾게 하는 것.
- 규칙을 바꿔도 되지만 그때는 **문서와 코드의 기준을 함께** 맞춰야 한다.

### 10. 적용 방법과 화자가 스스로 그은 한계
- 스타터킷이 기능을 대신 완성해 주지는 않는다: "구조와 규칙이 잡힌 출발점이고 서비스 기능은 그 위에 만들어야 해요" [07:36].
- **기존 프로젝트**: 통째로 갈아엎지 말고 필요한 규칙부터 작은 범위에 적용 + 기존 동작 확인.
- **새 프로젝트**: 규칙을 먼저 읽고 작은 기능 하나를 끝까지 붙여 보며 파일이 어디 생기고 어떤 공통 코드를 쓰는지 확인.

### 11. 세일즈 구조 (정보로 1회 기록)
- 영상에서 소개·시연한 **"바이브 코딩 스타터킷 확장형"은 화자가 직접 판매하는 유료 제품**이며, 영상 중 여러 화면(기술 스택 안내, 도메인·서비스·API 구조, 규칙 파일 구조)은 그 제품 상세 페이지 캡처다.
- 상세 페이지 링크는 설명란에 넣어 두겠다고 안내. 제작 동기는 "매번 바닥부터 세팅하는 일을 줄이려고".
- 마지막에 사용 경험·질문을 나눠 달라는 커뮤니티 유입 CTA. [불명확: 자막 원문 "스킬샵" — 플랫폼 명칭이 음차로만 남아 확정 불가]

## 3줄 오리엔테이션
- AI가 짠 코드를 계속 이어 쓰지 못하는 이유는 프롬프트가 짧아서가 아니라 **코드가 들어갈 자리(구조)와 서로 연결되는 규칙**이 없기 때문이라는 주장.
- 그 구조를 네 가지로 쪼개 설명한다 — 기술 스택 선택, 도메인 분리, 코드 재사용, 도커파일 최적화, 그리고 이 모두를 문서로 고정하는 컨벤션.
- 마지막은 화자 본인이 판매하는 유료 "바이브 코딩 스타터킷 확장형" 소개로 이어진다. 구조와 규칙이 잡힌 출발점일 뿐 기능을 대신 만들어 주지는 않는다는 단서를 화자 스스로 붙인다.

## 전문 — 시간순 워크스루

### [00:00–00:16] 문제 제기 — 한 군데 고치면 다른 데가 깨진다
AI가 만든 코드에 로그인, 결제, 주문까지 기능을 계속 붙여 나갈 수 있으면 좋겠지만, 실제로는 한 군데를 고치면 다른 곳이 깨지는 일이 생긴다. 그럴 때마다 AI에게 전체 코드를 처음부터 다시 설명하게 되고, 결국 프로젝트를 처음부터 다시 만들게 된다는 것이 화자가 잡은 출발점이다.

### [00:16–00:31] 프롬프트 길이로는 안 풀린다
화자는 이 문제가 프롬프트를 길게 쓴다고 해결되지 않는다고 단언한다. 필요한 것은 코드가 들어갈 **자리**와 그 자리들을 **연결하는 규칙**이라는 것.

> "이 문제는 프롬프트를 길게 쓴다고 풀리지는 않아요. 코드가 들어갈 자리와 서로 연결하는 규칙이 먼저 필요합니다." [00:15]

이어서 본인이 만든 "바이브 코딩 스타터 킷"을 소개하겠다고 밝히고, 특히 눈에 잘 보이지 않는 **백엔드 구조**가 왜 중요한지를 다루겠다고 예고한다. 다룰 항목은 도커파일, 기술 스택, 도메인 분리, 코드 재사용이다.

### [00:31–00:53] 기본 비유 — 가게 하나를 차린다고 생각하기
용어를 외울 필요는 없고 "작은 가게 하나 만든다"고 생각하면 된다는 비유를 깐다. 손님이 보는 진열대와 계산 화면이 프론트엔드, 뒤에서 주문을 받고 재고를 확인하는 주방이 백엔드다. 화면이 예뻐도 주방 동선이 엉키면 주문을 제대로 처리할 수 없고, 백엔드 설계가 중요한 이유가 여기에 있다고 정리한다.

### [00:53–01:14] 기술 스택 = 가게에 어떤 설비를 들일지
기술 스택은 이 가게에 어떤 설비를 들일지 정하는 일에 해당한다. 화면은 무엇으로 만들고, 서버는 무엇으로 돌리고, 데이터는 어디에 저장하고, 서버에는 어떻게 올릴지를 정하는 것이다. 유명한 기술을 전부 가져온다고 좋은 설계가 되는 것은 아니라는 경고가 붙는다.

> "유명한 기술을 전부 가져온다고 좋은 설계가 되지는 않아요." [01:05]

작은 카페에 대형 공장 설비를 들이면 관리할 것만 늘어난다는 비유로, **만들 팀이 다룰 수 있는 범위**에 맞춰 골라야 한다고 말한다. [의견]

### [01:14–01:33] 스타터킷의 실제 프론트엔드 스택
화면에 스타터킷의 실제 상세 페이지를 띄우고, 프론트엔드 구성으로 **Next.js + TypeScript + shadcn/ui**를 안내하고 있다고 설명한다(자막 원문은 "넥스트 JS 타입스크립트 샤드 CN UI"의 음차). 이렇게 출발점을 맞춰 두면 매번 도구부터 다시 고르지 않아도 되고, 그 위에서 자기 서비스에 필요한 부분만 바꾸면 된다는 것이 화자의 논지다.

### [01:33–01:53] 도메인 분리 — 여기서 도메인은 인터넷 주소가 아니다
다음 주제는 도메인 분리. 여기서 말하는 도메인은 인터넷 주소가 아니라 **회원·상품·주문처럼 서비스가 맡는 업무 단위**를 뜻한다고 못 박는다. 가게 서랍을 떠올려 보라며, 회원 서류와 주문표를 한 통에 섞으면 찾기 어렵고, 주문 하나를 고치려고 열었는데 회원 서류까지 전부 읽어야 한다면 사람도 헷갈리고 AI도 관계를 파악하는 데 힘을 쓴다고 설명한다. 그래서 업무별로 담당 서랍을 나눠 둔다.

### [01:53–02:25] API / 서비스 / 저장 코드의 역할 분담
실제 상세 페이지에도 "도메인·서비스·API에 자리를 정했다"고 나와 있다며 제품 상세 페이지를 그대로 캡처해 보여 준다. 쉬운 예로, 손님이 "주문하기" 버튼을 누른 상황을 든다. **API는 주문을 받는 창구**, **서비스는 재고를 확인하고 주문을 처리하는 담당자**, **데이터를 저장하는 코드는 창고 담당**이다. 창구가 창고 물건을 마음대로 만지는 대신 정해진 담당자를 거치게 하는 것이 요점이고, 이렇게 역할을 나누면 어디를 바꿔야 하는지 찾기 쉬워진다.

### [02:25–02:43] 폴더만 나눠서는 끝이 아니다 + 서버 쪼개라는 뜻도 아니다
두 가지 오해를 미리 차단한다. 첫째, 폴더만 따로 만든다고 끝나는 게 아니라 **서로의 내부 코드를 함부로 끌어다 쓰지 않는 연결 규칙**이 함께 있어야 한다.

> "폴더만 따로 만든다고 끝나는 건 아니에요." [02:27]

둘째, 처음부터 서버를 여러 개로 쪼개라는 뜻이 아니며 **한 서버 안에서도 업무와 책임을 충분히 나눌 수 있다**고 덧붙인다.

### [02:43–03:07] 코드 재사용은 복붙과 다르다
세 번째 주제는 코드 재사용인데, 복사해서 붙이는 것과는 다르고 **같은 부품을 여러 곳에서 함께 쓰는 쪽**에 가깝다고 구분한다. 예로 날짜를 표시하는 규칙이 세 화면에 필요한 경우를 든다. 세 군데에 똑같이 복사해 두면 규칙이 바뀔 때 세 번 고쳐야 하고, 한 군데를 놓치면 화면마다 날짜가 다르게 나온다. 공통 부품으로 만들어 두고 새 화면이 가져다 쓰면 관리가 쉬워진다.

### [03:07–03:27] 백엔드 공통 코드와 "합치면 안 되는 것"
백엔드에도 입력 확인이나 공통 오류 처리처럼 반복되는 부분이 있고, 이런 코드를 한 곳에서 관리하면 이미 검증된 동작을 계속 활용할 수 있다. 다만 **비슷하게 생겼다고 전부 하나로 합치면 안 된다**는 단서를 붙인다. 회원 할인과 배송비 할인은 규칙이 나중에 달라질 수 있기 때문이다.

> "진짜 같은 책임을 가진 코드만 공통으로 묶는 게 좋아요." [03:25]

### [03:27–03:40] 재사용이 자동으로 안전을 주지는 않는다
공통 부품을 바꾸면 그것을 쓰는 쪽도 함께 확인해야 한다고 못 박는다.

> "재사용한다고 자동으로 버그가 없어지지는 않아요." [03:32]

검증된 코드를 기반으로 작업하고 **바뀐 영향까지 확인할 때** 안정성이 올라간다는 조건부 서술이다.

### [03:40–04:12] 이 구조가 AI 컨텍스트에 미치는 영향 — 작업 책상 비유
여기서 구조 이야기가 AI 쪽으로 연결된다. 컨텍스트는 **AI가 지금 펼쳐 놓고 읽는 작업 책상**이라고 생각해 보라고 한다. 주문 기능 하나 고치는데 책상에 모든 서류를 올려 놓으면 복잡해지고, 관련 파일을 찾는 데도 관계를 다시 설명하는 데도 읽어야 할 내용이 늘어난다. 반대로 업무가 분리돼 있고 연결 규칙이 명확하면 필요한 서랍부터 볼 수 있고, 공통 부품의 사용법을 알면 그 내부를 매번 새로 만들 필요도 줄어든다. 결과적으로 불필요하게 코드를 읽고 다시 설명하는 양을 줄이는 데 도움이 된다는 주장. (효과의 크기는 수치로 제시되지 않음 — 미검증)

### [04:12–04:34] 과장하지 않는 단서 + 진짜 목적
화자는 곧바로 범위를 좁힌다.

> "컨텍스트를 전혀 쓰지 않는다는 뜻은 아니에요." [04:11]

AI가 실제로 어떤 파일을 읽는지에 따라 효과는 달라진다고 덧붙인다. 중요한 건 **기존 코드를 버리지 않고 계속 이어갈 수 있는 기준**이며, 새 대화를 시작해도 규칙 문서를 읽고 같은 자리에서 작업하게 만드는 것이 목표다. 그래서 자신은 화면보다 이런 백엔드 기초를 정말 중요하게 본다고 밝힌다. [의견]

### [04:34–04:55] 도커파일 = 포장 설명서
네 번째 주제는 도커파일 최적화. 이름은 어렵지만 **포장 설명서**라고 보면 쉽다고 한다. 도커 이미지는 프로그램을 실행할 준비물이 담긴 상자, 도커파일은 그 상자를 어떤 순서로 만들지 적은 설명서다. 상자에 공구와 쓰지 않는 짐까지 다 넣으면 보내는 데 오래 걸리므로, 실행에 필요한 것만 남기면 이미지 크기와 전송 부담을 줄일 수 있다.

### [04:55–05:22] 순서와 빌드 캐시 — 그리고 캐시의 한계
순서도 중요하다. 매번 바뀌는 소스 코드보다 **잘 안 바뀌는 준비물 목록(의존성)을 먼저 처리**하면, 준비물이 그대로일 때 이전에 만들어 둔 설치 결과를 다시 쓸 수 있다. 이게 빌드 캐시이고, "어제 포장한 기본 상자를 다시 쓰는 셈"이다. 코드 한 줄 고쳤다고 모든 패키지를 처음부터 다시 설치하지 않게 하는 장치다. 다만 준비물 목록이나 앞 단계가 바뀌면 다시 만드는 구간이 생기므로 **캐시가 언제나 유지된다고 생각하면 안 된다**고 단서를 단다.

### [05:22–05:35] 개발용 도구와 실행용 결과물 분리
개발할 때 쓰는 도구와 실제 실행에 필요한 결과물을 나누는 방법도 있다고 언급한다(멀티스테이지 빌드에 해당하는 설명이나 화자는 그 용어를 쓰지 않는다). 요리할 때 쓴 칼과 도마까지 배달 상자에 넣지는 않는다는 비유. 이런 포장 기준까지 챙겨야 배포를 반복할 때 시간이 덜 샌다.

### [05:35–05:54] 파이썬이라면 패키지 매니저 — uv
파이썬 백엔드라면 패키지 매니저도 살펴볼 만하다고 한다. 패키지는 남이 만들어 둔 필요한 부품, 패키지 매니저는 그걸 설치하는 도구다. 기존에는 pip을 많이 썼는데(자막 음차 "팁"), 여기서 **uv**를 사용할 수 있다는 것. uv는 필요한 부품을 찾고 설치하는 작업을 빠르게 처리한다.

### [05:54–06:14] 10~100배 수치와 그 한계
uv 공식 문서는 pip보다 **10배에서 100배 빠른 성능**을 소개한다고 인용한다(화자가 전한 공식 문서 주장, 이 영상 내에서는 미검증). 곧바로 범위를 좁히는데, 이건 **패키지 작업의 벤치마크**라는 점을 강조한다.

> "모든 배포가 100배 빨라진다는 뜻은 아닙니다." [05:56]

실제 차이는 패키지 구성, 네트워크, 캐시 상태에 따라 달라진다. 그래도 설치를 여러 번 반복하는 환경에서는 기다리는 시간을 많이 줄일 수 있고, 도커 캐시까지 잘 맞추면 배포 준비 시간을 아끼는 데 도움이 된다고 정리한다.

### [06:14–06:37] 속도 말고 버전 고정 — 잠금 파일
속도만 볼 것은 아니라며, 같은 부품을 **같은 버전**으로 맞추는 것도 중요하다고 짚는다. uv의 잠금 파일은 어떤 버전 조합을 사용할지 기록해 두는 목록이고, 내 컴퓨터와 배포 환경의 준비물을 맞추는 데 활용할 수 있다. 또 전체 배포에서 테스트나 이미지 전송이 오래 걸린다면 그 부분은 따로 봐야 한다며, 결론은 "빠른 설치 도구와 잘 만든 포장 설명서를 함께 챙기자"는 것이다.

### [06:37–07:07] 컨벤션 = 프로젝트에서 함께 지킬 약속
마지막 주제는 컨벤션. 파일 이름을 어떻게 짓고, 어떤 코드를 어느 폴더에 두고, 오류는 어떻게 돌려주고, 공통 코드는 어디에서 가져올지를 정하는 약속이다. 이 기준은 사람마다 프로젝트마다 다를 수 있는데, 매번 AI에게 새 기준을 설명하면 **같은 기능도 다른 모양으로 쌓이기 쉽다**는 것이 문제 지점이다. 그래서 이번 바이브 코딩 스타터킷에는 구조와 컨벤션을 함께 넣어 뒀다고 밝힌다.

### [07:07–07:30] 규칙 파일을 먼저 읽히고 요청하는 법
화면에 상세 페이지에 있는 실제 규칙 파일 구조를 보여 주며, 이 기준을 AI에게 **먼저 읽히고** 각자 프로젝트에 맞춰 가면 된다고 안내한다. 실제 요청 예시를 제시한다.

> "기존 규칙과 주문 도메인을 먼저 확인하고 공통 오류 처리를 재사용해서 취소 기능을 추가해 줘." [07:12]

새로 만들기 전에 이미 쓸 수 있는 부품부터 찾아 달라는 뜻이라고 해설한다. 프로젝트에 다른 규칙이 더 맞는다면 바꿔도 되지만, 그때는 **문서와 코드의 기준을 함께 맞추는 것**이 중요하다고 덧붙인다.

### [07:30–07:58] 스타터킷의 한계와 적용 방법
스타터킷이 모든 기능을 대신 완성해 주지는 않는다고 선을 긋는다.

> "구조와 규칙이 잡힌 출발점이고 서비스 기능은 그 위에 만들어야 해요." [07:36]

이미 잘 돌아가는 프로젝트가 있다면 통째로 갈아엎을 필요도 없고, 필요한 규칙부터 작은 범위에 적용하고 기존 동작을 확인하면 된다. 새 프로젝트라면 먼저 규칙을 읽고 **작은 기능 하나를 끝까지 붙여 보면서** 어디에 파일이 생기고 어떤 공통 코드를 쓰는지 확인해 보라고 권한다.

### [07:58–08:19] 마무리 — 유료 제품 안내
화자는 매번 바닥부터 세팅하는 일을 줄이려고 이 스타터킷을 만들었다고 동기를 밝힌다. 오늘 보여 준 **"바이브 코딩 스타터킷 확장형"은 본인이 직접 판매하는 제품**이며 상세 페이지 링크를 설명란에 넣어 두겠다고 안내한다(세일즈 장치 — 정보로 1회 기록). 구성과 사용 환경을 확인하고 자기 서비스의 출발점으로 활용해 보라고 권하며, 판매·커뮤니티 채널로 보이는 곳에서 사용 경험과 질문을 나눠 달라고 마무리한다. [불명확: 자막 원문 "스킬샵" — 판매/커뮤니티 플랫폼 명칭이 음차로만 남아 확정 불가]
