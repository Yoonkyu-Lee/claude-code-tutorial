# 왜 다들 Buzz로 가나 — 별 3만 개 받은 잭 도시 회사의 오픈소스

> 정리 방식: 시간순 심층 워크스루 (paraphrase) + 주제별 상세 요약
> 검증 배너: 별·포크·이슈·PR 수, 릴레이 내부 스펙(파이프라인 단계 수, 제한값 등)은 모두 **화자가 저장소·문서·공식 데모를 읽고 전한 주장**이며 이 정리에서 별도 검증하지 않았다. "안 되는 것" 목록도 화자가 확인했다고 말한 시점 기준이다.

## 요약 (주제별)

### 1. Buzz가 무엇인가 — 정체와 배경
- 잭 도시의 회사 **블록(Block)**이 만든 오픈소스. 이름 Buzz는 "벌집"이라는 뜻. GitHub 공개 6개월 만에 별 31,000개, 포크 4,000개 가까이(주장/미검증).
- 한 줄 정의가 어렵다. 채팅 앱이라기엔 Git 저장소를 품고, 개발 도구라기엔 채널과 DM이 있다. 공식 설명은 "**사람과 에이전트가 같이 일하는 작업 공간, 내가 소유한 릴레이 위에서**".
- 화자는 이 문장이 마케팅 카피인 줄 알고 코드·아키텍처 문서·공식 데모 영상을 프레임 단위로 확인했고, "카피가 아니라 설계가 실제로 그렇게 돼 있다"고 결론 냈다. [의견]

### 2. 없애려는 낭비 ① — 사람·에이전트 사이 복붙 왕복
- 현재 방식: 터미널에서 결과를 받아 슬랙에 복사 → 팀원 답변을 다시 복사해 터미널로. 이 왕복이 하루에 여러 번.
- 화자가 짚는 진짜 문제는 시간이 아니라 **에이전트가 그 대화를 못 본다**는 것 — "에이전트한테는 내가 붙여 넣은 조각만 세상의 전부입니다" [01:15].
- Buzz의 해법: 에이전트를 채널 안에 들여 사람과 **같은 스크롤**을 보게 한다. 그 결과 "컨텍스트를 옮겨 붙이는 비용이 0"이 된다는 게 화자의 정리.

### 3. 신원 모델 — Nostr 키쌍, "에이전트는 봇이 아니라 멤버다"
- Buzz는 **Nostr 프로토콜** 위에 올라간다. Nostr에서 계정은 곧 키쌍 — 공개 키가 이름, 비밀 키로 서명. 사람도 에이전트도 각자 키를 가진다.
- 그래서 에이전트가 남긴 모든 흔적에 서명이 붙고, 누가 코드를 밀었는지·누가 승인했는지가 **암호학적으로**, 서버 관리자도 사후 조작할 수 없는 형태로 남는다.
- 화자 평가: "API 키 발급하고 봇이라 부르는 것과는 층위가 다르다." 공식 문서의 "**에이전트는 봇이 아니라 멤버다**"가 프로젝트 전체를 요약한다고 본다. [의견]

### 4. 공식 데모가 보여준 장면 (블록 사이트 게시 영상)
- 엔지니어링 채널에서 사람 셋이 스택 논의 → **엘레나**가 플러터로 옮기자고 제안(한 코드베이스로 두 플랫폼).
- **알렉스**가 에이전트 **범블**을 호출해 포팅 계획 재작성 지시 → 범블이 리액트 뷰를 플러터 위젯으로 매핑하며 상태 레이어를 에이전트 **피즈**에게 위임 → 피즈가 게임 루프를 옮기며 **허니**를 호출, 허니가 위젯 트리 작성. **에이전트가 에이전트에게 일을 나눠 준다.**
- 화자가 화면을 멈춘 지점: "새 에이전트가 같은 쓰레드를 읽고 있으니까 가능한 겁니다. 아무도 컨텍스트를 다시 설명하지 않았습니다" [02:55].
- 후반부: 범블이 소스 PR을 Buzz 안에, 피즈가 배포 PR을 GitHub 쪽에 올리고 둘 다 같은 채널에 카드로 붙음 → 허니가 둘 다 리뷰 → 마지막에 사람에게 리뷰 1회 요청 → 알렉스가 PR 상세에서 승인. "탭을 바꾸지 않았습니다" [05:05].

### 5. 저장 구조 — 단일 이벤트 로그와 kind 라우팅
- **모든 게 이벤트**다. 메시지·반응·캔버스 수정·워크플로우 실행 전부 서명된 JSON 한 덩어리이고, 채널·종류가 달라도 **로그는 하나**.
- 결과: 검색이 한 번에 끝난다. 대화·코드·티켓을 따로 뒤질 필요 없이 **PostgreSQL 전문 검색 인덱스 하나**가 전부를 덮는다.
- 이벤트에 붙는 **kind(정수 하나)가 라우팅의 전부**. 새 기능 = 새 kind 정의로 끝이고, 모르는 kind를 받은 구버전 클라이언트는 무시하므로 **깨지는 변경이 원칙적으로 없다**. 화자는 이래야 확장 비용이 계단식으로 안 올라간다고 평가. [의견]

### 6. 릴레이 내부 구현
- 이벤트 하나가 들어오면 **12단계 파이프라인**(주장/미검증): 인증 확인 → 서명 검증 → 멤버십 확인 → 저장 → 팬아웃.
- 검색 색인·감사 로그·워크플로우 발동은 결과를 기다리지 않고 던져 놓고 지나가 사용자 응답(OK) 시점을 앞당긴다.
- 서명 검증은 런타임 스레드를 막지 않도록 별도 스레드로 분리. 화자는 **Rust로 짠 이유**가 이 대목에서 드러난다고 본다. [의견]

### 7. 없애려는 낭비 ② — 도구 간 탭 전환, Git을 이벤트로
- 문제: 논의는 슬랙, 이슈는 트래커, 코드 리뷰는 GitHub → 같은 결정이 세 군데에 흩어진다.
- Buzz는 Git을 이벤트로 취급 — **브랜치가 쓰레드, PR이 채팅 안 카드**.
- 기술적으로 릴레이가 **Git Smart HTTP**를 직접 받고, 푸시 전에 정책·권한을 확인한다. 인증은 **서명한 이벤트를 헤더에 실어 보내는** 방식.
- 감사 관점의 의미: 에이전트에게 커밋 권한을 주는 게 무서운 이유는 "누가 뭘 했는지 모르기 때문"인데, 자기 키 서명이 그 지점을 메운다는 게 화자 판단. [의견]

### 8. 워크플로우 엔진 — YAML + 방어 설계
- 클릭 UI가 아니라 **YAML**로 작성.
- **트리거 4종**: 메시지 게시 / 이모지 반응 / 정해진 시각 / 외부 웹훅 수신.
- **액션 7종**: 메시지 보내기, 다이렉트 메시지, 채널 주제 변경, 반응 달기, 외부 웹훅 호출, 승인 요청, 대기.
- 변수 지원(트리거의 텍스트·작성자·앞 단계 출력)과 조건문 지원.
- 방어 설계: 조건식 평가 **100ms 제한**, 외부 웹훅은 **리다이렉트 차단 + 응답 1MB 절단**, 동시 실행 **100개 초과 시 큐잉 없이 즉시 거절**, 워크플로우가 만든 메시지는 다른 워크플로우를 발동시키지 않게 제외해 **무한 루프를 구조적으로 차단**.

### 9. 한계 — Developer Preview, 안 되는 것 5가지
- 공식 사이트 첫 화면부터 **Developer Preview**. 블록도 완성품이라 말하지 않는다.
- ① **승인 게이트 미완성** — 사람 승인 대기 액션이 문서엔 있지만 실제로는 그 지점에서 실행이 실패 처리. 자동화에서 가장 중요한 안전장치가 미완.
- ② **일부 액션이 껍데기** — DM 보내기, 채널 주제 바꾸기.
- ③ **모바일 진행 중** — 플러터로 개발 중, 푸시 알림은 계획 단계.
- ④ **이름은 Nostr인데 P2P가 아님** — 릴레이 하나가 읽기·쓰기의 단독 창구이고 릴레이 간 교신 구조가 아니다. 탈중앙 기대하면 실망.
- ⑤ **셀프호스팅 문턱이 낮지 않음** — Docker 필요, PostgreSQL·Redis 기동, 빌드에는 Rust와 Node까지.
- 부가 지표: 열린 이슈 1,400개 / PR 1,800개(주장/미검증). 활발하다는 뜻이자 흔들린다는 뜻인데 화자는 후자를 더 크게 보고 "**회사 전체를 옮기는 건 아직 이르다**"고 판단. [의견]

### 10. 그럼 누가 지금 쓰나 — 두 부류
- **에이전트를 두 개 이상 굴리는 사람**: Buzz는 특정 모델에 묶이지 않고 **ACP(Agent Client Protocol)** 공용 규약을 쓴다. Claude Code, Codex, 블록의 **Goose**가 다 붙고 한 채널 안에서 서로 대화하게 만들 수 있다.
- **대화 기록을 외부에 두면 안 되는 팀**: 전부 자기 서버 안에서 돌고, 감사 로그가 **해시 체인**(앞 기록의 해시가 다음 기록에 포함)으로 묶여 중간을 지우면 사슬이 끊겨 바로 드러난다.
- 이 판단 자체는 화자 [의견].

### 11. 시작 방법·라이선스
- 맥·윈도우·리눅스 데스크톱 앱이 이미 있고 저장소 **릴리스 탭**에서 받으면 된다.
- 직접 띄우려면 **Railway 원클릭 배포 버튼** 제공.
- 라이선스는 전부 **Apache 2.0** — 상업적 사용·포크·수정 모두 가능. 실제 포크 4,000개 가까이(주장/미검증).

### 12. 영상의 결론과 CTA
- "Buzz가 없앤 건 기능이 아니라 **왕복**" — 사람·에이전트 간 복붙, 채팅/트래커/GitHub 간 탭 전환을 **이벤트 로그 하나로 접었다**는 것이 화자의 총평 [08:34].
- 아직 프리뷰지만 방향은 분명하다고 평가하고 [의견], "여러분은 지금 에이전트를 몇 개나 굴리고 계신가요?"라는 댓글 유도로 마무리.

## 3줄 오리엔테이션
- 잭 도시의 회사 Block이 낸 오픈소스 **Buzz**는 채팅 앱도 개발 도구도 아니고, "사람과 에이전트가 같은 채널에서 같이 일하는 작업 공간"이며 그 공간을 내 릴레이(서버)에 두는 구조다.
- 핵심 설계는 세 가지 — ① Nostr 키쌍 기반 신원(사람과 에이전트가 동일한 자격), ② 메시지·반응·캔버스·Git·워크플로가 전부 **하나의 서명된 이벤트 로그**, ③ YAML 워크플로 엔진. 이 셋이 "복붙 왕복"과 "탭 전환"을 없앤다는 게 영상의 주장이다.
- 다만 Developer Preview라서 승인 게이트 미완성, 일부 액션 껍데기, 모바일 미완, P2P 아님, 셀프호스팅 문턱 등 한계가 있고, 화자는 "회사 전체를 옮기기엔 아직 이르다"고 [의견]을 붙인다.

## 전문 — 시간순 워크스루

### [00:00–00:16] GitHub에 올라온 지 여섯 달 된 저장소
GitHub에 공개된 지 여섯 달 된 저장소 하나가 별 31,000개, 포크 4,000개 가까이를 모았다(주장/미검증). 만든 곳은 잭 도시의 회사 **블록(Block)**, 이름은 **버즈(Buzz)** — "벌집"이라는 뜻이다. 그런데 이게 무엇을 하는 물건인지가 한 줄로 설명되지 않는다는 게 화자의 출발점이다.

### [00:16–00:30] 채팅 앱도 개발 도구도 아닌 것
채팅 앱이라고 하기엔 Git 저장소를 품고 있고, 개발 도구라고 하기엔 채널과 다이렉트 메시지가 있다. 공식 설명은 "사람과 에이전트가 같이 일하는 작업 공간, 그것도 **내가 소유한 릴레이 위에서**"다.

### [00:30–00:56] 코드를 열어보고 내린 결론
화자는 이 문장을 마케팅 카피로 의심해서 코드를 열고, 아키텍처 문서를 끝까지 읽고, 공식 데모 영상을 프레임 단위로 뜯었다고 말한다. 결론은 카피가 아니라 실제 설계가 그렇게 돼 있다는 것.

> "그리고 이 설계 때문에 지금까지 우리가 당연하게 여기던 낭비가 통째로 사라집니다." [00:41]

이어서 영상 구성을 예고한다 — 그 낭비가 정확히 무엇이었는지, Buzz가 어떻게 없앴는지, 그리고 마지막에는 **아직 안 되는 것들도 정직하게** 짚겠다고 한다.

### [00:56–01:20] 첫 번째 낭비 — 사람·에이전트 사이의 복붙 왕복
지금 우리가 에이전트를 쓰는 방식은 이렇다. 터미널을 열고 프롬프트를 넣고 결과를 본다 → 그 결과를 복사해 슬랙에 붙인다 → 팀원이 읽고 답한다 → 그 답을 다시 복사해 터미널로 가져간다. 화자는 문제의 본질이 시간이 아니라고 못 박는다.

> "에이전트가 그 대화를 못 본다는 겁니다. 에이전트한테는 내가 붙여 넣은 조각만 세상의 전부입니다." [01:15]

### [01:20–01:42] Nostr 키쌍 — 사람과 에이전트의 신원 모델이 같다
Buzz는 에이전트를 채널 안으로 들여, 사람 옆자리에 앉히고 같은 스크롤을 보게 한다. 이게 가능한 이유는 **신원 모델이 사람과 에이전트가 똑같기** 때문이다. Buzz는 **Nostr 프로토콜** 위에 올라가 있고, Nostr에서 계정은 곧 키쌍이다 — 공개 키가 이름이고 비밀 키로 서명한다. 사람도 이 키를 쓰고, 에이전트도 자기 키를 따로 가진다.

### [01:42–01:57] 서명이 남기는 감사 흔적
그래서 에이전트가 남긴 모든 흔적에 서명이 붙는다. 누가 이 코드를 밀었는지, 누가 이 결정을 승인했는지가 **암호학적으로**, 그것도 서버 관리자가 나중에 조작할 수 없는 형태로 남는다. 화자는 이것이 "API 키 하나 발급해 주고 봇이라고 부르는" 방식과는 층위가 다르다고 평가한다. [의견]

### [01:57–02:14] "에이전트는 봇이 아니라 멤버다"
공식 문서에는 "에이전트는 봇이 아니라 멤버다"라는 문장이 있고, 화자는 이 한 줄이 프로젝트 전체를 요약한다고 본다. [의견] 말로만 하면 안 믿길 테니 블록이 자기 사이트에 올려둔 **공식 데모 영상**을 그대로 가져와 보여주겠다고 한다.

### [02:14–02:28] 데모 전반 — 사람 셋의 스택 논의
무대는 엔지니어링 채널. 사람 셋이 먼저 이야기한다. 프로토타입이 커지기 전에 스택을 정리하자는 논의이고, **엘레나**가 플러터로 옮기자고 제안한다(한 코드베이스로 두 플랫폼을 덮자는 것). 여기까지는 여느 슬랙 대화와 똑같다.

### [02:28–02:47] 알렉스가 에이전트를 부르고, 에이전트가 에이전트에게 위임한다
그다음 줄부터 달라진다. **알렉스**가 **범블(Bumble)**을 부르는데, 범블은 사람이 아니라 에이전트다. 방향이 바뀌었으니 포팅 계획을 다시 짜라고 지시하자 범블이 바로 답한다 — 리액트 뷰를 플러터 위젯으로 매핑하는 중이고, 상태 레이어는 **피즈(Fizz)**에게 넘기겠다고. 피즈도 에이전트다. 에이전트가 에이전트에게 일을 나눠 준다.

### [02:47–03:04] 사람이 심부름하지 않는다
피즈가 게임 루프를 옮기면서 **허니(Honey)**를 부르고, 허니가 위젯 트리를 짠다. 사람이 중간에서 심부름을 하지 않는다. 화자는 이 대목에서 화면을 멈췄다고 말한다.

> "새 에이전트가 같은 쓰레드를 읽고 있으니까 가능한 겁니다. 아무도 컨텍스트를 다시 설명하지 않았습니다." [02:55]

### [03:04–03:15] 효율의 정체 — 컨텍스트 이전 비용이 0
화자는 이 효율의 정체를 "**컨텍스트를 옮겨 붙이는 비용이 0이 된다**"로 정리한다. 그리고 왜 0이 되는지는 저장 구조를 보면 바로 보인다고 이어간다.

### [03:15–03:31] 모든 것이 하나의 서명된 이벤트, 하나의 로그
Buzz에서는 모든 게 **이벤트**다. 메시지도 이벤트, 반응도 이벤트, 캔버스 수정도, 워크플로우 실행도 이벤트이며 전부 서명된 JSON 한 덩어리다. 그리고 이 이벤트가 **전부 같은 로그**에 쌓인다 — 채널이 다르고 종류가 달라도 로그는 하나다.

### [03:31–03:39] 그래서 검색이 한 번에 끝난다
대화를 뒤지고 코드를 따로 뒤지고 티켓을 또 뒤질 일이 없다. **PostgreSQL 전문 검색 인덱스 하나**가 전부를 덮는다.

### [03:39–03:59] kind — 정수 하나가 라우팅의 전부
설계가 영리해지는 지점은 이벤트에 붙는 **kind**라는 정수 하나다. 이 숫자가 라우팅의 전부여서, 새 기능을 넣고 싶으면 새 kind를 정의하면 끝이다. 모르는 kind를 받은 옛날 클라이언트는 그냥 무시하므로, 기능을 추가해도 **깨지는 변경(breaking change)이 원칙적으로 없다**. 화자는 프로토콜을 이렇게 짜면 확장 비용이 계단식으로 뛰지 않는다고 평가한다. [의견]

### [03:59–04:16] 릴레이 내부 — 12단계 파이프라인과 비동기 분리
이벤트 하나가 들어오면 **12단계 파이프라인**을 탄다(주장/미검증). 인증 확인 → 서명 검증 → 멤버십 확인 → 저장 → 팬아웃(fan-out) 순서다. 그런데 검색 색인, 감사 로그, 워크플로우 발동은 결과를 기다리지 않고 던져 놓고 지나간다. 사용자에게 OK가 떨어지는 시점이 그만큼 앞당겨진다.

### [04:16–04:26] 서명 검증을 별도 스레드로 — Rust를 쓴 이유
서명 검증도 런타임 스레드를 막지 않으려고 별도 스레드로 빼놨다. 화자는 Buzz를 **Rust**로 짠 이유가 이 대목에서 드러난다고 본다. [의견]

### [04:26–04:44] 두 번째 낭비 — 도구 사이를 건너뛰는 일
논의는 슬랙에서, 이슈는 트래커에서, 코드 리뷰는 GitHub에서 하다 보면 **같은 결정이 세 군데에 흩어진다**. Buzz는 Git을 이벤트로 취급한다 — 브랜치가 쓰레드가 되고, 풀 리퀘스트가 채팅 안에 카드로 뜬다.

### [04:44–05:09] 데모 후반 — PR 카드, 에이전트 리뷰, 사람 한 번
데모 뒷부분이 정확히 이 장면이다. 범블이 소스 PR을 Buzz 안에 열고, 피즈는 배포 PR을 GitHub 쪽에 따로 올린다. 둘 다 같은 채널에 카드로 나란히 붙고 허니가 두 개를 다 리뷰한다. 그리고 마지막에 사람을 부른다 — 사람 리뷰 한 번만 해 달라고. 알렉스가 프로젝트 화면으로 넘어가면 PR 상세가 열리고 승인 버튼이 있다.

> "채널에서 시작한 대화가 승인까지 한 화면 안에서 끝납니다. 탭을 바꾸지 않았습니다." [05:05]

### [05:09–05:25] 기술적으로는 — Git Smart HTTP를 릴레이가 직접 받는다
릴레이가 **Git Smart HTTP**를 직접 받고, 푸시를 받기 전에 정책과 권한을 확인한다. 인증은 서명한 이벤트를 헤더에 실어 보내는 방식이다. 그래서 에이전트가 푸시를 해도 자기 키로 서명했으니 누가 했는지가 남는다.

### [05:25–05:34] 감사 관점의 의미
화자는 이것이 감사 관점에서 꽤 크다고 본다. [의견] 에이전트에게 커밋 권한을 주는 게 무서운 이유가 결국 "누가 뭘 했는지 모르기 때문"인데, 그 지점을 서명으로 막는다는 것.

### [05:34–06:01] 세 번째 — 워크플로우 엔진 (YAML, 트리거 4 / 액션 7)
Buzz에는 워크플로우 엔진이 들어 있고, 설정 화면에서 클릭으로 만드는 게 아니라 **YAML로 쓴다**. 트리거는 네 가지 — 메시지가 올라왔을 때, 누가 이모지를 달았을 때, 정해진 시각에, 외부에서 웹훅을 쐈을 때. 액션은 일곱 가지 — 메시지 보내기, 다이렉트 메시지, 채널 주제 바꾸기, 반응 달기, 외부 웹훅 호출, 승인 요청, 그리고 대기. 변수도 쓸 수 있어 트리거의 텍스트·작성자·앞 단계의 출력을 그대로 끌어오고, 조건문도 넣을 수 있다.

### [06:01–06:31] 방어 설계 — 100ms, 1MB, 동시 100개, 루프 차단
화자가 눈여겨본 건 방어 설계다. 조건식 평가에 **100ms 제한**이 걸려 있어 악의적인 식으로 릴레이를 붙잡아둘 수 없다. 외부 웹훅은 리다이렉트를 막고 응답을 **1MB**에서 자른다. 동시 실행은 **100개**까지만 받고 넘치면 줄을 세우는 게 아니라 즉시 거절한다. 그리고 워크플로우가 만든 메시지는 다른 워크플로우를 발동시키지 않게 제외해 뒀다 — 무한 루프를 구조적으로 막은 것이다. 자동화 도구를 만들어 본 사람은 이게 왜 중요한지 알 거라고 덧붙인다.

### [06:31–06:53] 한계 ① 승인 게이트가 아직 안 붙었다
여기까지가 좋은 이야기고, 이제 안 되는 것들이다. 공식 사이트 첫 화면에 **Developer Preview**라고 적혀 있어 블록도 완성품이라고 말하지 않는다. 첫째, **승인 게이트가 미완**이다 — 사람 승인을 기다리게 만드는 액션이 문서에는 있는데 실제로는 그 지점에서 실행이 실패로 처리된다. 자동화에서 제일 중요한 안전장치가 미완성이라는 뜻이다.

### [06:53–07:04] 한계 ②③ 껍데기 액션, 모바일 진행 중
둘째, 액션 중 일부가 아직 껍데기다 — 다이렉트 메시지 보내기와 채널 주제 바꾸기가 그렇다. 셋째, 모바일이 아직 진행 중이다. 플러터로 만들고 있고 푸시 알림은 계획 단계다.

### [07:04–07:15] 한계 ④ 이름은 Nostr인데 P2P가 아니다
넷째, 이름은 Nostr인데 **P2P가 아니다**. 릴레이 하나가 읽기와 쓰기의 단독 창구[불명확: 원문 "단독 권유"]이고, 릴레이끼리 서로 이야기를 주고받는 구조가 아니다. 탈중앙을 기대하고 들어오면 실망한다.

### [07:15–07:35] 한계 ⑤ 셀프호스팅 문턱 + 열려 있는 이슈·PR
다섯째, 자체 호스팅 문턱이 낮지 않다. Docker가 필요하고 PostgreSQL과 Redis를 띄워야 하며, 빌드하려면 Rust와 Node까지 갖춰야 한다. 그리고 지금 열려 있는 **이슈가 1,400개, 풀 리퀘스트가 1,800개**다(주장/미검증).

### [07:35–07:44] 화자의 판단 — 아직 이르다
그 숫자는 여섯 달 된 프로젝트치고 활발하다는 뜻이기도 하고 아직 흔들리는 중이라는 뜻이기도 한데, 화자는 후자를 더 크게 본다. [의견] 회사 전체를 여기로 옮기는 건 아직 이르다는 결론.

### [07:44–08:04] 그래도 지금 쓸 사람 ① 에이전트를 둘 이상 굴리는 사람
그렇다고 쓸 이유가 없느냐면 아니고, 화자는 두 부류에게는 지금이 맞다고 본다. [의견] 하나는 에이전트를 두 개 이상 굴리는 사람이다. Buzz는 특정 모델에 묶여 있지 않고 **ACP(Agent Client Protocol)**라는 공용 규약을 쓴다. 그래서 Claude Code도, Codex도, 블록이 만든 **Goose**도 붙고, 한 채널 안에서 서로 대화하게 만들 수 있다.

### [08:04–08:17] 쓸 사람 ② 대화 기록을 밖에 두면 안 되는 팀
다른 하나는 대화 기록을 외부에 두면 안 되는 팀이다. 전부 내 서버 안에서 돌고, 감사 로그가 **해시 체인**으로 묶인다 — 앞 기록의 해시가 다음 기록에 들어가므로 중간을 지우면 사슬이 끊어져 바로 티가 난다.

### [08:17–08:34] 시작하는 법 — 데스크톱 앱, Railway 원클릭, Apache 2.0
시작은 어렵지 않다. 맥·윈도우·리눅스용 앱이 이미 나와 있어 저장소 릴리스 탭에서 받으면 되고, 직접 띄워 보고 싶으면 **Railway 원클릭 배포 버튼**이 있다. 라이선스는 전부 **Apache 2.0**이라 상업적으로 써도 되고 포크해 고쳐도 된다. 실제로 포크가 4,000개 가까이 나와 있다(주장/미검증).

### [08:34–08:52] 정리 — 없앤 건 기능이 아니라 왕복
마무리에서 화자는 Buzz가 없앤 것을 이렇게 정리한다.

> "버즈가 없앤 건 기능이 아니라 왕복입니다. 사람과 에이전트 사이를 오가던 복사와 붙여 넣기, 채팅과 트래커와 GitHub 사이를 오가던 탭 전환. 그걸 이벤트 로그 하나로 접었습니다." [08:34]

아직 프리뷰지만 방향은 분명하다고 평가하며 [의견], "여러분은 지금 에이전트를 몇 개나 굴리고 계신가요?"라고 댓글 CTA로 닫는다.
