# 클로드 vs GPT, 석 달 동안 같은 일을 시켜봤습니다

## 요약 (주제별)

### 실험 설계 — 실무 병렬 테스트, 단일 기준
- 석 달 동안 클로드와 GPT를 같은 자료·같은 요청·같은 마감에 나란히 붙여 봤다. 시킨 일은 화자가 매일 하는 실무: 영상 대본 쓰기, 코드 고치기, 자료 정리, 광고 문구 뽑기.
- 흔한 비교 영상은 질문 하나 던지고 답이 예쁜지로 끝나는데, [의견] 화자는 그건 "시험 문제 하나 풀린 것"이지 일을 시켜 본 게 아니라고 본다.
- 유일한 평가 기준은 "다시 손대야 하는 시간" — 답이 그럴듯한지가 아니라 내가 얼마나 고쳐야 쓸 수 있는지. [의견] 실무에서 유일하게 중요한 기준이라는 입장.

### 일의 길이 축 — 짧은 일 무승부, 긴 일은 클로드
- 짧은 일(요약·번역·문장 다듬기)은 둘 다 잘해서 차이가 거의 없고 취향 차이 정도.
- 파일 여러 개를 훑고 찾고 고치고 확인하고 다시 고치는 흐름을 끝까지 끌고 가는 힘에서 클로드가 앞섰다. [의견] "기억력 30분 신입 vs 오후 내내 붙어 있는 신입"으로 비유.
- 화자 체감상 중간에 끼어들어 방향을 다시 잡는 횟수가 절반 정도로 줄었다(주장/미검증).

### 코드 작업 — 신규는 무승부, 기존 코드 수정은 클로드
- 새로 짜는 코드(로그인 화면, 표 정렬 함수 등)는 어떤 모델이든 웬만큼 해서 무승부.
- "남의 코드"(이미 돌아가는 프로젝트에 손대기)에서 갈린다. [의견] 여기서 중요한 건 실력이 아니라 조심성 — 건드리면 안 되는 걸 안 건드리는 능력.
- 화자 경험상 클로드가 덜 사고 쳤고, 멀쩡한 파일을 마음대로 다시 쓰는 일이 적었다(주장/미검증).

### GPT가 앞선 구간 — 막힌 문제·구조·문서
- 막힌 문제를 다른 각도로 푸는 것("이거 왜 안 되지" 상태에서 다른 접근 제시)은 GPT가 시원시원했다.
- 글쓰기에서 GPT는 구조를 잘 잡는다(서론·본론·결론, 항목 정리, 표). 깔끔한 문서가 필요할 때 편했다.

### 실제 사례 — 자막이 화면 밖으로 잘리는 버그
- 원인이 안 보이는 종류(글자 수/화면 크기/글꼴). GPT는 가능한 원인을 목록으로 나열해 방향 잡기는 좋았으나, 결국 화자가 하나씩 확인해야 했다.
- 클로드는 파일을 직접 열어 범인을 좁히고 고친 뒤 다시 확인, 남은 것도 같이 고쳤다. 화자는 상황 설명과 결과 확인만 했다. [의견] "답을 아는 것과 끝까지 처리하는 건 다른 일".

### 화자의 실사용 역할 분담
- 아이디어가 막히면 GPT에게 묻고, 실제 코드에 손대는 건 클로드에게 맡긴다. [의견] 둘이 싸울 이유가 없고 역할이 다르다.
- 정리: 긴 작업·파일 여러 개·실제 코드 수정 → 클로드 / 막힌 문제·자료 구조·문서 정리 → GPT.
- 사람에게 그대로 보내는 글(메일·대본)은 톤이 차분한 클로드가 손이 덜 갔다.

### 핵심 결론 — 모델보다 세팅
- [의견] 석 달 결론은 "모델보다 세팅이 결과를 더 많이 바꿨다" — 같은 모델도 어떻게 쓰느냐로 결과가 두 배씩 벌어졌다(주장/미검증).
- 반복 업무마다 짧은 규칙 문서 한 장(말투·금지 표현·결과 형식)을 붙였더니 두 모델 다 결과가 좋아졌고, 모델 간 격차도 줄었다.
- 그래서 모델 갈아타기보다 규칙 문서 다듬는 데 시간을 더 쓴다. 좋은 글의 조건은 모델이 아니라 사용자가 준 자료 — 자료를 주면 둘 다 살고, 안 주면 둘 다 뻔해진다.
- 순서 원칙: 모델부터 고르지 말고 할 일부터 정의한 다음 맞는 쪽에 던져라. 한마디로 "모델을 바꾸기 전에 조건을 먼저 바꿔라".

### 비용 관점
- [의견] 월정액 채팅만 쓰면 어느 쪽이든 큰 차이 없으니 손에 익은 걸 쓰면 된다.
- 돈이 갈리는 건 사람이 안 보는 자동·장기 실행 — 한번 잘못 돌면 비용이 훅 나간다.
- 대응 두 가지: 긴 작업은 짧게 쪼개서 시키고, 중간에 결과를 한번 확인하고 넘어간다. [의견] 비싼 모델을 피하는 것보다 헛도는 걸 막는 게 훨씬 효과가 크다.

### 세일즈·커뮤니티 구조와 예고
- 댓글로 각자 어떤 일에 어떤 모델을 쓰는지 물으며, 더 깊은 인사이트는 스킬샵과 오픈 톡톡방에서 나눈다고 안내(유입 구조).
- 다음 영상에서 자기가 쓰는 규칙 문서를 통째로 공개하겠다고 예고.

## 3줄 오리엔테이션
- 화자가 석 달 동안 자기 실무(대본·코드·자료·광고 문구)를 클로드와 GPT에 나란히 시켜 보고, "답이 예쁜가"가 아니라 "내가 다시 손대야 하는 시간"이라는 단일 기준으로 비교한 경험담.
- 짧은 일은 차이가 거의 없지만, 긴 작업·기존 코드 수정에서는 클로드가, 막힌 문제 풀기·구조 잡기·문서 정리에서는 GPT가 나았다는 역할 분담 결론.
- 최종 메시지는 "모델보다 세팅(규칙 문서·자료·작업 쪼개기)이 결과를 더 크게 바꾼다 — 모델을 바꾸기 전에 조건을 먼저 바꿔라".

## 전문 — 시간순 워크스루

### [00:00–00:23] 실험 방식 — 시험 문제가 아니라 실무를 시켰다
화자는 지난 석 달 동안 클로드와 GPT를 같은 자료·같은 요청·같은 마감에 나란히 붙여 봤고, 결과가 생각보다 깔끔하게 갈렸다고 연다. 흔한 비교 영상은 질문 하나 던져 놓고 답이 예쁜지 아닌지로 끝나는데, 그건 실제로 일을 시켜 본 게 아니라 "시험 문제 하나 풀린 것"일 뿐이라고 지적한다. 그래서 화자는 방식을 바꿔, 자기가 원래 하던 업무를 그대로 두 모델에게 시켰다고 한다.

> "대부분 질문 하나 던져 놓고 답이 예쁘다, 아니다로 끝나거든요. 그건 실제로 일시켜 본 게 아니에요. 시험 문제 하나 풀린 거죠." [00:18]

### [00:23–00:45] 유일한 평가 기준 — "다시 손대야 하는 시간"
시킨 일은 영상 대본 쓰기, 코드 고치기, 자료 정리하기, 광고 문구 뽑기. 매일 하는 일이라 결과가 좋은지 나쁜지 화자가 바로 안다는 점을 근거로 든다. 그리고 딱 하나만 봤다고 한다 — 답이 그럴듯한지가 아니라 "내가 얼마나 고쳐야 쓸 수 있는지", 즉 다시 손대야 하는 시간. [의견] 화자는 이게 실무에서는 유일하게 중요한 기준이라고 본다.

> "답이 그럴듯한지가 아니라 제가 얼마나 고쳐야 쓸 수 있는지. 이게 실무에서는 유일하게 중요한 기준이에요." [00:39]

### [00:45–01:12] 첫 번째 차이 — 일의 길이 (짧은 일 vs 긴 일)
첫 번째 차이는 "일의 길이"에서 나왔다. 질문 하나 던지고 답 하나 받는 일과, 30단계짜리 일을 맡기는 것은 완전히 다른 종목이라는 것. 짧은 일(요약해 줘, 번역해 줘, 이 문장 다듬어 줘)에서는 둘 다 잘해서 차이가 거의 없고 취향 차이 정도였다. 하지만 일이 길어지면 얘기가 달라져서, 파일 열 개를 훑고 고칠 곳을 찾고 고치고 확인하고 다시 고치는 흐름을 끝까지 끌고 가는 힘에서 클로드가 앞섰다고 한다.

### [01:12–01:33] 비유 — 기억력 30분 신입 vs 오후 내내 붙어 있는 신입
[의견] 화자는 이 차이를 "기억력이 30분짜리인 신입 직원"과 "오후 내내 하나에 붙어 있는 신입 직원"의 차이로 비유한다. 둘 다 똑똑하지만 긴 일을 맡기면 결과가 완전히 달라진다는 것. 화자 체감으로는, 중간에 자기가 끼어들어 방향을 다시 잡아주는 횟수가 절반 정도로 줄었고(주장/미검증), 이게 하루로 쌓이면 꽤 큰 시간이라고 한다.

### [01:33–02:03] 코드 — 새로 짜기는 무승부, 남의 코드 고치기에서 클로드
코드에서 가장 확실하게 갈렸다고 한다. 새로 짜는 코드(로그인 화면, 표 정렬 함수 등)는 지금 어떤 모델이든 웬만큼 하니 둘 다 잘 쓴다. 문제는 "남의 코드", 즉 이미 돌아가는 프로젝트에 손을 넣는 일. [의견] 화자는 기존 코드를 고칠 때 중요한 건 실력이 아니라 "조심성", 건드리면 안 되는 걸 안 건드리는 능력이라고 본다. 화자 경험으로는 클로드가 여기서 덜 사고 쳤고, 멀쩡한 파일을 자기 마음대로 다시 쓰는 일이 적었다(주장/미검증).

### [02:03–02:19] GPT가 좋았던 구간 — 막힌 문제를 다른 각도로
반대로 GPT가 좋았던 구간도 분명히 있다. 막힌 문제를 다른 각도로 풀 때, "이거 왜 안 되지" 하고 붙잡고 있을 때 아예 다른 접근을 던져 주는 건 GPT가 시원시원했다고 한다. 그래서 화자는 아이디어가 막히면 GPT에게 물어보고, 실제로 코드에 손대는 건 클로드에게 맡긴다. [의견] 둘이 싸울 이유가 없고 역할이 다르다는 정리.

> "아이디어가 막히면 GPT한테 물어보고요. 실제로 코드에 손대는 건 클로드한테 맡겨요. 둘이 싸울 이유가 없어요. 역할이 다르니까요." [02:15]

### [02:19–03:03] 실제 사례 — 자막이 화면 밖으로 잘리는 버그
말로만 하면 감이 안 오니 한 가지 예를 든다. 화자 프로젝트에서 자막이 화면 밖으로 잘리는 문제가 있었는데, 원인이 눈에 안 보이는 종류였다 — 글자 수 문제인지, 화면 크기 문제인지, 글꼴 문제인지. GPT에게 물었을 때는 가능한 원인을 쭉 나열해 줬고, 목록으로 정리해 주니 방향 잡기는 좋았지만 결국 화자가 하나씩 확인해야 했다. 반면 클로드는 파일을 직접 열어 범인을 좁히고, 고친 뒤 다시 확인하고 남은 것도 같이 고쳤다. 화자가 한 건 처음에 상황을 설명하고 마지막에 결과를 본 게 다였다고 한다. [의견] "답을 아는 것과 끝까지 처리하는 건 다른 일"이라는 게 화자가 말한 차이.

> "클로드는 파일을 직접 열어보고 범인을 좁혔습니다. … 제가 한 건 처음에 상황 설명하고 마지막에 결과 본 게 다예요." [02:45]

### [03:03–03:24] 글쓰기 — 승부 없음, 성격이 다름
글 쓰는 일은 승부가 안 났고 성격이 다르다고 한다. GPT는 구조를 잘 잡는다 — 서론·본론·결론, 항목 정리, 표 만들기. 깔끔하게 정리된 문서가 필요할 땐 GPT가 편했다. 클로드는 톤이 차분해서 문장을 덜 꾸미고 과장을 덜 하며, 사람한테 그대로 보내는 글(메일이나 대본)은 클로드 쪽이 손이 덜 갔다고 한다.

### [03:24–03:44] 글쓰기의 진짜 변수 — 모델이 아니라 준 자료
[의견] 화자는 어느 쪽이든 그냥 쓰면 티가 난다고 한다 — 둘 다 안전한 문장을 좋아하기 때문. 좋은 글의 조건은 모델이 아니라 사용자가 준 자료라는 것. 자료를 던져 주면 둘 다 확 살고, 안 주면 둘 다 뻔해진다.

> "좋은 글의 조건은 모델이 아니라 여러분이 준 자료예요. 자료를 던져 주면 둘 다 확 (살고) 안 주면 둘 다 뻔해집니다." [03:33]

### [03:44–03:56] 핵심 전환 — 모델보다 세팅이 결과를 더 바꿨다
"그래서 뭘 쓰라는 거야?"라는 반응이 나올 지점에서, 화자가 석 달 써 보고 내린 결론은 좀 다르다고 한다. [의견] 모델보다 세팅이 결과를 더 많이 바꿨다는 것 — 같은 모델인데 어떻게 쓰느냐로 결과가 두 배씩 벌어졌다(주장/미검증).

### [03:56–04:31] 규칙 문서 한 장의 효과
가장 크게 바뀐 건 자료를 붙여 줬을 때다. [의견] 화자는 이를 "신입한테 알아서 잘해 봐"와 "회사 매뉴얼 주고 시키는 것"의 차이로 비유한다 — 사람이 바뀐 게 아니라 조건이 바뀐 것. 화자는 반복되는 일마다 짧은 규칙 문서를 만들어 뒀다: 말투는 이렇게, 금지 표현은 이거, 결과는 이 형식으로 — 한 장짜리, 길게 안 쓴다. 이 문서 하나를 붙였더니 두 모델 다 결과가 좋아졌고, 재밌는 건 모델 사이의 격차가 줄었다는 점. 세팅이 좋으면 어느 쪽을 써도 쓸 만한 게 나오므로, 화자는 모델 갈아타기보다 규칙 문서 다듬는 데 시간을 더 쓴다 — 그게 더 남는 장사더라는 것.

### [04:31–05:05] 비용 — 채팅은 무의미, 돈은 자동 장기 실행에서 갈린다
