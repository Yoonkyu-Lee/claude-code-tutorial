## 요약 (주제별)

### 무엇이 바뀌었나 (기능 정의)
- 클로드 코드 2.1.224(8월 첫 주 릴리스)부터 **여러 세션이 서로에게 직접 메시지를 보낸다**. 예전에도 세션을 여러 개 띄울 수는 있었으나 서로를 몰랐고, 둘 사이를 잇는 건 사람의 기억이었다.
- 건너가는 건 **파일 전체가 아니라 클로드가 쓴 요약 텍스트 한 줄**("작업 끝냈다" 알림, "필요한 것" 되묻기 등). 화자는 긴 코드 뭉치를 넘기면 받는 쪽 맥락이 흐려지고 한 문장 요약이 훨씬 잘 먹힌다고 본다. [의견]
- 별도 설정 없이 **버전만 맞으면 동작**. [의견] 같은 컴퓨터 안에서 주고받으면 앤트로픽 서버를 거치지 않아 지연이 거의 없다는 화자 설명(미검증).

### 사용법과 전제
- 세션 두 개를 띄우고 각자 맡을 일을 알려 준 뒤 "필요할 때 상대에게 말하라"고 하면 됨.
- 그냥 띄운다고 알아서 굴러가지 않음 — **무엇을 언제 알릴지는 사람이 한 번은 정해 줘야** 한다.

### 잘 맞는 상황 7가지
1. **프론트/백엔드 동시 작업**: 백엔드가 응답 형태를 바꾼 순간 프론트 세션에 필드 변경(무엇→무엇, 영향받는 화면)이 전달됨. [의견] 타입스크립트가 못 잡는 "타입 없는 구간"(응답 JSON 키 이름 같은 컴파일러가 모르는 약속)에서 효과가 가장 컸다. 예: 이름 필드를 둘로 쪼갤 때 화면 깨지기 전에 프론트가 먼저 알게 됨.
2. **큰 마이그레이션**: 디렉터리 10개짜리를 A(서버)/B(클라이언트)로 나눠 돌릴 때, 규칙이 갈라지는 게 진짜 문제(카멜 표기 vs 밑줄 표기). 먼저 정한 쪽 규칙(이름·폴더 구조·예외 처리)이 넘어가 결과가 한 방향으로 모임. [의견] 규칙 준수는 사람이 제일 못하는 일이라 기계가 오히려 잘함.
3. **버그 재현/수정 분리**: 재현 세션이 원인을 찾은 순간 수정 세션으로 전달. 예: "타임아웃이 아니라 커넥션 풀 고갈이다"[03:32] 한 줄로 수정 방향이 즉시 바뀜. 원인이 예상과 다른 층에 있을 때 차이 큼.
4. **리뷰(만들기/뜯어보기 분리)**: [의견] 같은 세션 리뷰는 자기 코드라 관대해지지만, 세션을 나누면 맥락 분리로 냉정한 지적이 나옴. 화자 기본 조합 = "만드는 세션 하나 + 의심하는 세션 하나".
5. **대기 시간**: 10분짜리 테스트가 끝나면 작업 중 세션으로 결과(실패 테스트 이름 포함)가 넘어옴. 주의를 끊지 않고 필요한 정보만 도착 — 빌드·배포 등 오래 걸리는 일에 적용.
6. **문서/구현 분리**: 스펙 세션과 구현 세션을 분리. 스펙 변경이 즉시 전달되어, 구현 시작 전이면 방향만 바꾸면 되어 수정 비용이 쌈.
7. **멀티 저장소**: 서버 저장소 + 앱 저장소에 각각 세션을 두고 대화시키면 모노레포처럼 동작. [의견] 화자가 체감이 가장 컸던 방식 — 양쪽 동시 변경(서버 규격 변경 → 앱 대응)의 왕복이 사라짐.

### 안 맞는 상황 / 주의
- **작은 작업엔 쓰지 마라** — 파일 하나 고치는데 세션 둘 띄우면 조율이 더 오래 걸림.
- **같은 파일 동시 편집은 여전히 나쁨** — 말을 건다고 편집 충돌이 사라지지 않음. **영역(폴더)을 먼저 갈라 놓고** 말을 걸게 해야 함.
- **메시지가 너무 잦으면** 양쪽 다 산만해짐(모든 변경 알림 금물).
- **결과를 안 봐도 되는 건 아님** — 잘못된 결론·틀린 전제도 그대로 건너가 되돌리기 더 번거로움. [의견] 화자는 큰 결정은 바로 반영 말고 자기한테 한 번 보여 달라는 **중간 점검**을 넣음.

### 실전 요령 6가지
1. 세션마다 역할을 **이름으로** 부여("백엔드 담당" 등) → 메시지가 정확해짐.
2. **알릴 기준을 미리** 지정("약속이 바뀔 때만") → 소음 감소.
3. 오래 걸리는 작업은 **시작 사실부터** 알리게 → 상대가 대기/선행 판단.
4. 끝나면 **양쪽 요약**을 받기 → 커밋 메시지가 쉬워짐.
5. **두 개로 시작** — 셋 넘어가면 관리 어려움, 익숙해진 뒤 늘리기.
6. **한쪽을 조용한 세션**으로 — 수다스러운 세션 옆에 긴 작업만 하는 세션을 두면 균형. 양쪽 다 수다스러우면 사람이 피곤.

### 화자의 결론 (관점)
- [의견] "세션끼리 말을 건다"는 건 기능 추가라기보다 **일하는 방식의 변화**에 가까움. 지금까지 사람이 가운데서 모든 정보를 중계했다면, 이제 그 선이 직접 연결되고 사람 역할은 "영역을 나누고 기준을 정하는 것"으로 축소.
- [의견] 처음엔 습관대로 복붙하게 되지만, 한번 맡겨 보면 다시 손으로 나르기 싫어짐 — 일이 줄어서라기보다 "끊기는 지점이 없어져서". "창 두 개 띄워 놓고 같은 말을 두 번 하고 있었다면 오늘 한번 놔 보라"[07:23].

## 3줄 오리엔테이션
- 클로드 코드 2.1.224부터 여러 세션이 서로에게 직접 메시지를 보낼 수 있게 됐고(세션 간 요약 문장 전달), 이제까지 사람이 손으로 하던 "한쪽에서 알아낸 걸 다른 쪽에 옮기는 일"이 사라진다는 얘기다.
- 이 기능이 실제로 도움이 되는 7가지 상황(프론트/백엔드 동시 작업, 큰 마이그레이션, 버그 재현·수정 분리, 리뷰, 대기 시간, 문서·구현 분리, 멀티 저장소)과, 오히려 방해되는 경우(작은 작업, 같은 파일 동시 편집, 과도한 메시지, 무검증 신뢰)를 하나씩 짚는다.
- 화자의 결론은 "기능이 하나 늘었다기보다 일하는 방식이 바뀐다" — 사람은 영역을 나누고 알림 기준만 정하는 역할로 줄어든다는 것.

## 전문 — 시간순 워크스루

### [00:00–00:30] 문제 제기: 정보를 나르는 건 늘 사람이었다
화자는 클로드 코드를 여러 창으로 띄워 쓸 때 "한쪽에서 알아낸 걸 다른 쪽에 다시 설명하는 일"을 거의 매일 했다고 말한다. 고친 파일 경로를 복사하고, 바뀐 함수 이름을 붙여 놓고, 왜 바꿨는지 한 번 더 적는 식이었다. 작업은 나눠서 하는데 정보를 나르는 건 늘 사람이었다는 것. 그런데 8월 첫 주에 나온 2.1.224부터 그 일이 사라졌다고 한다.
> "세션끼리 서로 말을 겁니다." [00:22]

화자는 오늘 이 기능이 어떤 상황에서 실제로 도움이 되는지, 반대로 언제는 오히려 방해가 되는지 하나씩 짚어 보겠다고 예고한다.

### [00:30–00:56] 무엇이 바뀌었나 — 세션 간 직접 메시지
예전에도 세션을 여러 개 띄울 수는 있었지만 서로를 몰랐다. 각자 자기 대화만 보고 있었고, 둘 사이를 잇는 건 사람의 기억이었다. 이제는 한쪽 세션이 다른 쪽 세션에 직접 메시지를 보낸다 — 작업을 끝냈다고 알리기도 하고, 필요한 걸 되묻기도 한다. 건너가는 것은 클로드가 쓴 텍스트 한 줄이며, 파일을 통째로 넘기는 게 아니라 무슨 일이 있었는지 요약한 문장이다.

### [00:56–01:11] 요약 문장이라서 더 잘 먹힌다 + 로컬 처리
화자는 이 점이 생각보다 중요하다고 강조한다. 긴 코드 뭉치를 넘기면 받는 쪽 맥락이 오히려 흐려지는데, 한 문장으로 요약된 변경 사실이 훨씬 잘 먹힌다는 것. [의견] 또 같은 컴퓨터 안에서 주고받으면 앤트로픽 서버도 거치지 않아서 지연도 거의 없다고 설명한다. (같은 머신 내 세션 간 전달이면 서버를 경유하지 않는다는 화자 설명 — 미검증)

### [01:11–01:31] 쓰는 방법과 전제
쓰는 방법 자체는 간단하다. 세션을 두 개 띄우고, 각자 무슨 일을 맡는지 알려 준 다음, 필요할 때 상대에게 말하라고 하면 된다. 별도로 켜야 하는 설정은 없고 버전만 맞으면 그냥 된다. 다만 그냥 띄워 놓는다고 알아서 잘 굴러가지는 않으며, 무엇을 언제 알릴지는 사람이 한 번은 정해 줘야 한다고 못박는다(뒤에서 다시 다룬다).

### [01:31–02:22] 상황 1 — 프론트와 백엔드를 같이 만질 때
가장 자주 오는 경우다. 백엔드 세션에서 응답 형태를 바꾸면 프론트 쪽은 그걸 모르고, 보통은 화면이 깨지고 나서야 "아 스키마 바꿨지" 하고 떠올린다. 이제는 백엔드가 필드를 바꾼 순간 그 사실이 프론트 세션으로 넘어간다 — 필드 이름이 무엇에서 무엇으로 바뀌었는지, 어떤 화면이 영향을 받는지까지.

[의견] 화자가 써 보니 효과가 가장 컸던 건 "타입이 없는 구간"이었다. 타입스크립트가 잡아주는 부분은 어차피 빌드에서 걸리지만, 응답 JSON의 키 이름처럼 컴파일러가 모르는 약속은 못 잡는다. 그 부분을 말로 넘겨 준다는 게 생각보다 큰 차이를 만들었다고 한다. 예시로, 사용자 정보 응답에서 이름 필드를 둘로 쪼갠 경우 — 예전이라면 화면 여기저기가 비어 나오고 그제야 원인을 찾아 올라갔지만, 이제는 쪼갠 그 순간에 프론트 세션이 먼저 알게 되어 깨진 화면을 보기 전에 고친다.

### [02:22–03:11] 상황 2 — 큰 마이그레이션
디렉터리가 열 개쯤 되는 작업을 한 세션에 다 맡기면 중간에 맥락이 흐려지므로 보통 나눠서 돌린다(A 세션은 서버 쪽, B 세션은 클라이언트 쪽). 이때 진짜 문제는 규칙이 갈라지는 것이다 — A는 함수 이름을 카멜 표기로 바꾸고 B는 밑줄 표기로 가면, 둘 다 틀린 건 아닌데 합쳐 놓으면 엉망이 된다. 세션이 서로 말을 걸면 먼저 정한 쪽의 규칙(이름 규칙, 폴더 구조, 예외 처리 방식 등)이 그대로 넘어가서, 사람이 중간에서 심판을 보지 않아도 결과가 한 방향으로 모인다.

[의견] 화자는 이걸 큰 리팩터링에서 처음 느꼈다고 한다. 예전에는 합치는 날 하루를 통째로 정리에만 썼다는 것. 그는 규칙을 지키게 만드는 일이 사실 사람이 제일 못하는 일이라고 본다 — 열 개 폴더를 돌다 보면 본인이 정한 규칙도 잊어버리는데, 이건 오히려 기계가 잘한다고 말한다.

### [03:11–03:42] 상황 3 — 버그를 잡을 때 (재현 / 수정 분리)
화자는 재현과 수정을 나눠서 쓴다 — 한쪽은 로그를 파고 다른 쪽은 코드를 고친다. 예전에는 이게 잘 안 맞았다. 재현 세션이 원인을 찾아내도 수정 세션은 여전히 옛날 가설로 코드를 만지고 있었기 때문이다. 이제는 원인을 찾은 순간 그 문장이 수정 쪽으로 넘어간다.
> "타임아웃이 아니라 커넥션 풀 고갈이다." [03:32]

이 한 줄이 건너가면 수정 방향이 즉시 바뀌고 헛수고하는 시간이 확 줄어든다. 특히 원인이 예상과 다른 층에 있을 때 차이가 크다고 한다.

### [03:42–04:10] 상황 4 — 리뷰 (만드는 세션 / 뜯어보는 세션)
한 세션은 만들고 다른 세션은 그걸 뜯어 본다. [의견] 같은 세션 안에서 리뷰를 시키면 자기가 방금 쓴 코드라 관대해지는 경향이 있는데, 세션을 나누면 맥락이 분리돼서 조금 더 냉정한 지적이 나온다는 것. 리뷰 세션이 문제를 찾으면 구현 세션으로 바로 전달되어, 사람이 두 창을 오가며 지적을 옮겨 적을 필요가 없다. 화자는 요즘 이 조합을 기본으로 쓴다고 한다 — 만드는 세션 하나, 의심하는 세션 하나.

### [04:10–04:36] 상황 5 — 기다리는 시간
테스트가 10분씩 걸리는 프로젝트에서는 기다리는 동안 다른 걸 하게 되는데, 문제는 테스트가 끝났을 때 다른 작업에 빠져 있어서 결과 확인이 한참 늦어진다는 것이다. 이제는 테스트 세션이 끝나면 작업 중인 세션에 결과(실패한 테스트 이름과 함께)가 넘어온다. 주의를 끊지 않으면서 필요한 정보만 도착하며, 빌드나 배포처럼 오래 걸리는 일에 다 적용된다.

### [04:36–04:56] 상황 6 — 문서와 구현을 나눌 때
스펙을 정리하는 세션과 그걸 구현하는 세션을 따로 둔다. 예전에는 스펙이 바뀌면 구현 쪽이 마지막에야 알아서 이미 만들어 놓은 걸 뜯어야 했다. 이제는 문장이 바뀐 시점에 전달되므로, 구현이 아직 시작 전이면 그냥 방향만 바꾸면 끝이라 고치는 비용이 훨씬 싸다.

### [04:56–05:25] 상황 7 — 저장소가 여러 개일 때
서버 저장소와 앱 저장소가 갈려 있으면 한 세션에서 둘 다 보기가 어렵다. 각 저장소에 세션을 하나씩 두고 둘이 대화하게 하면 모노레포처럼 굴러간다. [의견] 화자는 이 방식이 가장 체감이 컸다고 한다 — 저장소가 갈려 있으면 양쪽을 동시에 바꿔야 하는 변경이 제일 성가신데(서버에서 규격을 바꾸고 앱에서 그걸 맞추는 사이를 사람이 왕복했음), 이제 그 왕복이 사라진다.

### [05:25–05:57] 반대 얘기 — 잘 안 맞는 경우
공평하게 반대 얘기도 한다.
- **작업이 작으면 쓰지 마라.** 파일 하나 고치는 일에 세션을 두 개 띄우면 조율하는 데 더 오래 걸린다.
- **같은 파일 동시 편집은 여전히 나쁘다.** 서로 말을 건다고 해서 편집 충돌이 사라지지는 않는다. 영역을 먼저 갈라 놓아야 한다("이 세션은 이 폴더만, 저 세션은 저 폴더만") — 그러고 나서 말을 걸게 하는 것.
- **메시지가 너무 잦아도 문제.** 모든 변경을 알리게 하면 양쪽 다 산만해진다.

### [05:57–06:18] 결과를 안 봐도 되는 건 아니다 (중간 점검)
세션이 서로 말한다고 해서 결과를 안 봐도 되는 건 아니다. 잘못된 결론도 그대로 건너가고, 틀린 전제가 양쪽으로 퍼지면 되돌리는 게 더 번거롭다. [의견] 그래서 화자는 중간 점검을 넣는다 — 한쪽이 큰 결정을 내렸을 때 바로 반영하지 말고 자기한테 한번 보여 달라고 한다. 결정 하나만 확인하면 되니 부담도 크지 않다는 것.

### [06:18–07:05] 실전 요령 6가지
화자가 실제로 쓰면서 정리한 요령:
1. **세션마다 역할을 이름으로 주기** — "백엔드 담당", "프론트 담당"처럼. 역할이 분명하면 메시지도 정확해진다.
2. **알릴 기준을 미리 말해 두기** — "약속이 바뀔 때만 알려 달라"고 하면 소음이 크게 줄어든다.
3. **오래 걸리는 작업은 시작 사실부터 먼저 알리게 하기** — 상대 세션이 기다릴지 다른 걸 먼저 할지 판단한다.
4. **끝나면 양쪽 요약을 받아보기** — 두 세션이 각자 무엇을 했는지 정리해 주면 커밋 메시지가 쉬워진다.
5. **세션은 두 개로 시작하기** — 세 개 넘어가면 관리가 어려워진다. 익숙해진 다음 늘려도 늦지 않다.
6. **한쪽을 조용한 세션으로 두기** — 계속 말을 거는 세션 옆에 묵묵히 긴 작업만 하는 세션을 두면 균형이 잘 맞는다. 양쪽 다 수다스러우면 결국 사람이 피곤해진다.

### [07:05–07:45] 마무리 — 일하는 방식이 바뀐다
화자는 세션끼리 말을 건다는 게 "기능 하나가 늘어난 것보다 일하는 방식이 바뀌는 쪽에 가깝다"고 정리한다. 지금까지는 사람이 가운데였고 모든 정보가 그를 거쳐 갔지만, 이제는 그 선이 직접 연결되어 사람이 할 일은 "영역을 나누고 기준을 정하는 것" 정도로 줄었다는 것.
> "창 두 개를 띄워 놓고 같은 말을 두 번 하고 계셨다면 오늘 한번 놔 보세요." [07:23]

[의견] 화자 자신도 며칠은 습관대로 복사해서 붙여 넣고 있었지만, 한번 맡겨 보면 다시 손으로 나르기가 싫어진다고 한다. 일이 줄어서라기보다 "끊기는 지점이 없어져서" 그렇고, 생각보다 금방 익숙해진다는 말로 끝맺는다.
