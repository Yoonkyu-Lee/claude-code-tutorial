## 요약 (주제별)

### 스킬의 목적과 배경
- 유튜브 영상 한 편은 8단계다: 대본 → 목소리 → 자막 타이밍 → 화면 → 렌더 → 썸네일 → 업로드 → 예약.
- 처음엔 각 단계를 매번 개별 지시로 시켰으나 결과가 매번 달랐다(자막이 반박자 밀리고, 어제 쓴 옵션을 오늘 안 쓰는 식). 가장 답답했던 건 이미 아는 걸("이 목소리 써라", "이 해상도로 렌더해라", "자막은 몇 픽셀 위에") 매번 다시 타이핑해야 한 것.
- 이 영상 자체가 사람 편집 없이 이 스킬 하나로 제작된 산출물이라고 화자는 강조한다.

### 스킬 구조 — 3덩어리와 "읽는 시점 옮기기"
- **본문(순서만, 300줄 조금 안 됨) + 참고 문서 4개(목소리·화면·썸네일·업로드) + 실행 파일 5개(코드).**
- 본문에 다 적으면 클로드가 매번 다 읽는다("매뉴얼 200장 문제"). 순서만 본문에 두고 나머지는 밖으로 빼, 예컨대 썸네일 만들 때가 되면 그때 썸네일 문서만 읽는다.
- 참고 문서 4개 합치면 본문보다 훨씬 길지만 필요할 때만 열린다. 핵심은 "글자 수를 줄인 게 아니라 읽는 시점을 옮긴 것".
- **스킬 경계 원칙: 하나의 스킬 = 하나의 결과물.** 롱폼·쇼츠·인스타를 한 스킬에 묶으려다 본문이 길어져 클로드가 중간을 흘려서, 롱폼/쇼츠/인스타로 쪼갰다.

### 실행 파일 5개
- **목소리 파일**: 대본을 넣으면 음성 + 자막 타이밍을 한꺼번에 뱉음(소리 크기 정규화 포함).
- **썸네일 파일**: 한 장씩 순서대로, 실패 시 재시도.
- **화면 캡처 파일**: 전체 화면 찍으면 다른 창이 같이 찍혀 사고 날 뻔 → 브라우저로 해당 페이지만 캡처.
- **파일 넘겨주는 서버**: 업로드용(아래 참고).
- **자막 보조 파일**: 남이 만든 음성으로 중간부터 시작할 때만 사용.

### 실전 절차와 수치 (단계별 함정)
- **대본**: 길이는 감이 아니라 실측. 짧게 합성해 글자수÷오디오길이 → 화자는 초당 8.69자, 10분 ≈ 5,200자. 편집기 예상 시간은 신뢰 금지(다른 도구는 실제보다 50%+ 짧게 표시 — 주장). 문단이 아니라 자막 한 줄씩 작성 → 대본이 곧 화면 자막이 되어 변환 불필요, 문장도 저절로 짧아짐.
- **나레이션·자막**: 순서를 뒤집어 자막을 먼저 쓰고 그대로 읽힌다 → STT 받아쓰기 불필요(고유명사·화자 이름 오인식 제거). 목소리 생성 시 글자별 타이밍을 함께 받음. 자막 한 줄 30자 이하(한 글자 ≈ 42픽셀, 30자 = 1,260픽셀로 화면 안에 맞음).
- **목소리 생성 규칙**: ① 문단 단위(약 800자씩)로 만들어 억양 초기화 방지 ② 소리 크기 정규화 — 문단 간 차이가 10dB 넘기도(주장), 맞춘 뒤 3dB 이내인지 재확인 ③ 대본 수정 시 임시 파일 삭제(안 지우면 옛 음성이 다시 나옴).
- **화면**: 60fps 유지(30으로 낮추면 모션 끊김); 신 전환 시 전체 화면 확대 효과 제거(이어붙이면 내내 흔들림); 배경 텍스트 간격 신마다 벌어지던 것 제거.
- **제목 크기**: 내용 기반 자동 축소가 제목까지 줄여 신마다 커졌다 작아짐(제일 작을 때 26픽셀, 최소~최대 10배 차 — 주장). 해결: 위쪽 300픽셀을 제목 자리로 고정, 자동 축소는 아래 그림에만.
- **흔들림 검출**: 눈으로는 못 잡음. 연속 프레임 두 장을 빼서 변화 %를 측정, 요소 등장이 끝났는데 계속 바뀌면 흔들림.
- **렌더**: 11분 ≈ 4만 프레임, 돌려놓고 다른 일. 완료 후 영상 길이 = 오디오 길이 확인(어긋나면 자막 통째로 밀림). 폰트 로드 실패(미리보기는 되고 렌더에서만 죽음)는 시스템 폰트 사용으로 회피(한글 굵은 글씨 충분).
- **썸네일**: 레퍼런스는 참고지 복사 대상 아님 — 자기 채널 최고 썸네일 그대로 만들면 시청자가 이미 수십 번 봐 피드에서 안 보임 → 반대색으로 변경. 한 장씩 만들고 확인(세 장 한 번에 시키면 두 장쯤 조용히 사라짐). 만든 뒤 한글 글자 깨짐(받침 누락·오탈자)을 사람이 눈으로 대조. 썸네일 3장 + 제목 3개를 짝지어 유튜브 A/B 비교에 맡김.
- **업로드**: 파일 브라우저 주입이 보안으로 막혀 → 작은 웹서버를 잠깐 띄워 파일을 페이지에 건네는 방식으로 우회.

### 업로드 화면의 함정 3가지
- 제목·설명칸이 평범한 입력창이 아니라 붙여넣기 불가 → 다른 방법으로 주입.
- 자동완성 창 닫으려 ESC 누르면 업로드 창이 통째로 닫힘(임시 저장은 됨).
- 예약 날짜 기본값이 내일 → 오늘로 직접 선택, 시간칸은 눌러 커서 잡고 타이핑. 이 셋을 모르면 업로드 한 번에 30분씩 소요.

### 비용
- 목소리 생성은 글자 수만큼 과금. 10분 대본 5,000자+, 대본 수정 후 재생성 시 그만큼 또 지출. 스킬에 "생성 직전 예상 비용을 먼저 알려라"를 넣어, 분량을 다시 정할 기회를 확보(기능이라기보다 습관).

### 이 스킬을 안 쓰는 때
- 쇼츠(규격·자막 위치 달라 별도 스킬), 대본만 필요할 때(대본 스킬만 호출), 이미 만든 영상 업로드만 할 때(이 스킬을 쓰되 앞 단계 건너뜀 — "무엇을 가졌으면 몇 단계부터"를 표로 정리).

### 철학 — 스킬은 매뉴얼이 아니라 흉터
- 스킬에 적힌 함정(예상치 믿지 마라 / 받아쓰기 하지 마라 / 프레임 낮추지 마라 / 화면 전체 움직이지 마라 / 레퍼런스 복사하지 마라)은 전부 화자가 직접 틀린 뒤 적은 것.
- "스킬은 매뉴얼이 아니라 흉터에 가깝다. 틀릴 때마다 한 줄씩 늘어난다." [의견] 처음부터 완벽하게 쓰려 오래 붙잡기보다 짧게 만들어 쓰다 틀릴 때마다 붙이는 게 훨씬 빠르다.
- 다음 영상 예고: 이 스킬이 실제로 도는 걸 처음부터 끝까지 시연. (세일즈·커뮤니티 유입: 스킬샵·오픈톡방 언급.)

## 3줄 오리엔테이션
- 화자가 유튜브 영상 한 편(대본→목소리→자막→화면→렌더→썸네일→업로드→예약, 8단계)을 사람 손 없이 만드는 데 쓰는 단일 스킬의 내부를 처음부터 끝까지 뜯어본다.
- 스킬은 "본문(순서만) + 참고 문서 4개 + 실행 파일 5개" 구조이며, 각 단계마다 화자가 직접 틀리면서 얻은 함정(실측 사용, 받아쓰기 배제, 프레임 유지, 화면 흔들림 제거, 레퍼런스 복사 금지 등)이 한 줄씩 누적돼 있다.
- 핵심 철학: 스킬은 매뉴얼이 아니라 "흉터" — 처음부터 완벽하게 쓰지 말고 짧게 만들어 쓰다가 틀릴 때마다 한 줄씩 붙이는 게 훨씬 빠르다.

## 전문 — 시간순 워크스루

### [00:00–00:13] 이 영상 자체가 스킬의 산출물
화자는 이 영상이 사람이 편집하지 않았다고 못을 박는다. 데본(코딩 에이전트로 추정)을 쓰고 목소리를 만들고 자막을 붙이고 화면을 그리고 렌더까지, 스킬 하나가 다 했다는 것이다. 지난 영상에서 "매일 쓰는 스킬 하나를 통째로 뜯어보겠다"고 약속했고 오늘 그걸 실행한다고 예고한다.

### [00:13–00:27] 왜 스킬로 묶었나 — 8단계 반복 작업
유튜브 영상 한 편을 만들려면 단계가 많다. 화자는 이를 여덟 단계로 정리한다: 대본 쓰기 → 목소리 입히기 → 자막 타이밍 맞추기 → 화면 만들기 → 렌더 돌리기 → 썸네일 뽑기 → 업로드 → 예약 걸기.

### [00:27–00:55] 매번 시키던 방식의 문제
처음엔 이 단계들을 매번 개별로 시켰다("대본 써 줘", "목소리 만들어 줘", "자막 붙여 줘"). 되긴 됐지만 결과가 매번 달랐다는 게 문제다. 어제는 자막이 잘 맞았는데 오늘은 반박자씩 밀리고, 어제 쓴 옵션을 오늘은 안 쓰는 식이었다. 가장 답답했던 건 이미 알고 있는 걸 매번 다시 알려줘야 했다는 점이다.

> "제일 답답했던 건 제가 이미 알고 있는 걸 매번 다시 알려 줘야 한다는 거였어요. 이 목소리 써라. 이 해상도로 렌더해라. 자막은 몇 픽셀 위에 둬라." [00:42]

똑같은 지시를 매번 다시 타이핑하고 있었기에 스킬로 묶었다.

### [00:55–01:19] 스킬 경계 정하기 — 하나의 스킬 = 하나의 결과물
묶기 전에 "어디까지를 한 스킬로 볼 거냐"부터 정했다. 처음엔 욕심을 내서 영상도 만들고 쇼츠도 자르고 인스타에도 올리는 거대한 스킬 하나를 만들려 했지만 결과가 안 좋았다. 본문이 너무 길어지니 클로드가 중간을 흘렸다(빠뜨렸다)는 것이다. 그래서 쪼갰다 — 롱폼 제작 하나, 쇼츠 따로, 인스타 따로. **하나의 스킬은 하나의 결과물만 만들게** 했다.

### [01:19–01:36] 스킬의 3덩어리 구조
이 스킬은 세 덩어리다.
- **본문 하나**: 여기엔 순서만 있다 — 뭘 먼저 하고 뭘 나중에 하는지.
- **참고 문서 네 개**: 목소리 만드는 법, 화면 만드는 법, 썸네일 만드는 법, 업로드하는 법.
- **실행 파일 다섯 개**: 이건 코드다.

### [01:36–02:05] 왜 이렇게 나눴나 — "읽는 시점을 옮긴다"
본문에 전부 적으면 클로드가 매번 그걸 다 읽는다. 지난 영상에서 말한 "매뉴얼 200장 문제"다. 그래서 순서만 본문에 두고 나머지 셋은 밖으로 뺐다. 썸네일 만들 때가 되면 그때 썸네일 문서만 읽는다. 숫자로 보면 본문은 300줄이 조금 안 되고, 참고 문서 네 개를 합치면 본문보다 훨씬 길지만 그 긴 부분은 필요할 때만 열린다.

> "글자 수를 줄인 게 아니라 읽는 시점을 옮긴 겁니다." [01:59]

이게 지난 영상에서 말한 "쪼개기"의 실제 모습이라고 정리한다.

### [02:05–02:47] 1단계 대본 — 길이 계산과 실측
첫 단계는 대본이다. 여기서 제일 많이 틀린 건 길이 계산이었다. 10분짜리 영상을 만들려면 대본을 몇 글자 써야 하나 — 한참을 감으로 하다 매번 어긋났다. 방법은 단순하다: 한번 만들어 보고 재는 것. 짧게 합성해서 글자 수를 오디오 길이로 나누면 초당 몇 글자인지 나온다. 화자 목소리는 **초당 8.69자**, 10분이면 약 **5,200자**다.

함정 하나: 목소리 만드는 프로그램들이 예상 시간을 보여주는데 그걸 믿으면 안 된다. 화자가 쓰던 다른 도구는 예상치가 실제보다 50% 넘게 짧았다(주장). 그래서 스킬에 "편집기 예상치 말고 실측을 쓰라"고 적어 놨다.

### [02:47–03:07] 대본을 자막 한 줄씩 쓰는 이유
대본을 쓸 때 문단으로 쓰지 않고 **자막 한 줄씩** 쓴다. 처음엔 글 쓰는 느낌이 안 나 어색했지만, 이렇게 쓰면 뒤 단계가 통째로 편해진다. 이 배열이 그대로 읽을 대본이 되고 동시에 화면 자막이 되어 변환할 게 없다. 또 한 줄씩 쓰면 문장이 저절로 짧아지고 말하듯이 써진다.

### [03:07–03:34] 2단계 나레이션·자막 — 순서를 뒤집다
보통은 목소리를 만들고 그 음성을 다시 받아쓰기(STT) 돌려서 자막을 뽑는다. 그런데 받아쓰기가 틀린다 — 특히 고유명사, 화자 이름도 자꾸 틀리게 나왔다. 그래서 순서를 바꿨다: **자막을 먼저 쓰고**(한 줄씩 끊어서) 그걸 그대로 읽힌다. 그러면 목소리를 만들 때 각 글자가 몇 초에 나오는지 같이 알려줘서 받아쓰기가 아예 필요 없고 틀릴 일도 없다.

### [03:34–03:47] 자막 한 줄 30자 이하 — 픽셀 근거
자막 한 줄은 30자 이하로 끊는다. 글자가 길어지면 화면 밖으로 잘려 나가기 때문이다. 한 글자가 약 42픽셀이니 30자면 1,260픽셀, 화면 안에 딱 들어간다.

### [03:47–04:18] 목소리 만들 때 규칙 세 가지
- **문단 단위로 만든다**: 한 줄씩 따로 만들면 문장마다 억양이 초기화돼 뚝뚝 끊긴다. 약 800자씩 묶어 한 번에 만들면 자연스럽게 이어진다.
- **소리 크기를 맞춘다**: 문단마다 크기가 다르게 나온다. 화자의 경우 제일 조용한 문단과 제일 큰 문단 차이가 10데시벨이 넘었다(주장). 그냥 이어붙이면 영상 중간부터 소리가 작아지므로, 문단마다 크기를 재서 같은 높이로 맞추고, 맞춘 뒤 다시 재서 차이가 3데시벨 안쪽인지 확인한다.
- **대본을 고쳤으면 임시 파일을 지운다**: 안 지우면 예전에 만든 목소리가 그대로 다시 나온다. "고쳤는데 왜 안 바뀌지?" 하며 한참 헤맨 적이 있다.

### [04:18–04:56] 3단계 화면 만들기 — 규격·흔들림 함정
여기서 제일 많이 넘어졌다 — 규격을 안 지켜서다.
- **프레임**: 이 채널 영상은 초당 60프레임이 기본인데, 렌더 시간이 두 배라 30으로 낮추고 싶어진다. 실제로 그랬더니 모션이 뚝뚝 끊겨서 다시 렌더했다.
- **흔들림**: 신(scene)이 바뀔 때마다 화면 전체를 살짝 확대하는 효과를 넣어 뒀는데, 한 장면만 보면 괜찮지만 장면들을 이어붙이면 영상 내내 화면이 흔들렸다. 배경 텍스트의 간격도 신마다 조금씩 벌어지고 있었다. 둘 다 지웠다.

### [04:56–05:27] 제목 크기 자동 축소의 부작용
비슷한 문제 하나 더 — 제목 크기다. 화면에 들어가는 내용이 신마다 다르니(어떤 신은 카드 2개, 어떤 신은 목록 5줄) 내용에 맞춰 자동으로 크기를 줄이게 했는데, 제목까지 같이 줄어들었다. 결과적으로 제목이 신마다 커졌다 작아졌다 했고, 실제로 재보니 제일 작을 때가 26픽셀, 제일 작을 때와 클 때 차이가 열 배가 넘었다(주장). 지금은 위쪽 300픽셀을 제목 자리로 고정하고, 자동 축소는 아래쪽 그림에만 건다.

### [05:27–05:40] 흔들림은 눈이 아니라 픽셀로 잡는다
이런 건 눈으로 잡으면 거의 못 잡는다 — 장면 하나씩 보면 다 멀쩡해 보인다. 그래서 픽셀로 잡는다: 연속된 프레임 두 장을 빼서 몇 퍼센트가 바뀌었는지 본다. 요소 등장이 끝났는데도 계속 바뀌고 있으면 그게 흔들리는 것이다.

### [05:40–06:13] 4단계 렌더 — 시간·검증·폰트 실패
렌더는 시간이 걸린다. 11분짜리 영상이 약 4만 프레임이라 그냥 돌려놓고 다른 걸 한다. 끝나면 반드시 영상 길이와 오디오 길이가 맞는지 확인한다 — 여기가 어긋나면 자막이 통째로 밀린다. 렌더가 실패할 때도 있는데, 제일 자주 본 건 폰트를 불러오다 멈추는 것이었다. 미리보기에서는 되는데 렌더에서만 죽는다. 그래서 폰트를 따로 안 불러오고 시스템에 있는 걸 쓴다 — 한글 굵은 글씨는 그걸로도 충분했다. 이런 것도 전부 참고 문서에 적어 뒀다(다음에 같은 에러를 만나면 찾아보면 되니까).

### [06:13–06:38] 5단계 썸네일 — 레퍼런스는 복사 대상이 아니다
여기서 재밌는 걸 배웠다. 처음엔 자기 채널에서 제일 잘된 썸네일을 가져와 똑같이 만들었다 — 논리적으로는 맞다. 그런데 "발려당했다"(성과가 안 나왔다). 제일 잘된 썸네일 스타일은 이미 시청자들이 수십 번 본 화면이라 똑같이 만들면 피드에서 안 보이기 때문이다. 그래서 색부터 바꿨다 — 쓰던 색 말고 반대색으로.

> "레퍼런스는 참고지 복사 대상이 아니더라고요." [06:35]

### [06:38–07:08] 썸네일은 한 장씩 만들고 눈으로 대조
썸네일은 한 장씩 따로 만든다. 세 장을 한 번에 시키면 두 장쯤 조용히 사라진다(만들었다고는 하는데 파일이 없다). 그래서 한 장 만들고 확인, 또 한 장 만들고 확인한다. 만든 뒤엔 반드시 글자를 눈으로 대조한다 — 한글이 자꾸 깨져서 받침이 빠지거나 엉뚱한 글자가 들어가는데 이건 사람이 봐야 잡힌다. 이 영상 썸네일도 그렇게 세 장 만들어 한 장씩 열어 글자를 봤고, 제목도 세 개 준비해 썸네일과 짝을 지었다(어느 조합이 잘 먹히는지 유튜브가 알아서 비교해 준다).

### [07:08–07:44] 6단계 업로드 — 파일 넣기와 웹서버 우회
마지막이 업로드다. 여기가 제일 까다로웠다 — 파일을 브라우저에 넣는 게 생각보다 안 됐다. 자동화 도구가 파일을 넣으려면 보안 때문에 막히는 게 많다. 결국 작은 웹서버를 잠깐 띄우고 그 서버가 파일을 읽어 페이지에 건네주는 방식으로 풀었다. 알아내는 데 꽤 오래 걸렸지만 한번 알아내 스킬에 적어 두니 다음부터는 그냥 된다.

### [07:44–08:04] 업로드 화면의 함정 세 가지
- 제목·설명칸이 평범한 입력창이 아니라 붙여넣기가 안 먹는다 — 다른 방법으로 넣어야 한다.
- 자동완성 창을 닫으려고 ESC를 누르면 업로드 창이 통째로 닫힌다(다행히 임시 저장은 된다).
- 예약할 때 날짜가 내일로 기본 설정돼 있어 오늘로 하려면 직접 골라야 하고, 시간칸은 눌러서 커서를 잡은 다음 타이핑해야 들어간다.

이 세 개를 모르면 업로드 한 번에 30분씩 쓴다.

### [08:04–08:19] 스킬을 쓰는 진짜 이유 + 실행 파일을 코드로 둔 이유
이게 스킬을 쓰는 진짜 이유다 — 어려운 걸 한 번만 풀면 되고 두 번째부터는 안 풀어도 된다.

> "글로 적어 두면 매번 다시 짜요. 파일로 두면 그냥 실행해요." [08:14]

이것이 실행 파일 다섯 개를 넣어 둔 이유다.

### [08:19–08:54] 실행 파일 다섯 개의 역할
- **첫째, 목소리 만드는 파일**: 대본을 넣으면 음성과 자막 타이밍을 한꺼번에 뱉는다. 소리 크기 맞추는 것도 이 안에 있다.
- **둘째, 썸네일 만드는 파일**: 한 장씩 순서대로 만들고 실패하면 다시 시도한다.
- **셋째, 화면 캡처하는 파일**: 화면 전체를 찍으면 열어둔 다른 창이 같이 찍혀 사고가 날 뻔했다. 그래서 브라우저로 그 페이지만 찍게 했다.
- **넷째, 파일 넘겨주는 서버**(앞서 말한 업로드용 웹서버).
- **다섯째, 자막 만드는 보조 파일**: 남이 만든 음성으로 중간부터 시작할 때만 쓴다.

### [08:54–09:17] 이 스킬을 안 쓰는 때
- **쇼츠 만들 때**: 규격이 다르고 자막 위치도 달라 따로 스킬이 있다.
- **대본만 필요할 때**: 대본 스킬만 부르면 된다.
- **이미 만든 영상을 올리기만 할 때**: 이 스킬을 쓰긴 하되 앞 단계는 건너뛴다. 중간부터 시작할 수 있게 "뭘 갖고 있으면 몇 단계부터 시작하면 되는지" 표로 정리해 뒀다.

### [09:17–09:38] 돈 얘기 — 비용을 미리 알리는 습관
목소리 만드는 건 글자 수만큼 돈이 나간다. 10분짜리 대본이면 5,000자가 넘고, 대본을 고쳐 다시 만들면 그만큼 또 나간다. 그래서 스킬에 "만들기 직전에 얼마 나갈지 먼저 알리라"고 적어 놨다 — 그래야 분량을 다시 정할 기회가 생긴다. 화자는 이런 건 기능이 아니라 습관에 가깝지만 이런 것도 스킬에 넣을 수 있다고 짚는다.

### [09:38–10:02] 정리 — 스킬은 매뉴얼이 아니라 흉터
정리하면 이 스킬 하나에 화자가 밟은 함정이 전부 적혀 있다: 예상치 믿지 마라, 받아쓰기 하지 마라, 프레임 낮추지 마라, 화면 전체를 움직이지 마라, 레퍼런스를 복사하지 마라 — 전부 화자가 틀리고 나서 적은 것이다.

> "그래서 스킬은 매뉴얼이 아니라 흉터에 가까워요. 틀릴 때마다 한 줄씩 늘어나요." [09:52]

[의견] 처음부터 완벽하게 쓰려고 오래 붙잡고 있는 것보다 일단 짧게 만들어 쓰고 틀릴 때마다 붙이는 게 훨씬 빠르다.

### [10:02–10:18] 마무리 — 질문과 다음 예고
화자는 시청자에게 "어떤 일을 제일 자주 반복하는지" 댓글로 남겨 주면 그걸 스킬로 어떻게 묶을지 같이 생각해 보겠다고 한다. 더 깊은 얘기는 스킬샵과 오픈톡방에서 계속 나누고 있다고 안내하고(세일즈·커뮤니티 유입 장치), 다음 영상에서는 이 스킬이 실제로 도는 걸 처음부터 끝까지 보여주겠다고 예고하며 마친다.
