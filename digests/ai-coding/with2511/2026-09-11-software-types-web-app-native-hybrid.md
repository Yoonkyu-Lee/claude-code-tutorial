## 요약 (주제별)

### 1. 소프트웨어의 대분류 — 이 영상의 뼈대
- 눈에 보이는 형태로 크게 **웹 애플리케이션**과 **스마트폰 앱**으로 나뉜다. 웹은 브라우저로 URL에 접속해 보는 형태, 앱은 기기에 설치해서 쓰는 형태(카카오톡·게임·티맵).
- 여기에 **PC 설치형 소프트웨어**(엑셀, 파워포인트, 워드, 포토샵, 백신), **시스템 소프트웨어**(OS — 윈도우·리눅스·맥OS, 그리고 드라이버), **DBMS**(데이터 저장 전용 — MySQL·오라클·몽고DB)가 더해져 총 5개 분류가 된다.
- 계층: **하드웨어(CPU·메모리·디스크, 노트북·데스크탑) → OS → 그 위에서 동작하는 소프트웨어**(브라우저, 엑셀, 카카오톡).
- 전체 그림 한 컷: DB가 있고, 리눅스 같은 OS 위에 서버를 설치하고, 그 서버가 앱과 통신하거나 웹 브라우저가 접속해 웹 서버에서 내용을 받아온다.

### 2. 용어 정리 — 소프트웨어 / 애플리케이션 / 하드웨어
- 첫 갈림은 **소프트웨어 대 하드웨어**. 소프트웨어 안에 애플리케이션이 들어 있다.
- 대부분의 소프트웨어는 애플리케이션이 맞지만, **운영체제는 애플리케이션이라 부르지 않는다 — 그래도 소프트웨어는 맞다**는 것이 핵심 구분점.
- "소프트웨어는 눈에 안 보인다"는 말의 뜻: 엑셀 창이 뜬 것을 보는 차원이 아니라, 코드로 만들어져 컴퓨터 안에 저장된 파일들이 실행되는 형태라는 의미.

### 3. 웹의 동작 원리 — URL·HTTP·프로토콜
- 웹의 독특함: 엑셀처럼 설치해 내 컴퓨터 안에서 쓰는 게 아니라, **처음엔 빈 화면이었다가 URL에 접속해야 데이터를 보여 준다**.
- URL = Uniform Resource Locator = 인터넷 주소. 쪼개면 앞쪽 **HTTP**, 뒤쪽 **도메인**.
- **HTTP의 P = 프로토콜 = 약속이자 통신 규칙**. "이렇게 주면 이렇게 이해해라"는 상호 약속이고, 그중 웹 데이터를 주고받는 대표 약속이 HTTP(HyperText Transfer Protocol).
- 이 단계에서 요구하는 이해 수준은 "웹사이트는 URL이고, URL은 HTTP + 도메인으로 쪼개지며, P는 프로토콜 = 주고받기 위한 약속"까지. 나머지는 책 뒷부분.
- 웹의 제약: **네트워크가 연결돼야만 쓸 수 있다**. 카카오톡도 네트워크가 필요하지만, 일부 앱은 연결 없이도 되는 반면 웹은 대부분 서버에서 데이터를 받아오는 구조라는 대비를 강조하려는 표현이다.
- 네트워크가 잘 되면서 문서 작성·이메일·예약까지 웹으로 수렴하고 있다. `[의견]` "여러분이 만드실 서비스도 아마 웹을 검토하실 확률이 많다"[11:37].

### 4. 프론트엔드와 백엔드 — 기술 스택
- **프론트엔드(화면)** = **HTML**(마크업 언어, 구조) + **CSS**(스타일·꾸밈) + **자바스크립트**(동작).
- **백엔드(서버)** 언어 = **자바, 자바스크립트, 파이썬, PHP**(전통적으로 많이 쓰임). 실제 개발 시 쓰는 것으로 **리액트, 스프링부트, 노드, FastAPI**를 나열(리액트는 통상 프론트 쪽이지만 영상에서는 함께 묶어 언급).
- 프론트엔드/백엔드의 본격적인 내용은 **다음 영상**에서 다룬다고 예고.

### 5. 실습 시연 두 가지 (직접 따라 할 수 있는 것)
- **페이지 소스 보기**: 사이트에서 오른쪽 클릭 → '페이지 소스 보기' → 자동 줄바꿈 → 그래도 안 예쁘면 코드 포매팅 사이트(자막 "프리티" — Prettier 계열로 추정)에 붙여 정렬. 정렬된 소스에서 **바깥을 감싸는 HTML 태그(header 등)**, **script 태그와 .js 파일 = 자바스크립트**, **.css 파일(태그 없이도 넣을 수 있음)**, **body부터의 실제 내용**을 각각 짚어 준다. 목적은 문법 습득이 아니라 "화면은 이렇게 보였지만 실제 소스는 이러하다"를 눈으로 확인시키는 것.
- **F12 개발자 도구**: F12로 개발자 도구를 열고 화면 크기를 조절하면 아이폰 12 Pro, 아이폰 16 Pro Max 같은 프리셋에서 사이트가 어떻게 보이는지 확인 가능. 휴대폰에 일일이 깔기 전 빠른 점검법. 화자는 자기 사이트가 깨져 보이는 것을 보여 주며 "개선이 필요하겠죠"라고 인정하고, 반대로 구글 사이트는 크기를 바꿔도 자연스럽게 늘어나는 것을 대조로 보여 준다.
- 시연에 쓴 자기 사이트 이름은 `[불명확: 원문 "바이브코딩 위술로트 알렉"]` — 자막 음차로 확정 불가. 검색창에 "API 궁금합니다"를 넣으면 설명이 나오는 형태.

### 6. 웹사이트 vs 웹서비스 — API와 매시업
- **웹사이트** = 사람이 쓰는 것(구글·네이버처럼 눈으로 보는 화면).
- **웹서비스** = 웹 형태로 서비스를 제공하는 것, **대부분 API로 제공**되며 **컴퓨터끼리 데이터를 주고받는** 쪽. 우리가 **이용할 수도 있고 제공할 수도 있는** 양방향 개념이라 따로 언급했다.
- **매시업(mashup)** = 이런 서비스들을 다양하게 조합해 또 다른 서비스를 만드는 것.
- API 자체는 책 뒷부분에서 본격적으로 다루므로 지금은 "API가 있다" 정도까지.

### 7. 앱의 4가지 형태 — 웹 / 네이티브 / 웹앱 / 하이브리드 (영상이 "중요하다"고 명시한 부분)
- **웹**: 브라우저로 접속해 내용을 보는 형태.
- **네이티브 앱**: 각 OS의 언어로 직접 만들어 기기에 설치. **안드로이드 = 자바·코틀린**, **iOS = Swift·오브젝티브-C**. 양대 OS는 구글 안드로이드 / 애플 iOS.
- **웹앱**: 웹을 위주로 보여 주는 형태. 대표 예 **네이버 앱** — "이게 웹사이트다"라는 느낌이 있다.
- **하이브리드 앱**: 웹 기술과 네이티브를 섞는다. **위치·카메라** 같은 네이티브 기능은 네이티브로, 안쪽 데이터·콘텐츠는 웹처럼 가져와 보여 준다.
- **선택 기준**: 스마트폰 기능을 직접적으로 많이 써야 하면 네이티브, 다양한 기능이 조화롭게 필요하면 하이브리드.

### 8. 제목이 말하는 "선택의 포인트" — 앱의 업데이트 문제
- 앱은 **사용자가 다시 다운로드하지 않으면 버전을 올릴 수 없다**. 업데이트가 나와도 설치하지 않으면 그대로다.
- 그래서 **강제 업데이트**를 걸어 "업데이트 버전 있습니다, 다운로드해서 설치할까요?"를 띄우고 그 전까지 실행을 막는 경우가 있다 — 이런 상황까지 설계에 고려해야 한다.
- `[의견]` 아주 필요하지 않은 이상 사용자는 설치를 잘 안 하고, 요즘은 앱 관리도 어렵다는 것이 화자의 경험적 판단. 수치 근거는 제시되지 않았다.
- **반응형 웹**은 그 대척점의 장점 — 하나의 웹사이트가 PC·태블릿·휴대폰 화면 크기에 맞춰 자동으로 매끄럽게 바뀐다(구글 사이트가 좋은 예).

### 9. 책의 구성·난이도에 대한 저자 주장 (세일즈 구조)
- `[의견]` 컴퓨터 내부 구조나 네트워크가 아니라 네이버·카카오톡처럼 **이미 다 아는 결과물**에서 시작해서 쉽다는 것이 저자의 설계 의도이자 자기 평가. "편하게 읽어진다는 게 제 의도가 맞다"[00:59].
- 각 절마다 "지금은 여기까지만 이해하면 된다"고 **범위를 좁혀 주는 것**이 반복 패턴이다 — DBMS·API·HTTP 풀네임·HTML 문법 모두 "이름과 역할만 알면 되고 상세는 뒤에서"로 미룬다.
- 세일즈 장치: "제가 영상으로 부연 설명을 해 드릴 테니 마음 편히 책을 구매하셔도 좋겠습니다"[05:05 부근]. 마무리에는 좋아요 요청 CTA.

### [00:00–01:20] 파트 2 도입 — "쉽게 시작한다"는 책의 접근법
화자는 자신의 책 파트 2 "소프트웨어의 종류와 특징"을 펼치며, 이 파트를 굉장히 쉽게 접근하도록 썼다고 말한다. 그 근거로, 컴퓨터 내부 구조나 네트워크부터 시작하지 않고 **일반인도 이미 많이 접한 결과물**에서 출발했다는 점을 든다. 네이버·카카오톡 같은 것들이 곧 소프트웨어라는 문장으로 시작해서, 네이버는 대표적인 웹사이트이니 웹 애플리케이션 설명으로, 카카오톡은 대표적인 앱이니 앱이 어떻게 연동하고 네트워크로 데이터를 주고받는지로 차차 풀어 나간다는 구성이다.

> "지금 좀 다소 쉽게 느껴진다, 그냥 편하게 읽어진다 — 맞습니다. 제 의도가 맞고, 이렇게 편하게 읽다가 조금씩 조금씩 그 구조에 대해서 이제 살펴보게 됩니다." [00:59]

`[의견]` 쉽게 읽힌다는 평가와 "의도한 난이도 설계"라는 설명은 모두 저자 본인의 자기 평가다.

### [01:21–02:30] 소프트웨어의 대분류 — 웹 / 앱 / PC 설치형
종류를 나열하면 우선 **웹 애플리케이션**과 **스마트폰 앱**이 있고, 이 둘이 우리 눈에 보이는 형태의 큰 구분이라고 정리한다. 웹은 웹 브라우저를 통해 URL(인터넷 주소)에 접속해서 내용을 보는 형태이고, 스마트폰 앱은 휴대폰에 **설치**해서 특정 기능을 주고받으며 쓰는 형태다. 앱의 예로 카카오톡, 게임, 위치 기반 서비스인 티맵을 든다. 여기에 더해 **PC 설치형 소프트웨어**(엑셀, 파워포인트, 백신 같은 PC 프로그램)가 또 한 분류로 존재한다.

### [02:30–03:30] 시스템 소프트웨어(OS)와 하드웨어의 계층 관계
시스템 소프트웨어로는 **운영체제(OS, Operating System)**가 있다. 브라우저나 엑셀 같은 소프트웨어가 돌아가려면 OS가 필요하고, 가장 많이 접하는 것이 윈도우, 그 외에 맥OS·리눅스가 있다(자막 원문 "리스 윈도우", "메os 리누스" — 문맥상 리눅스/윈도우/맥OS로 교정). 화자는 "이것도 소프트웨어"라는 점을 강조한다. 반대로 **하드웨어**는 CPU·메모리·디스크가 대표적이고, 눈에 보이는 노트북이나 데스크탑 컴퓨터가 하드웨어다. 계층으로 보면 하드웨어 위에 OS가 있고, 그 위에 브라우저나 (휴대폰이면) 카카오톡 같은 소프트웨어가 동작한다.

### [03:31–03:55] DBMS — 데이터 저장 전용 소프트웨어
별도 분류로 **DBMS**가 있다. 데이터만 주로 저장하는 소프트웨어이며, MySQL·오라클·몽고DB 같은 종류가 있다(자막 원문 "마이스QL", "몽고디"). 이것도 소프트웨어 중 하나라는 분류만 편하게 이해하면 되는 범위라고 선을 긋는다.

### [03:55–05:15] 전체 그림 한 컷과 "여기까지만 이해하면 된다"는 범위 설정
결국 나중에는 DB가 있고, 리눅스 같은 OS 위에 서버를 설치하고, 그 서버가 앱과 통신하거나 웹 브라우저가 접속해 웹 서버에서 내용을 받아오는 구조가 된다고 한 문장으로 그려 준다. 다만 지금 단계에서 이해할 것은 "소프트웨어 종류 중에 웹이 있고, 앱이 있고, OS가 있고, DB가 있고, 설치형(엑셀·파워포인트·백신)이 있다"까지라고 못 박는다. 단계적으로 어려워지는 구성이라 비전공자·비개발자, 특히 AI로 개발해 보려는 사람도 따라올 수 있다는 것이 저자의 판단이며, 영상으로 부연 설명을 해 줄 테니 마음 편히 책을 구매해도 좋겠다는 권유를 덧붙인다(세일즈 장치 — 여기 한 번 기록).

### [05:15–06:50] 소프트웨어 vs 애플리케이션 vs 하드웨어 — 용어 정리
화자 스스로 "잔소리 같은 수준의 자세한 내용"이라고 표현하면서 용어를 정리한다. 소프트웨어와 애플리케이션은 비슷한 말이지만 같지는 않다. 큰 구분은 먼저 **소프트웨어 대 하드웨어**이고, 소프트웨어 안에 애플리케이션이 있다. 대부분의 소프트웨어가 애플리케이션이 맞지만, **운영체제는 애플리케이션이라고 부르지 않는다 — 그러나 소프트웨어는 맞다**는 것이 핵심 구분점이다. 하드웨어는 CPU·메모리·디스크, 그리고 눈에 보이는 노트북·데스크탑이고, 소프트웨어는 눈에 안 보인다 — 엑셀 창이 떴다는 의미의 '보임'이 아니라, 코드로 만들어져 컴퓨터 안에 저장된 파일들이 실행되는 형태라는 뜻이다. OS도, 웹 브라우저도, 엑셀·파워포인트·게임도 모두 소프트웨어다.

### [06:52–08:20] 웹사이트를 따로 뺀 이유 — 홈페이지에서 웹사이트로
책에서 웹사이트를 따로 떼어 낸 이유는 웹이라는 형태가 독특하기 때문이다. 엑셀 같은 것은 설치해서 그 컴퓨터 안에서 쓰지만, 웹은 **처음엔 반드시 빈 화면이었다가 URL에 접속하면 데이터를 보여 준다**. 초창기에는 이런 것들을 대부분 '홈페이지'라고 불렀고 주로 텍스트와 이미지 정도였지만, 지금 웹사이트는 다양한 기능을 탑재하고 있다. 웹사이트의 대표적 특징은 URL(Uniform Resource Locator)을 갖는다는 것이고, 브라우저를 켜고 주소를 쳐서 어딘가 들어가는 동작은 모르는 사람이 거의 없다 — 그 익숙한 동작이 곧 우리가 만들어야 할 사이트의 동작 원리이기도 하다.

### [08:21–10:28] URL 쪼개 보기 — HTTP와 도메인, P는 프로토콜
URL은 인터넷 주소이고, 이미 아는 상식을 쪼개서 개념으로 이해하는 과정이 이어진다. URL 자체의 풀네임보다 더 중요한 것은 **HTTP로 시작한다**는 점, 그리고 `http:` 뒤의 부분이 **도메인**이라는 표현이라는 점이다. 여기서 한 걸음 더 들어가 **HTTP의 P가 프로토콜(Protocol)**이고, 프로토콜은 **약속이자 통신 규칙**이라고 설명한다.

> "약속이라는 건 뭐냐? 이렇게 주면 이렇게 이해해라, 이렇게 주면 이렇게 이해해라. 뭐 서로 약속을 하는 거죠. 주고받기 위한 약속입니다." [09:34]

그중 웹사이트 데이터를 주고받는 대표 프로토콜이 HTTP(HyperText Transfer Protocol)이다. 다만 이 단계에서 그 풀네임까지는 복잡하니 뒤에서 자세히 다루고, 지금은 "웹사이트는 URL이고, URL은 HTTP라는 개념과 도메인으로 쪼개지며, P는 프로토콜, 프로토콜은 주고받기 위한 약속"까지만 이해하면 된다고 정리한다.

### [10:29–11:42] 웹의 특징이자 제약 — 네트워크 연결 필수
책은 웹사이트의 장점·단점·차이점을 설명하는데, 그중 하나가 "웹사이트는 네트워크가 연결돼야만 사용할 수 있다"는 것이다. 화자는 여기에 스스로 단서를 단다 — 카카오톡도 네트워크가 연결돼야 하는 건 당연하지만, **어떤 앱은 연결 없이도 쓸 수 있는** 반면 웹은 대부분 서버에 접속해 데이터를 가져오는 구조라는 점을 강조하기 위한 표현이라는 것이다.

### [11:42–12:15] 웹으로의 수렴 — "여러분 서비스도 웹을 검토할 확률이 높다"
네트워크가 워낙 잘 되어 있다 보니 많은 프로그램이 웹 형태로 제공되고 있고, 이제는 웹으로 문서 작성도, 이메일도, 예약도 다 된다고 짚는다.

> "여러분이 만드실 그 서비스도 아마 웹을 검토하실 확률도 좀 많죠." [11:37] `[의견]`

### [12:15–13:07] 웹 vs 앱 비교로 넘어가며 — 프론트엔드의 정체
이어서 책은 웹사이트와 앱이 어떻게 다른지를 한 번 더 쪼개 비교한다. 웹은 브라우저에서 주소를 통해 접속하며 대부분 온라인에서 제공되는 서비스다. 그 화면을 **프론트엔드**라고 부르는데, 프론트엔드는 **HTML·CSS·자바스크립트**로 만들어진다. HTML은 마크업 언어로 구조를 만들고, CSS는 스타일(꾸밈)을 담당하는 문법이며, 자바스크립트라는 언어로 화면이 동작한다 — 이 정도 이해면 충분하다고 한다.

### [13:07–15:15] 실습 시연 — 페이지 소스 보기로 HTML·CSS·JS 확인
말로만 하지 않고 브라우저 시연이 들어간다. 화자는 자신이 바이브코딩으로 만든 사이트(`[불명확: 원문 "바이브코딩 위술로트 알렉"` — 사이트명이 자막에서 음차되어 확정 불가])를 띄워 검색창에 "API 궁금합니다"를 입력해 설명이 나오는 것을 보여 준 뒤, **오른쪽 클릭 → 페이지 소스 보기**를 누른다. 소스가 한 줄로 붙어 보이자 자동 줄바꿈을 켜고, 그래도 보기 어려우니 소스를 예쁘게 포매팅해 주는 사이트(자막 원문 "프리티" — Prettier 계열 코드 포매터로 추정)에 넣어 정렬한다. 정렬된 소스에서 짚어 주는 것은 세 가지다.

- 가장 바깥을 감싸는 `HTML` 태그(`header` 등 태그 구조) — 이것이 HTML
- `script` 태그와 `.js`로 끝나는 파일 — 이것이 자바스크립트
- `.css` 파일 — CSS는 별도 태그 없이도 파일로 넣을 수 있다
- `body` 부터 시작하는 실제 내용 — 화면에 글자를 찍어 주는 부분

요지는 "화면에는 이렇게 보였지만 실제 소스는 이러하다", 즉 HTML·CSS·자바스크립트라는 문법으로 화면을 만든다는 것을 눈으로 확인시키는 것이다. 문법을 다 이해하라는 게 아니라 "HTML이 뭐야, CSS가 뭐야, 자바스크립트가 뭐야" 정도까지만 알면 되는 단계라고 다시 범위를 좁힌다.

### [15:15–16:30] 백엔드 — 언어와 프레임워크
화면이 프론트엔드라면 서버 쪽은 **백엔드**다. 백엔드 서버를 만드는 언어로는 **자바, 자바스크립트, 파이썬, PHP**(전통적으로 많이 쓰임)를 든다. 실제 개발에 쓰는 것으로는 **리액트, 스프링부트, 노드, FastAPI** 같은 것들을 나열한다(리액트는 통상 프론트엔드 쪽이지만 영상에서는 함께 묶어 언급). 프론트엔드와 백엔드는 기술적으로도 다르고 책 뒤에서 충분히 다루므로, 여기서는 설명을 위한 맛보기라고 밝힌다.

### [16:30–17:10] 앱 — 안드로이드/iOS와 네이티브 앱
스마트폰 쪽은 앱이고, OS로 신경 쓸 것은 **안드로이드와 iOS** 둘이다. 안드로이드는 주로 **자바나 코틀린**으로, iOS는 **오브젝티브-C나 Swift**로 개발하며, 이렇게 각 OS의 언어로 직접 만든 것을 **네이티브 앱**이라고 부른다. 유형별 차이는 뒤에서 더 자세히 나오고, 지금은 "이러한 종류가 있습니다" 정도까지의 단계다.

### [17:10–17:47] PC 소프트웨어와 시스템 소프트웨어 재확인
PC 소프트웨어는 설치해서 쓰는 프로그램으로 워드·엑셀·포토샵이 대표적이며, 백신도 여기 해당한다(자막 원문 "핏소프트웨어" → PC 소프트웨어). 시스템 소프트웨어는 앞서 구두로 말한 OS에 해당하고, 윈도우·리눅스·맥OS에 더해 **드라이버**도 시스템 소프트웨어로 분류한다.

### [17:47–18:56] 데이터베이스 — 구조화해서 저장하는 전용 소프트웨어
데이터베이스는 "조금 더 자세히 다룰 중요한 부분"으로 소개된다. 데이터가 주로 저장되는 전문 소프트웨어이며, 이름만이라도 기억하면 좋은 것으로 **MySQL, 오라클, 몽고DB**를 든다(자막 원문 "마이스/마이오스", "몽고디"). 핵심 성질은 **구조화 저장**이다 — 텍스트 파일에 텍스트를 쭉 적는 형태가 아니라, 의미 있는 내용끼리 묶어서 저장하며 그것을 '테이블' 같은 표현으로 부른다. 상세는 데이터베이스 파트에서 다루고, 지금은 "소프트웨어 중에 데이터베이스가 있다" 정도면 된다.

### [18:57–20:18] 웹사이트 vs 웹서비스 — API와 매시업
같은 '웹'이라도 둘을 구분한다. **웹사이트**는 우리가 구글이나 네이버에 접속해서 보는 것, 즉 **사람이 쓰는 것**이다. **웹서비스**는 웹 형태로 서비스를 제공하는 것으로 **대부분 API로 제공**되며, **컴퓨터끼리 데이터를 주고받거나** 우리가 이용하려고 접속해서 받아오는 쪽이다. 화자가 웹서비스를 따로 언급한 이유는 그것이 **이용할 수도 있고 제공할 수도 있는** 양방향 개념이기 때문이고, 어느 쪽이든 API를 알아야 한다. API 자체는 뒤에서 본격적으로 다루므로 지금은 "API가 있다" 정도. 여기에 **매시업(mashup)** 개념이 붙는다 — 이런 서비스들을 다양하게 조합해 또 다른 서비스를 만드는 것을 매시업이라고 한다(자막 원문 "매쉬업", "당하게 조합" → 다양하게 조합).

### [20:18–21:12] 스마트폰 애플리케이션과 양대 OS
스마트폰 애플리케이션은 설치해서 쓰는 것으로 카카오톡, 책 읽는 앱, 전화 기능, 위치 기능, 지도, 지하철 앱 등이 예시다. 이 부분은 독자가 이미 많이 써 봤기 때문에 편하게 읽으면 이해되는 영역이라고 한다. 운영체제 얘기로는 **구글이 만든 안드로이드, 애플의 iOS**가 양대 축이라는 설명이 들어간다.

### [21:13–22:35] 중요한 구분 — 웹 / 네이티브 앱 / 웹앱 / 하이브리드 앱
화자가 "중요한데요"라고 강조하며 들어가는 대목이다. 실제로 만들 때 이 형태 중 하나를 고르게 되므로 관심이 더 가는 부분이라는 것.

- **웹**: 웹 브라우저로 접속해 내용을 보는 형태
- **앱(네이티브 앱)**: 스마트폰이나 태블릿 기기에 설치해서 쓰는 형태
- **웹앱**: 웹을 위주로 보여 주는 형태. 대표 예로 **네이버 앱**을 들며 "이게 웹사이트다"라는 느낌이 있다고 설명한다
- **하이브리드 앱**: 웹 기술과 네이티브를 같이 쓸 수 있게 한 형태. 앱과 웹앱에 각각 장단점이 있으니 이를 조합해서, **위치·카메라** 같은 네이티브 기능은 네이티브로 쓰고 안쪽 데이터·콘텐츠는 웹처럼 가져와 보여 주는 방식이다. 이런 형태로도 많이 만든다

### [22:37–23:38] 앱의 결정적 약점 — 업데이트는 사용자가 받아야 한다
제목이 말하는 '선택의 포인트'가 여기서 나온다. 앱은 **사용자가 다시 다운로드하지 않으면 버전을 올릴 수 없다**. 업데이트가 나와도 사용자가 설치하지 않으면 바뀌지 않으므로, 어떤 경우에는 **강제 업데이트**를 걸어 "업데이트 버전 있습니다, 다운로드해서 설치할까요?"를 띄우고 그 전에는 더 이상 실행되지 않게 막기도 한다. 이런 상황까지 고려해야 하는 것이 앱이고, 아주 필요하지 않은 이상 사용자가 설치를 잘 안 할뿐더러 요즘은 **관리도 어렵다**는 점을 이해해야 한다고 말한다. `[의견]` 설치 기피·관리 난이도에 대한 판단은 화자의 경험적 견해이며, 영상에서 수치 근거는 제시되지 않는다.

### [23:38–25:36] 반응형 웹과 F12 개발자 도구 시연
**반응형 웹**은 "웹사이트인데 반응을 한다"는 뜻으로, PC 브라우저·휴대폰 브라우저·태블릿의 화면 크기가 다른 상황에서 사이트가 그 사이즈에 맞게 바뀌는 것이다. 화자는 이걸 확인하는 방법을 직접 보여 준다 — 브라우저에서 **F12**를 누르면 **개발자 도구**가 펼쳐지고, 거기서 화면 크기를 조절하면 휴대폰 크기로 어떻게 보이는지 확인할 수 있다. 휴대폰에 일일이 깔아 보기 전에 빠르게 점검하는 방법이다. 아이폰 12 Pro나 아이폰 16 Pro Max 같은 프리셋에서 자기 사이트가 **깨져 보이는 것**을 보여 주며 "이런 건 개선이 필요하겠죠"라고 짚고, 반대로 **구글 사이트**를 열어 크기를 바꾸면 화면이 자연스럽게 넓어졌다 좁아지는 것을 보여 준다 — 그렇게 매끄럽게 맞춰지는 것이 반응형 웹이라는 개념이다.

### [25:37–26:24] 네이티브 앱을 선택하는 기준 / 하이브리드 앱 재정리
네이티브 앱은 설치되는 형태이고, **언제 선택하느냐**의 기준은 **스마트폰의 기능들을 직접적으로 많이 써야 할 때**다. 안드로이드는 자바·코틀린, iOS는 Swift·오브젝티브-C로 개발하며 설치 과정이 필요하다. 하이브리드 앱은 **다양한 기능이 조화롭게 필요할 때** 각 방식의 장점을 끌어와 이용하는 방식이라고 다시 정리한다.
